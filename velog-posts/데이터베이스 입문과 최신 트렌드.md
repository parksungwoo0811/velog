<blockquote>
<p>우리가 매일 사용하는 쇼핑몰, 은행 앱, 배달 앱은 수많은 데이터를 어떻게 안전하게 저장하고 함께 사용할까?<br />이 글에서는 데이터베이스의 기초 구조를 먼저 미리 보고, 최신 기술 사례를 통해 데이터베이스가 실제 서비스와 AI 환경에서 어떻게 활용되는지 살펴본다. 이후 파일 관리의 한계부터 DBMS, 관계형 데이터베이스와 NoSQL의 차이까지 초보자의 눈높이에서 차근차근 알아본다.</p>
</blockquote>
<h2 id="먼저-보는-학습-지도">먼저 보는 학습 지도</h2>
<p>데이터베이스를 처음 공부하면 테이블, 기본 키, SQL처럼 낯선 용어가 한꺼번에 등장한다. 그러나 모든 용어를 처음부터 외울 필요는 없다. 다음 네 가지 질문을 중심으로 공부하면 전체 흐름을 이해하기 쉽다.</p>
<ol>
<li>데이터를 왜 파일이 아닌 데이터베이스에 저장할까?</li>
<li>데이터를 어떤 구조로 나누고 서로 연결할까?</li>
<li>저장한 데이터를 어떤 언어로 조회하고 변경할까?</li>
<li>서비스 규모와 데이터의 성격이 달라지면 어떤 데이터베이스를 선택할까?</li>
</ol>
<p>이 글의 학습 흐름은 다음과 같다.</p>
<pre><code class="language-text">파일과 엑셀의 한계
        ↓
데이터베이스와 DBMS의 등장
        ↓
테이블, 키, 관계, 정규화, ERD
        ↓
SQL로 데이터 정의·조회·변경
        ↓
RDBMS와 NoSQL의 선택
        ↓
대규모 서비스와 AI 시대의 데이터베이스</code></pre>
<hr />
<h2 id="0-본격적으로-시작하기-전-10분-만에-보는-큰-그림">0. 본격적으로 시작하기 전, 10분 만에 보는 큰 그림</h2>
<p>이 절은 앞으로 등장할 개념의 예고편이다. 지금 모두 기억하지 않아도 괜찮다. 글을 끝까지 읽고 다시 돌아오면 각 용어의 관계가 선명해진다.</p>
<h3 id="01-관계형-데이터베이스는-표로-데이터를-관리한다">0.1 관계형 데이터베이스는 표로 데이터를 관리한다</h3>
<p>관계형 데이터베이스는 성격이 같은 데이터를 <strong>테이블(Table)</strong>이라는 표에 모아 저장한다.</p>
<table>
<thead>
<tr>
<th align="right">customer_id</th>
<th>name</th>
<th>email</th>
<th>joined_at</th>
</tr>
</thead>
<tbody><tr>
<td align="right">1</td>
<td>김지훈</td>
<td><a href="mailto:jihoon@example.com">jihoon@example.com</a></td>
<td>2025-03-02</td>
</tr>
<tr>
<td align="right">2</td>
<td>이서연</td>
<td><a href="mailto:seoyeon@example.com">seoyeon@example.com</a></td>
<td>2025-05-14</td>
</tr>
<tr>
<td align="right">3</td>
<td>박민준</td>
<td><a href="mailto:minjun@example.com">minjun@example.com</a></td>
<td>2025-07-21</td>
</tr>
</tbody></table>
<p>이 표에서 각 요소의 이름은 다음과 같다.</p>
<ul>
<li><strong>테이블(Table)</strong>: 고객처럼 같은 성격의 데이터를 모아 놓은 표</li>
<li><strong>행(Row)</strong>: 김지훈 고객처럼 실제 데이터 한 건</li>
<li><strong>열(Column)</strong>: 이름, 이메일, 가입일처럼 저장할 정보의 종류</li>
</ul>
<p>쉽게 말하면 열은 &quot;어떤 정보를 저장할지&quot; 정하고, 행은 그 구조에 맞춰 실제 값을 담는다.</p>
<h3 id="02-기본-키는-행의-이름표다">0.2 기본 키는 행의 이름표다</h3>
<p>동명이인이 있다면 이름만으로 고객을 정확히 구별할 수 없다. 그래서 각 고객에게 절대 겹치지 않는 번호를 부여한다.</p>
<pre><code class="language-text">customer_id = 1 -&gt; 김지훈
customer_id = 2 -&gt; 이서연</code></pre>
<p>이처럼 테이블의 각 행을 유일하게 식별하는 값을 <strong>기본 키(Primary Key, PK)</strong>라고 한다.</p>
<p>기본 키에는 보통 다음 특징이 있다.</p>
<ul>
<li>테이블 안에서 값이 중복되지 않는다.</li>
<li>값이 비어 있을 수 없다.</li>
<li>다른 테이블이 특정 행을 정확하게 가리킬 때 기준으로 사용한다.</li>
</ul>
<p>이메일처럼 바뀔 수 있는 업무 정보보다 <code>customer_id</code> 같은 별도의 일련번호를 기본 키로 사용하면 관리가 안정적이다.</p>
<h3 id="03-외래-키는-테이블-사이의-연결고리다">0.3 외래 키는 테이블 사이의 연결고리다</h3>
<p>고객 정보와 주문 정보를 하나의 표에 모두 저장하면 고객의 이름과 이메일이 주문마다 반복된다. 이를 피하기 위해 고객과 주문을 서로 다른 테이블로 나눈다.</p>
<pre><code class="language-text">customers
+-------------+----------+
| customer_id | name     |
+-------------+----------+
| 1           | 김지훈   |
| 2           | 이서연   |
+-------------+----------+

orders
+----------+-------------+----------+
| order_id | customer_id | item     |
+----------+-------------+----------+
| 101      | 1           | 키보드   |
| 102      | 1           | 마우스   |
| 103      | 2           | 모니터   |
+----------+-------------+----------+</code></pre>
<p><code>orders.customer_id</code>는 <code>customers.customer_id</code>를 참조한다. 이렇게 다른 테이블의 기본 키를 가리키는 값을 <strong>외래 키(Foreign Key, FK)</strong>라고 한다.</p>
<p>외래 키 덕분에 고객 정보는 한 번만 저장하면서도 주문이 어느 고객의 것인지 알 수 있다.</p>
<h3 id="04-관계는-11-1n-nm으로-생각한다">0.4 관계는 1:1, 1:N, N:M으로 생각한다</h3>
<p>테이블 사이의 관계는 크게 세 가지로 구분할 수 있다.</p>
<table>
<thead>
<tr>
<th>관계</th>
<th>의미</th>
<th>예시</th>
</tr>
</thead>
<tbody><tr>
<td>1:1</td>
<td>한 행이 다른 테이블의 한 행과 연결</td>
<td>사용자와 사용자 상세 정보</td>
</tr>
<tr>
<td>1:N</td>
<td>한 행이 다른 테이블의 여러 행과 연결</td>
<td>고객 한 명과 여러 주문</td>
</tr>
<tr>
<td>N:M</td>
<td>양쪽의 여러 행이 서로 연결</td>
<td>여러 학생과 여러 강좌</td>
</tr>
</tbody></table>
<p>N:M 관계는 관계형 데이터베이스에서 보통 중간 테이블로 풀어서 표현한다.</p>
<pre><code class="language-text">students 1:N enrollments N:1 courses</code></pre>
<p>학생과 강좌 사이에 <code>enrollments</code>라는 수강 신청 테이블을 두면 &quot;어떤 학생이 어떤 강좌를 수강하는가&quot;를 표현할 수 있다.</p>
<h3 id="05-정규화는-중복을-줄이는-정리-방법이다">0.5 정규화는 중복을 줄이는 정리 방법이다</h3>
<p>주문 테이블에 고객 이름과 이메일을 함께 저장하면 같은 고객이 주문할 때마다 정보가 반복된다.</p>
<pre><code class="language-text">정규화 전
주문 101 | 김지훈 | jihoon@example.com
주문 102 | 김지훈 | jihoon@example.com</code></pre>
<p>이메일이 바뀌면 두 주문 행을 모두 수정해야 하고, 하나라도 놓치면 데이터가 서로 달라진다.</p>
<p>이를 다음처럼 분리할 수 있다.</p>
<pre><code class="language-text">customers: 고객 정보는 한 번만 저장
orders: customer_id로 고객을 참조</code></pre>
<p>이처럼 데이터의 중복을 줄이고 일관성을 지키기 위해 테이블을 나누는 설계 과정을 <strong>정규화(Normalization)</strong>라고 한다.</p>
<p>정규화의 목적은 무조건 테이블을 많이 만드는 것이 아니다. <strong>같은 사실을 여러 곳에서 따로 관리하지 않도록 데이터의 책임을 분리하는 것</strong>이 핵심이다.</p>
<h3 id="06-erd는-데이터베이스를-만들기-전-그리는-설계도다">0.6 ERD는 데이터베이스를 만들기 전 그리는 설계도다</h3>
<p><strong>ERD(Entity-Relationship Diagram)</strong>는 테이블이 될 대상과 속성, 테이블 사이의 관계를 그림으로 표현한 설계도다.</p>
<p>집을 짓기 전에 평면도를 그리듯, 데이터베이스도 코드를 작성하기 전에 구조를 먼저 설계하면 실수를 줄일 수 있다. ERD는 개발자뿐 아니라 기획자와 데이터 분석가가 같은 데이터 구조를 보며 이야기할 수 있게 해주는 공용 언어이기도 하다.</p>
<p>ERD를 볼 때는 다음 순서로 질문해 보자.</p>
<ol>
<li>이 테이블은 현실 세계의 무엇을 나타내는가?</li>
<li>한 행을 구별하는 기본 키는 무엇인가?</li>
<li>어떤 외래 키가 어느 테이블을 참조하는가?</li>
<li>관계가 1:1, 1:N, N:M 중 무엇인가?</li>
<li>실제 업무 규칙과 관계의 개수가 일치하는가?</li>
</ol>
<h3 id="07-sql은-관계형-데이터베이스와-대화하는-언어다">0.7 SQL은 관계형 데이터베이스와 대화하는 언어다</h3>
<p><strong>SQL(Structured Query Language)</strong>은 관계형 데이터베이스의 구조를 정의하고 데이터를 조회하거나 변경하는 표준 언어다.</p>
<p>SQL 명령은 목적에 따라 다음과 같이 구분한다.</p>
<table>
<thead>
<tr>
<th>분류</th>
<th>역할</th>
<th>대표 명령</th>
</tr>
</thead>
<tbody><tr>
<td>DDL</td>
<td>테이블과 같은 구조 정의</td>
<td><code>CREATE</code>, <code>ALTER</code>, <code>DROP</code></td>
</tr>
<tr>
<td>DML</td>
<td>데이터 조회와 변경</td>
<td><code>SELECT</code>, <code>INSERT</code>, <code>UPDATE</code>, <code>DELETE</code></td>
</tr>
<tr>
<td>DCL</td>
<td>사용자 권한 관리</td>
<td><code>GRANT</code>, <code>REVOKE</code></td>
</tr>
<tr>
<td>TCL</td>
<td>트랜잭션 확정과 취소</td>
<td><code>COMMIT</code>, <code>ROLLBACK</code></td>
</tr>
</tbody></table>
<p>처음에는 <code>SELECT</code>, <code>FROM</code>, <code>WHERE</code>, <code>JOIN</code>의 역할부터 익히면 된다.</p>
<pre><code class="language-sql">SELECT name, email
FROM customers
WHERE joined_at &gt;= '2025-01-01';</code></pre>
<ul>
<li><code>SELECT</code>: 어떤 열을 보여 줄지 지정한다.</li>
<li><code>FROM</code>: 어느 테이블에서 가져올지 지정한다.</li>
<li><code>WHERE</code>: 어떤 조건의 행만 남길지 지정한다.</li>
</ul>
<p>고객과 주문처럼 서로 다른 테이블의 정보를 함께 보려면 <code>JOIN</code>을 사용한다.</p>
<pre><code class="language-sql">SELECT
    c.name,
    o.item
FROM customers AS c
JOIN orders AS o
    ON o.customer_id = c.customer_id;</code></pre>
<p><code>JOIN</code>은 마법처럼 아무 데이터나 합치는 기능이 아니다. <code>customers.customer_id</code>와 <code>orders.customer_id</code>처럼 <strong>의미가 같은 키를 기준으로 관련된 행을 연결하는 연산</strong>이다.</p>
<hr />
<h2 id="최신-트렌드-데이터베이스-기술은-지금-어디로-가고-있을까">최신 트렌드: 데이터베이스 기술은 지금 어디로 가고 있을까?</h2>
<blockquote>
<p>이 절의 제품 이름과 수치를 외울 필요는 없다. 사례에서 반복되는 설계 원칙을 발견하는 것이 더 중요하다. 기초 개념을 먼저 공부하고 다시 읽어도 좋다.</p>
</blockquote>
<p>오늘날 데이터베이스의 변화는 &quot;기존 기술이 사라지고 새로운 기술이 대신한다&quot;는 단순한 흐름이 아니다. 검증된 관계형 데이터베이스를 계속 활용하면서, 특정 문제에는 NoSQL이나 벡터 검색 같은 기술을 조합하는 방향으로 발전하고 있다.</p>
<h3 id="사례-1-openai는-왜-postgresql을-바로-버리지-않았을까">사례 1. OpenAI는 왜 PostgreSQL을 바로 버리지 않았을까?</h3>
<p>OpenAI는 2026년 1월 공개한 엔지니어링 글에서 ChatGPT와 API의 핵심 시스템이 단일 프라이머리 Azure PostgreSQL과 전 세계에 배치된 약 50개의 읽기 복제본을 기반으로 수백만 QPS와 8억 사용자 규모를 지원한다고 설명했다. 지난 1년간 부하가 10배 이상 증가했지만, 쓰기를 담당하는 PostgreSQL 프라이머리는 샤딩하지 않은 구조를 유지했다. <a href="https://openai.com/index/scaling-postgresql/">OpenAI 공식 엔지니어링 글</a></p>
<h4 id="먼저-알아둘-구조">먼저 알아둘 구조</h4>
<pre><code class="language-text">애플리케이션
     ├── 쓰기 요청 ──&gt; Primary PostgreSQL 1대
     └── 읽기 요청 ──&gt; 지역별 Read Replica 약 50대</code></pre>
<ul>
<li><strong>프라이머리(Primary)</strong>: <code>INSERT</code>, <code>UPDATE</code>, <code>DELETE</code> 같은 쓰기를 최종 처리하는 원본 서버</li>
<li><strong>읽기 복제본(Read Replica)</strong>: 프라이머리의 데이터를 복제해 조회 요청을 나누어 처리하는 서버</li>
<li><strong>QPS(Queries Per Second)</strong>: 데이터베이스가 1초 동안 처리하는 쿼리 수</li>
</ul>
<p>&quot;사용자가 많다면 무조건 처음부터 데이터베이스를 잘게 샤딩해야 하지 않을까?&quot;라고 생각할 수 있다. 하지만 기존 시스템을 샤딩하려면 수많은 API와 쿼리, 트랜잭션을 다시 설계해야 한다. 읽기 요청이 많은 서비스라면 복제본과 캐시를 활용해 기존 관계형 DB를 확장하는 편이 더 현실적일 수 있다.</p>
<p>OpenAI가 사용한 주요 대응 전략은 다음과 같다.</p>
<table>
<thead>
<tr>
<th>문제</th>
<th>대응 방식</th>
<th>배울 수 있는 개념</th>
</tr>
</thead>
<tbody><tr>
<td>프라이머리의 쓰기 한계</td>
<td>분할하기 쉬운 쓰기 중심 워크로드를 Azure Cosmos DB로 이전</td>
<td>폴리글랏 퍼시스턴스</td>
</tr>
<tr>
<td>많은 읽기 요청</td>
<td>지역별 읽기 복제본과 캐시로 부하 분산</td>
<td>복제, 캐시</td>
</tr>
<tr>
<td>비효율적인 쿼리</td>

<p>여기서 핵심은 &quot;PostgreSQL 한 대가 모든 일을 했다&quot;가 아니다. 실제로는 읽기 복제본, 캐시, 연결 풀, 쿼리 최적화, 요청 제한, NoSQL 이전이 함께 사용되었다.</p>
<h4 id="이-사례가-주는-교훈">이 사례가 주는 교훈</h4>
<ol>
<li>검증된 기술은 충분한 최적화와 운영 정책을 통해 예상보다 크게 확장될 수 있다.</li>
<li>모든 데이터를 하나의 DB에 넣기보다 워크로드의 성격에 따라 역할을 나눌 수 있다.</li>
<li>새로운 분산 DB로 이전하는 비용과 기존 시스템을 개선하는 비용을 함께 비교해야 한다.</li>
<li>데이터베이스 성능은 제품 선택뿐 아니라 쿼리, 연결, 캐시, 장애 대응 정책에 의해 결정된다.</li>
</ol>
<h3 id="사례-2-벡터-검색과-그래프-검색이-하나의-db에서-만난다">사례 2. 벡터 검색과 그래프 검색이 하나의 DB에서 만난다</h3>
<p>생성형 AI와 RAG가 확산되면서 <strong>벡터 검색(Vector Search)</strong>이 중요한 데이터베이스 기능으로 자리 잡고 있다.</p>
<h4 id="벡터와-임베딩이란">벡터와 임베딩이란?</h4>
<p>컴퓨터는 문장의 의미를 사람처럼 바로 이해하지 못한다. 임베딩 모델은 문장, 이미지, 상품 같은 데이터를 여러 개의 숫자로 이루어진 벡터로 변환한다.</p>
<pre><code class="language-text">&quot;데이터베이스 입문서&quot; -&gt; [0.12, -0.31, 0.87, ...]
&quot;초보자를 위한 SQL 책&quot; -&gt; [0.10, -0.28, 0.83, ...]</code></pre>
<p>의미가 비슷한 데이터는 벡터 공간에서도 가까운 위치에 놓이도록 학습된다. 따라서 키워드가 정확히 같지 않아도 의미가 비슷한 문서나 상품을 찾을 수 있다.</p>
<h4 id="그래프-검색은-관계를-따라간다">그래프 검색은 관계를 따라간다</h4>
<p>그래프 데이터베이스는 데이터를 노드와 관계로 표현한다.</p>
<pre><code class="language-text">사용자 -&gt; 구매함 -&gt; 상품
상품 -&gt; 속함 -&gt; 카테고리
사용자 -&gt; 팔로우함 -&gt; 다른 사용자</code></pre>
<p>벡터 검색이 &quot;무엇이 의미상 비슷한가?&quot;를 찾는다면 그래프 검색은 &quot;무엇과 어떤 관계로 연결되어 있는가?&quot;를 탐색한다.</p>
<p>TigerVector 연구는 TigerGraph의 정점에 임베딩 타입을 추가하고, 벡터 검색 결과와 그래프 관계 탐색을 하나의 쿼리 흐름에서 결합했다. 이 시스템은 MPP 인덱스 구조와 확장된 GSQL을 사용하며 2024년 12월 TigerGraph 4.2에 반영되었다. <a href="https://arxiv.org/abs/2501.11216">TigerVector 논문</a></p>
<pre><code class="language-text">질문: &quot;이 사용자와 관심사가 비슷하면서 친구의 친구인 사람은?&quot;

1. 벡터 검색으로 관심사가 비슷한 사용자 후보 찾기
2. 그래프 관계로 친구의 친구 조건 확인하기
3. 두 조건을 만족하는 결과만 반환하기</code></pre>
<p>과거에는 벡터 DB와 그래프 DB를 별도로 운영하고 애플리케이션이 결과를 합쳐야 했다. 두 기능을 한 엔진에서 결합하면 데이터 이동과 애플리케이션 로직을 줄일 가능성이 있다.</p>
<p>이 사례는 벡터 검색이 반드시 별도의 전문 DB에만 존재하는 것이 아니라 관계형 DB나 그래프 DB의 기능으로 흡수되는 흐름도 있다는 점을 보여 준다. 실제로 어떤 방식이 유리한지는 데이터 규모, 검색 정확도, 지연 시간, 기존 시스템과의 통합 비용을 함께 고려해야 한다.</p>
<h4 id="mpp는-많은-작업자가-데이터를-나누어-처리하는-방식이다">MPP는 많은 작업자가 데이터를 나누어 처리하는 방식이다</h4>
<p>TigerVector에 등장하는 <strong>MPP(Massively Parallel Processing)</strong>는 여러 독립된 컴퓨팅 노드가 데이터를 나누어 동시에 처리하는 구조다.</p>
<pre><code class="language-text">큰 데이터 검색 작업
    ├── 노드 A: 파티션 A 검색
    ├── 노드 B: 파티션 B 검색
    ├── 노드 C: 파티션 C 검색
    └── 결과를 모아 최종 응답</code></pre>
<p>각 노드는 자신의 메모리와 디스크를 사용한다. 데이터가 늘면 노드를 추가해 처리 능력을 확장할 수 있어 대규모 분석 시스템과 데이터 웨어하우스에서 자주 사용된다.</p>
<p>하지만 노드를 추가한다고 성능이 정확히 같은 비율로 증가하는 것은 아니다. 노드 사이에서 데이터를 주고받고 결과를 합치는 비용도 함께 늘어나기 때문이다.</p>
<h3 id="사례-3-코어와-서버를-늘렸는데-왜-더-느려질까">사례 3. 코어와 서버를 늘렸는데 왜 더 느려질까?</h3>
<p>2026년 발표된 연구는 Qdrant, Milvus, Weaviate를 두 대의 슈퍼컴퓨터에서 최대 64개 노드, 256개 워커까지 확장해 평가했다. 일부 조건에서는 코어를 더 투입했을 때 쿼리 처리량이 최대 30.67% 감소했고, 워커를 16개에서 256개로 16배 늘려도 성능 향상은 5.46배에 그쳤다. <a href="https://arxiv.org/abs/2606.08950">When More Cores Hurts 논문</a></p>
<p>이 결과가 &quot;벡터 DB는 느리다&quot;는 뜻은 아니다. 연구가 보여 주는 핵심은 <strong>클라우드 환경에 맞춰 설계된 소프트웨어를 HPC 환경으로 옮기면 내부 동시성 제어, 네트워크, 스토리지 방식이 맞지 않아 병목이 생길 수 있다</strong>는 점이다.</p>
<h4 id="왜-자원을-추가해도-선형으로-빨라지지-않을까">왜 자원을 추가해도 선형으로 빨라지지 않을까?</h4>
<ul>
<li>작업을 여러 노드에 분배하고 결과를 모으는 비용이 발생한다.</li>
<li>노드가 공유하는 네트워크나 스토리지가 새로운 병목이 될 수 있다.</li>
<li>여러 워커가 같은 자원이나 잠금을 두고 경쟁할 수 있다.</li>
<li>데이터 복제와 인덱스 유지 비용이 증가할 수 있다.</li>
<li>소프트웨어가 처음 설계된 환경과 실제 실행 환경이 다를 수 있다.</li>
</ul>
<p>자동차 차선을 2개에서 4개로 늘려도 합류 구간과 출구가 그대로라면 전체 통행 시간이 절반이 되지 않는 것과 비슷하다.</p>
<h4 id="이-사례가-주는-교훈-1">이 사례가 주는 교훈</h4>
<ol>
<li>CPU, 메모리, 서버 수가 많다고 항상 빠른 것은 아니다.</li>
<li>제품의 공개 벤치마크가 내 데이터와 쿼리에서도 재현되는지 확인해야 한다.</li>
<li>평균 응답 시간뿐 아니라 p95, p99 지연 시간과 처리량을 함께 측정해야 한다.</li>
<li>실제 운영 환경과 비슷한 조건에서 부하 테스트해야 한다.</li>
<li>최신 기술이라는 이유만으로 도입하지 말고 해결할 문제가 명확한지 먼저 확인해야 한다.</li>
</ol>

<h2 id="들어가며">들어가며</h2>
<p>간단한 프로그램을 처음 만들 때는 데이터를 텍스트 파일이나 엑셀 파일에 저장해도 큰 문제가 없어 보인다.</p>
<p>예를 들어 작은 쇼핑몰의 주문 내역을 다음과 같은 CSV 파일로 관리한다고 생각해 보자.</p>
<pre><code class="language-csv">order_id,customer_name,customer_phone,product_name,quantity,status
1001,김코덱스,010-1111-2222,키보드,1,결제완료
1002,이데이터,010-3333-4444,마우스,2,배송중</code></pre>
<p>데이터가 몇십 건이고 한 사람만 사용한다면 충분할 수 있다. 하지만 이용자가 늘고 주문, 결제, 배송 프로그램이 동시에 같은 데이터를 사용하기 시작하면 파일만으로 데이터를 안전하게 관리하기가 어려워진다.</p>
<p>이 문제를 해결하기 위해 등장한 것이 <strong>데이터베이스(Database)</strong>와 <strong>DBMS(Database Management System)</strong>다.</p>
<hr />
<h2 id="1-기존-파일-관리에는-어떤-한계가-있을까">1. 기존 파일 관리에는 어떤 한계가 있을까?</h2>
<p>파일은 데이터를 저장하는 가장 단순한 방법이다. 하지만 여러 사람과 프로그램이 함께 사용하는 서비스에서는 다음과 같은 문제가 발생한다.</p>
<h3 id="11-데이터가-중복된다">1.1 데이터가 중복된다</h3>
<p>주문팀, 배송팀, 고객센터가 각각 별도의 파일을 사용한다고 가정해 보자.</p>
<pre><code class="language-text">주문팀_고객목록.xlsx
배송팀_배송주소.xlsx
고객센터_회원정보.xlsx</code></pre>
<p>세 파일에 고객 이름, 전화번호, 주소가 반복해서 저장된다. 저장 공간의 낭비보다 더 큰 문제는 <strong>같은 정보를 여러 곳에서 따로 수정해야 한다는 것</strong>이다.</p>
<h3 id="12-데이터가-서로-달라질-수-있다">1.2 데이터가 서로 달라질 수 있다</h3>
<p>고객이 주소를 변경했는데 주문팀 파일만 수정하고 배송팀 파일은 수정하지 않았다면 어떻게 될까?</p>
<pre><code class="language-text">주문팀 파일: 서울특별시 강남구
배송팀 파일: 부산광역시 해운대구</code></pre>
<p>같은 고객의 주소가 파일마다 달라지는 <strong>데이터 불일치</strong>가 발생한다. 어떤 값이 최신 정보인지 판단하기도 어렵다.</p>
<h3 id="13-여러-사람이-동시에-수정하기-어렵다">1.3 여러 사람이 동시에 수정하기 어렵다</h3>
<p>두 직원이 같은 파일을 동시에 열어 주문 상태를 변경하면 한 사람의 작업이 다른 사람의 작업을 덮어쓸 수 있다.</p>
<p>예를 들어 다음 두 작업이 거의 동시에 발생할 수 있다.</p>
<ol>
<li>배송 담당자가 주문 상태를 <code>배송중</code>으로 변경한다.</li>
<li>고객센터 직원이 같은 주문을 <code>취소</code>로 변경한다.</li>
</ol>
<p>단순한 파일은 두 작업의 순서와 충돌을 안전하게 조정하기 어렵다. 반면 DBMS는 <strong>트랜잭션과 동시성 제어</strong>를 통해 여러 사용자의 작업을 조정한다.</p>
<h3 id="14-데이터-사이의-관계를-표현하기-어렵다">1.4 데이터 사이의 관계를 표현하기 어렵다</h3>
<p>쇼핑몰에는 다음과 같은 데이터가 서로 연결되어 있다.</p>
<pre><code class="language-text">고객 1명 -&gt; 여러 주문
주문 1건 -&gt; 여러 주문 상품
상품 1개 -&gt; 하나의 카테고리</code></pre>
<p>파일을 나누면 각 파일을 어떤 기준으로 연결할지 프로그램이 직접 관리해야 한다. 데이터가 많아질수록 특정 고객의 주문과 주문 상품을 찾아 연결하는 과정이 복잡해진다.</p>
<h3 id="15-규칙을-일관되게-적용하기-어렵다">1.5 규칙을 일관되게 적용하기 어렵다</h3>
<p>다음과 같은 서비스 규칙이 있다고 생각해 보자.</p>
<ul>
<li>주문 번호는 중복될 수 없다.</li>
<li>존재하지 않는 고객의 주문은 등록할 수 없다.</li>
<li>상품 가격은 0원보다 작을 수 없다.</li>
<li>필수 정보인 고객 이름은 비어 있을 수 없다.</li>
</ul>
<p>파일에서는 모든 프로그램이 이 규칙을 빠짐없이 구현해야 한다. 한 프로그램이라도 검사를 누락하면 잘못된 데이터가 저장된다. DBMS는 기본 키, 외래 키, <code>NOT NULL</code>, <code>CHECK</code> 같은 <strong>제약 조건</strong>으로 데이터 규칙을 중앙에서 관리할 수 있다.</p>
<h3 id="16-검색-보안-백업이-점점-어려워진다">1.6 검색, 보안, 백업이 점점 어려워진다</h3>

<h2 id="2-데이터베이스란">2. 데이터베이스란?</h2>
<p><strong>데이터베이스</strong>는 여러 사람과 프로그램이 함께 접근할 수 있도록 데이터를 구조화하여 저장하고 관리하는 데이터의 모음이다.</p>
<p>여기서 중요한 점은 데이터베이스가 값만 저장하지 않는다는 것이다. 다음 요소도 함께 관리한다.</p>
<ul>
<li><strong>구조</strong>: 어떤 데이터 항목을 저장할 것인가?</li>
<li><strong>관계</strong>: 고객과 주문은 어떻게 연결되는가?</li>
<li><strong>규칙</strong>: 어떤 값이 필수이며, 어떤 값은 중복될 수 없는가?</li>
<li><strong>권한</strong>: 누가 어떤 데이터를 조회하거나 수정할 수 있는가?</li>
</ul>
<p>쇼핑몰 데이터베이스라면 고객, 상품, 주문 데이터를 다음처럼 나누어 관리할 수 있다.</p>
<pre><code class="language-text">customers
- customer_id
- name
- email

products
- product_id
- name
- price

orders
- order_id
- customer_id
- ordered_at
- status</code></pre>
<p><code>orders.customer_id</code>를 이용하면 주문이 어느 고객의 것인지 연결할 수 있다. 데이터가 여러 테이블로 나뉘어 있어도 관계를 통해 필요한 정보를 다시 조합할 수 있다.</p>

<h2 id="3-dbms는-무슨-일을-할까">3. DBMS는 무슨 일을 할까?</h2>
<p>DBMS는 단순히 데이터를 저장하는 프로그램이 아니다. 애플리케이션과 실제 데이터 사이에서 데이터를 안전하고 효율적으로 관리한다.</p>
<h3 id="31-저장하고-구조화한다">3.1 저장하고 구조화한다</h3>
<p>DBMS는 테이블, 문서, 키-값 등 DBMS가 지원하는 구조에 따라 데이터를 저장한다. 관계형 DBMS에서는 데이터 타입과 제약 조건도 함께 정의할 수 있다.</p>
<pre><code class="language-sql">CREATE TABLE customers (
    customer_id BIGINT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) UNIQUE
);</code></pre>
<p>이 테이블에는 다음 규칙이 적용된다.</p>
<ul>
<li><code>customer_id</code>는 고객을 구별하는 값이며 중복될 수 없다.</li>
<li><code>name</code>은 반드시 입력해야 한다.</li>
<li><code>email</code>은 같은 값이 두 번 저장될 수 없다.</li>
</ul>
<h3 id="32-데이터를-검색하고-조회한다">3.2 데이터를 검색하고 조회한다</h3>
<p>관계형 DBMS에서는 SQL을 이용해 필요한 데이터만 조회할 수 있다.</p>
<pre><code class="language-sql">SELECT order_id, status
FROM orders
WHERE customer_id = 101
ORDER BY ordered_at DESC;</code></pre>
<p>이 쿼리는 전체 주문 중 <code>customer_id</code>가 101인 고객의 주문만 골라 최신순으로 보여 준다.</p>
<p>인덱스가 있다면 책의 색인처럼 원하는 데이터를 빠르게 찾을 수 있다.</p>
<h3 id="33-여러-사용자의-동시-작업을-제어한다">3.3 여러 사용자의 동시 작업을 제어한다</h3>
<p>한정판 상품의 재고가 1개 남았는데 두 사용자가 동시에 구매 버튼을 눌렀다고 가정해 보자. DBMS가 동시 작업을 제어하지 않으면 두 주문이 모두 성공해 재고가 음수가 될 수 있다.</p>
<p>DBMS는 잠금, 데이터 버전 관리, 트랜잭션 격리 같은 방법을 사용해 동시에 실행되는 작업의 충돌을 줄이고 데이터의 일관성을 지킨다.</p>
<h3 id="34-트랜잭션으로-작업-단위를-보호한다">3.4 트랜잭션으로 작업 단위를 보호한다</h3>
<p><strong>트랜잭션(Transaction)</strong>은 하나의 논리적인 작업 단위다. 은행 송금은 대표적인 예다.</p>
<pre><code class="language-text">1. A 계좌에서 10,000원을 차감한다.
2. B 계좌에 10,000원을 추가한다.</code></pre>
<p>두 작업 중 하나만 실행되면 돈이 사라지거나 새로 생긴다. 따라서 둘 다 성공하거나 둘 다 취소되어야 한다.</p>
<pre><code class="language-sql">BEGIN;

UPDATE accounts
SET balance = balance - 10000
WHERE account_id = 'A';

UPDATE accounts
SET balance = balance + 10000
WHERE account_id = 'B';

COMMIT;</code></pre>
<p>관계형 DB에서 안전한 트랜잭션을 설명할 때는 보통 <strong>ACID</strong>라는 네 가지 성질을 사용한다.</p>
<table>
<thead>
<tr>
<th>성질</th>
<th>의미</th>
<th>송금 예시</th>
</tr>
</thead>
<tbody><tr>
<td>Atomicity, 원자성</td>
<td>작업 전체가 성공하거나 전체가 취소됨</td>
<td>출금과 입금이 함께 처리됨</td>
</tr>
<tr>
<td>Consistency, 일관성</td>
<td>작업 전후에 데이터 규칙을 지킴</td>
<td>잔액 규칙이 깨지지 않음</td>
</tr>
<tr>
<td>Isolation, 격리성</td>
<td>동시에 실행되는 작업이 함부로 간섭하지 않음</td>
<td>다른 송금 작업과 충돌을 제어함</td>
</tr>
<tr>
<td>Durability, 지속성</td>
<td>완료된 결과가 장애 후에도 유지됨</td>
<td>송금 완료 결과가 사라지지 않음</td>
</tr>
</tbody></table>
<h3 id="35-wal은-데이터-파일보다-로그를-먼저-기록한다">3.5 WAL은 데이터 파일보다 로그를 먼저 기록한다</h3>
<p>DBMS가 데이터를 변경할 때마다 큰 데이터 파일을 즉시 안전하게 디스크에 반영하면 쓰기 비용이 커질 수 있다. 많은 관계형 DBMS는 실제 데이터 페이지보다 변경 로그를 먼저 기록하는 <strong>WAL(Write-Ahead Logging)</strong> 방식을 사용한다.</p>
<pre><code class="language-text">1. 사용자가 UPDATE를 요청한다.
2. DBMS가 변경 내용을 WAL에 먼저 기록한다.
3. 커밋에 필요한 로그가 안전하게 기록되면 성공을 응답한다.
4. 실제 데이터 페이지는 이후 체크포인트 과정에서 반영될 수 있다.</code></pre>
<p>은행 장부에 비유하면 금고 속 원장을 매번 다시 만들기 전에 &quot;어떤 거래를 했는지&quot; 거래 기록부터 안전하게 남기는 방식이다.</p>
<pre><code class="language-sql">BEGIN;

UPDATE accounts
SET balance = balance - 10000
WHERE account_id = 'A';

UPDATE accounts
SET balance = balance + 10000
WHERE account_id = 'B';

COMMIT;</code></pre>
<p>서버가 갑자기 중단되면 DBMS는 WAL을 이용해 필요한 변경을 다시 적용하고, 완료되지 않은 트랜잭션이 최종 결과로 보이지 않도록 복구한다. 세부 복구 방식은 DBMS마다 다르지만 핵심 원칙은 <strong>데이터 파일보다 복구 가능한 기록을 먼저 안전하게 남긴다</strong>는 것이다.</p>
<p>WAL의 주요 목적은 다음과 같다.</p>
<ul>
<li>커밋된 변경의 지속성 보장</li>
<li>장애 발생 후 데이터베이스 복구</li>
<li>순차적인 로그 쓰기를 통한 쓰기 효율 개선</li>
<li>읽기 복제본에 변경 내용을 전달하는 복제 기반 제공</li>
</ul>
<h3 id="36-consensus는-여러-노드가-같은-순서에-합의하는-방법이다">3.6 Consensus는 여러 노드가 같은 순서에 합의하는 방법이다</h3>
<p>WAL이 한 DBMS 안에서 장애 복구를 위한 기록이라면, <strong>Consensus(합의 알고리즘)</strong>는 여러 노드가 어떤 변경을 어떤 순서로 확정할지 합의하는 문제를 다룬다.</p>
<pre><code class="language-text">클라이언트 요청
      ↓
Leader가 로그 항목 생성
      ↓
Follower 노드에 전달
      ↓
필요한 수의 노드가 동의
      ↓
Commit 확정</code></pre>
<p>분산 시스템에서는 네트워크 지연이나 일부 노드의 장애로 각 노드가 서로 다른 상태를 볼 수 있다. Raft나 Paxos 계열의 합의 알고리즘은 어떤 로그가 최종적으로 선택되었는지 노드들이 합의하도록 돕는다.</p>

<thead>
<tr>
<th>비교</th>
<th>WAL</th>
<th>Consensus</th>
</tr>
</thead>
<tbody><tr>
<td>주요 범위</td>
<td>하나의 DBMS와 저장 엔진</td>
<td>여러 분산 노드</td>
</tr>
<tr>
<td>주요 목적</td>
<td>장애 복구와 트랜잭션 지속성</td>
<td>노드 사이의 동일한 변경 순서 합의</td>
</tr>
<tr>
<td>핵심 동작</td>
<td>변경 로그를 데이터보다 먼저 기록</td>
<td>여러 노드가 로그 항목에 동의</td>
</tr>
<tr>
<td>함께 사용 가능?</td>
<td>가능</td>
<td>분산 DB는 합의할 로그 자체를 WAL 형태로 기록할 수 있음</td>
</tr>
</tbody></table>
<p>합의는 일관성과 고가용성을 높이지만 공짜가 아니다. 여러 노드의 응답을 기다리므로 네트워크가 느리거나 노드가 멀리 떨어질수록 쓰기 지연 시간이 증가할 수 있다.</p>
<h3 id="37-격리-수준은-동시성과-일관성-사이의-선택이다">3.7 격리 수준은 동시성과 일관성 사이의 선택이다</h3>
<p>여러 트랜잭션이 동시에 실행될 때 모든 작업을 완전히 한 줄로 세우면 안전하지만 성능이 낮아진다. 반대로 서로의 작업을 너무 자유롭게 보게 하면 잘못된 결과를 읽을 수 있다.</p>
<p><strong>트랜잭션 격리 수준(Isolation Level)</strong>은 동시에 실행되는 트랜잭션이 서로의 변경을 어느 정도 볼 수 있는지 정하는 기준이다.</p>
<p>먼저 대표적인 이상 현상을 알아보자.</p>
<table>
<thead>
<tr>
<th>이상 현상</th>
<th>설명</th>
<th>예시</th>
</tr>
</thead>
<tbody><tr>
<td>Dirty Read</td>
<td>아직 커밋되지 않은 값을 읽음</td>
<td>곧 취소될 임시 잔액을 다른 거래가 사용</td>
</tr>
<tr>
<td>Non-Repeatable Read</td>
<td>같은 행을 두 번 읽었는데 값이 달라짐</td>
<td>첫 조회 후 다른 트랜잭션이 해당 행 수정</td>
</tr>
<tr>
<td>Phantom Read</td>
<td>같은 조건으로 다시 조회했는데 행의 수가 달라짐</td>
<td>다른 트랜잭션이 조건에 맞는 새 행 추가</td>
</tr>
</tbody></table>

</tr>

</tr>

<td>방지</td>
<td>허용 가능</td>

<p>팬텀 리드의 예시는 다음과 같다.</p>
<pre><code class="language-text">트랜잭션 A: 10만 원 이상 주문 수 조회 -&gt; 5건
트랜잭션 B: 15만 원 주문 추가 후 COMMIT
트랜잭션 A: 같은 조건으로 다시 조회 -&gt; 6건</code></pre>
<p>두 번째 조회에서 처음에는 없던 행이 나타났으므로 팬텀이라고 부른다.</p>
<p>실제 DBMS는 잠금, MVCC, 스냅샷 격리 같은 서로 다른 방식으로 격리 수준을 구현한다. 따라서 같은 <code>Repeatable Read</code>라는 이름이라도 팬텀 처리와 충돌 동작이 제품마다 다를 수 있다. 기본값만 믿지 말고 사용하는 DBMS의 문서와 실제 테스트를 확인해야 한다.</p>
<p>격리 수준을 높이면 이상 현상은 줄어들지만 다음 비용이 생길 수 있다.</p>
<ul>
<li>잠금 대기 증가</li>
<li>트랜잭션 충돌과 재시도 증가</li>
<li>동시 처리량 감소</li>
<li>긴 트랜잭션으로 인한 버전 정리 부담 증가</li>
</ul>
<p>중요한 것은 가장 높은 수준을 무조건 선택하는 것이 아니라 주문, 결제, 통계 조회 등 업무의 정확성 요구와 충돌 가능성에 맞는 수준을 선택하는 것이다.</p>
<h3 id="38-보안과-권한을-관리한다">3.8 보안과 권한을 관리한다</h3>
<p>모든 사용자가 모든 데이터를 수정할 수 있어서는 안 된다.</p>
<pre><code class="language-text">고객센터: 고객과 주문 정보 조회
배송 담당자: 배송 주소 조회와 배송 상태 수정
데이터 분석가: 개인정보를 제외한 매출 데이터 조회
관리자: 사용자와 권한 관리</code></pre>
<p>DBMS는 사용자와 역할을 구분하고 <code>SELECT</code>, <code>INSERT</code>, <code>UPDATE</code>, <code>DELETE</code> 같은 작업별 권한을 부여할 수 있다.</p>
<h3 id="39-백업하고-장애에서-복구한다">3.9 백업하고 장애에서 복구한다</h3>
<p>서버 고장, 프로그램 오류, 사용자의 실수로 데이터가 손상될 수 있다. DBMS는 전체 백업, 증분 백업, 트랜잭션 로그 등을 이용해 데이터를 복구할 수 있도록 돕는다.</p>
<blockquote>
<p>정리하면 DBMS는 데이터의 <strong>저장과 구조화</strong>, <strong>검색과 조회</strong>, <strong>동시성 제어</strong>, <strong>규칙과 트랜잭션</strong>, <strong>보안</strong>, <strong>백업과 복구</strong>를 담당한다.</p>
</blockquote>
<hr />
<h2 id="4-관계형-데이터베이스란">4. 관계형 데이터베이스란?</h2>
<p><strong>관계형 데이터베이스(Relational Database)</strong>는 데이터를 행과 열로 구성된 테이블에 저장하고, 키를 이용해 테이블 사이의 관계를 표현한다. 관계형 데이터베이스를 관리하는 시스템을 <strong>RDBMS</strong>라고 한다.</p>
<p>대표적인 RDBMS는 다음과 같다.</p>
<ul>
<li>PostgreSQL</li>
<li>MySQL, MariaDB</li>
<li>Oracle Database</li>
<li>Microsoft SQL Server</li>
</ul>
<h3 id="관계형-데이터베이스의-핵심-용어">관계형 데이터베이스의 핵심 용어</h3>
<table>
<thead>
<tr>
<th>용어</th>
<th>설명</th>
<th>예시</th>
</tr>
</thead>
<tbody><tr>
<td>테이블(Table)</td>
<td>같은 종류의 데이터를 저장하는 표</td>
<td>고객 테이블</td>
</tr>
<tr>
<td>행(Row)</td>
<td>하나의 데이터 항목</td>
<td>고객 한 명</td>
</tr>
<tr>
<td>열(Column)</td>
<td>데이터의 속성</td>
<td>이름, 이메일</td>
</tr>
<tr>

<td>각 행을 고유하게 구별하는 값</td>
<td>고객 번호</td>
</tr>
<tr>

<td>다른 테이블의 기본 키를 참조하는 값</td>

<p>다음 두 테이블을 살펴보자.</p>
<pre><code class="language-text">customers
+-------------+----------+
| customer_id | name     |
+-------------+----------+
| 101         | 김코덱스 |
| 102         | 이데이터 |
+-------------+----------+

orders
+----------+-------------+--------+
| order_id | customer_id | amount |
+----------+-------------+--------+
| 1001     | 101         | 35000  |
| 1002     | 101         | 12000  |
| 1003     | 102         | 58000  |
+----------+-------------+--------+</code></pre>
<p><code>orders.customer_id</code>는 <code>customers.customer_id</code>를 참조한다. 이 관계를 이용하면 고객 이름과 주문 정보를 함께 조회할 수 있다.</p>
<pre><code class="language-sql">SELECT
    c.name,
    o.order_id,
    o.amount
FROM customers AS c
JOIN orders AS o
    ON o.customer_id = c.customer_id;</code></pre>
<p>결과는 다음과 같다.</p>
<pre><code class="language-text">김코덱스 | 1001 | 35000
김코덱스 | 1002 | 12000
이데이터 | 1003 | 58000</code></pre>
<h3 id="rdbms가-잘-맞는-경우">RDBMS가 잘 맞는 경우</h3>
<ul>
<li>주문, 결제, 재고처럼 정확성이 중요한 데이터</li>
<li>고객과 주문처럼 데이터 사이의 관계가 분명한 경우</li>
<li>복잡한 조건, 집계, 조인이 필요한 경우</li>
<li>구조와 업무 규칙이 비교적 명확한 경우</li>
<li>트랜잭션의 안전성이 중요한 경우</li>
</ul>
<h3 id="rdbms-사용-시-고려할-점">RDBMS 사용 시 고려할 점</h3>
<ul>
<li>구조를 변경할 때 스키마 변경 작업이 필요하다.</li>
<li>관계가 매우 복잡하면 조인 비용이 커질 수 있다.</li>
<li>서버를 여러 대로 나누는 수평 확장은 제품과 설계에 따라 복잡할 수 있다.</li>
</ul>

<h2 id="5-nosql-데이터베이스란">5. NoSQL 데이터베이스란?</h2>
<p><strong>NoSQL</strong>은 관계형 테이블 모델 이외의 다양한 방식으로 데이터를 저장하는 데이터베이스의 큰 범주다. 이름을 &quot;SQL을 절대 사용하지 않는다&quot;는 뜻으로 이해하기보다는 <strong>Not Only SQL</strong>, 즉 관계형 모델 외의 선택지도 제공한다고 이해하는 편이 좋다.</p>
<p>NoSQL은 데이터 구조가 자주 바뀌거나, 매우 많은 데이터를 여러 서버에 나누어 처리하거나, 특정 조회 패턴을 빠르게 처리해야 할 때 자주 사용된다.</p>

</thead>

<td>문서형</td>

<pre><code class="language-json">{
  &quot;productId&quot;: 501,
  &quot;name&quot;: &quot;기계식 키보드&quot;,
  &quot;price&quot;: 89000,
  &quot;options&quot;: {
    &quot;switch&quot;: &quot;brown&quot;,
    &quot;color&quot;: &quot;black&quot;
  },
  &quot;tags&quot;: [&quot;keyboard&quot;, &quot;office&quot;, &quot;gaming&quot;]
}</code></pre>
<p>상품마다 옵션의 종류가 달라도 하나의 문서 안에 유연하게 표현할 수 있다.</p>
<h3 id="nosql이-잘-맞는-경우">NoSQL이 잘 맞는 경우</h3>
<ul>
<li>데이터 구조가 자주 바뀌거나 항목마다 형태가 다른 경우</li>
<li>캐시, 사용자 세션처럼 키를 통한 빠른 조회가 중요한 경우</li>
<li>로그나 이벤트처럼 매우 많은 데이터가 계속 들어오는 경우</li>
<li>관계보다 특정 화면이나 API의 조회 형태가 더 중요한 경우</li>
<li>여러 서버로 데이터를 분산해 대규모 요청을 처리해야 하는 경우</li>
</ul>
<h3 id="nosql-사용-시-고려할-점">NoSQL 사용 시 고려할 점</h3>
<ul>
<li>제품마다 쿼리 방식과 트랜잭션 기능이 크게 다르다.</li>
<li>데이터를 중복 저장하는 설계가 흔해 수정 시 여러 데이터를 함께 갱신해야 할 수 있다.</li>
<li>복잡한 조인이나 다양한 분석 쿼리는 관계형 DB보다 불편할 수 있다.</li>
<li>유연한 구조가 곧 &quot;규칙이 필요 없다&quot;는 뜻은 아니다. 애플리케이션 또는 DB 기능으로 데이터 품질을 관리해야 한다.</li>
</ul>
<blockquote>
<p>모든 NoSQL이 일관성과 트랜잭션을 포기하는 것은 아니다. MongoDB처럼 다중 문서 트랜잭션을 지원하거나, 강한 일관성을 선택할 수 있는 제품도 있다. 실제 보장 범위는 제품과 설정에 따라 확인해야 한다.</p>
</blockquote>

<h3 id="무엇이-더-좋은-데이터베이스일까">무엇이 더 좋은 데이터베이스일까?</h3>
<p>정답은 &quot;요구사항에 따라 다르다&quot;이다.</p>
<p>다음 질문으로 선택 범위를 좁힐 수 있다.</p>
<ol>
<li>결제처럼 반드시 정확해야 하는 데이터인가?</li>
<li>여러 데이터 사이의 관계와 조인이 중요한가?</li>
<li>데이터 구조가 자주 바뀌는가?</li>
<li>읽기와 쓰기 중 어느 작업이 더 많은가?</li>
<li>데이터와 사용자가 얼마나 빠르게 증가하는가?</li>
<li>복잡한 분석이 필요한가, 정해진 형태의 빠른 조회가 필요한가?</li>
<li>팀이 안정적으로 운영할 수 있는 기술인가?</li>
</ol>
<h3 id="실제-서비스에서는-함께-사용한다">실제 서비스에서는 함께 사용한다</h3>
<p>관계형 DB와 NoSQL 중 하나만 선택해야 하는 것은 아니다. 기능에 따라 여러 데이터베이스를 함께 사용하는 <strong>폴리글랏 퍼시스턴스(Polyglot Persistence)</strong> 방식이 흔하다.</p>
<pre><code class="language-text">쇼핑몰 서비스
├── PostgreSQL: 회원, 주문, 결제, 재고
├── Redis: 로그인 세션, 인기 상품 캐시
├── MongoDB: 형식이 다양한 상품 상세 정보
└── Elasticsearch: 상품 검색과 로그 검색</code></pre>
<p>여기서 가장 중요한 것은 데이터베이스의 개수가 아니라 <strong>각 데이터의 원본이 어디인지 명확히 정하는 것</strong>이다. 같은 정보를 여러 저장소에 두면 어느 데이터를 기준으로 판단할지 정해야 한다.</p>
<hr />
<h2 id="7-정규화-중복을-줄이고-데이터의-책임을-나누기">7. 정규화: 중복을 줄이고 데이터의 책임을 나누기</h2>
<p><strong>정규화(Normalization)</strong>는 데이터 중복을 줄이고, 데이터가 한 곳에서 일관되게 관리되도록 테이블 구조를 개선하는 과정이다.</p>
<p>정규화가 필요한 이유를 이해하려면 먼저 잘못 설계된 테이블에서 어떤 문제가 생기는지 살펴봐야 한다.</p>
<h3 id="71-비정규화-테이블에서-발생하는-세-가지-이상-현상">7.1 비정규화 테이블에서 발생하는 세 가지 이상 현상</h3>

majors(major_id, major_code, major_name, major_office)</code></pre>
<h3 id="72-함수-종속을-쉽게-이해하기">7.2 함수 종속을 쉽게 이해하기</h3>
<p>정규화에서는 <strong>함수 종속(Functional Dependency)</strong>이라는 말을 자주 사용한다.</p>
<pre><code class="language-text">student_id -&gt; student_name</code></pre>
<p>이는 <code>student_id</code> 값을 알면 <code>student_name</code>이 하나로 결정된다는 뜻이다. 여기서 왼쪽의 <code>student_id</code>를 <strong>결정자</strong>라고 한다.</p>
<p>다음 관계도 생각해 볼 수 있다.</p>
<pre><code class="language-text">major_id -&gt; major_name, major_office</code></pre>
<p>학생 번호가 아니라 학과 번호가 학과명과 사무실을 결정하므로, 학과 정보는 학생 테이블보다 학과 테이블이 책임지는 편이 자연스럽다.</p>
<h3 id="73-제1정규형-한-칸에는-하나의-값만-저장한다">7.3 제1정규형: 한 칸에는 하나의 값만 저장한다</h3>
<p><strong>제1정규형(1NF)</strong>의 핵심은 각 칸에 더 이상 목록으로 분해해야 하는 반복값을 넣지 않는 것이다.</p>
<p>다음 테이블은 <code>subjects</code> 한 칸에 여러 과목을 저장하므로 1NF에 맞지 않는다.</p>
<table>
<thead>
<tr>
<th align="right">student_id</th>
<th>name</th>
<th>subjects</th>
</tr>
</thead>
<tbody><tr>
<td align="right">1001</td>
<td>김학생</td>
<td>데이터베이스, 네트워크, 운영체제</td>
</tr>
</tbody></table>
<p>문자열을 쉼표로 나누어 저장하면 특정 과목의 수강생을 조회하거나 외래 키로 과목의 존재를 검증하기 어렵다. 학생, 과목, 수강 신청을 분리하는 편이 좋다.</p>
<pre><code class="language-text">students(student_id, name)
courses(course_id, title)
enrollments(student_id, course_id)</code></pre>
<blockquote>
<p>1NF는 테이블 전체에 같은 값이 반복되면 안 된다는 뜻이 아니다. 여러 학생의 학년이 모두 <code>1</code>일 수 있다. 중요한 것은 한 셀에 의미상 여러 값을 목록처럼 넣지 않는 것이다.</p>
</blockquote>
<h3 id="74-제2정규형-복합-키의-일부에만-의존하는-속성을-분리한다">7.4 제2정규형: 복합 키의 일부에만 의존하는 속성을 분리한다</h3>
<p><strong>제2정규형(2NF)</strong>은 1NF를 만족하면서, 일반 속성이 복합 기본 키 전체에 의존하도록 만드는 단계다.</p>
<p>다음 수강 테이블의 기본 키가 <code>(student_id, course_id)</code>라고 가정해 보자.</p>
<table>
<thead>
<tr>
<th align="right">student_id</th>
<th align="right">course_id</th>
<th>student_name</th>
<th>course_title</th>
<th align="right">score</th>
</tr>
</thead>
<tbody><tr>
<td align="right">1001</td>
<td align="right">10</td>
<td>김학생</td>
<td>데이터베이스</td>
<td align="right">95</td>
</tr>
</tbody></table>
<p>각 속성의 의존 관계는 다음과 같다.</p>
<pre><code class="language-text">student_id -&gt; student_name
course_id -&gt; course_title
(student_id, course_id) -&gt; score</code></pre>
<p><code>student_name</code>은 복합 키 중 <code>student_id</code>에만 의존하고, <code>course_title</code>은 <code>course_id</code>에만 의존한다. 이를 <strong>부분 함수 종속</strong>이라고 한다.</p>
<p>따라서 다음처럼 분리한다.</p>
<pre><code class="language-text">students(student_id, student_name)
courses(course_id, course_title)
enrollments(student_id, course_id, score)</code></pre>
<h3 id="75-제3정규형-일반-속성이-다른-일반-속성에-의존하지-않게-한다">7.5 제3정규형: 일반 속성이 다른 일반 속성에 의존하지 않게 한다</h3>
<p><strong>제3정규형(3NF)</strong>은 2NF를 만족하면서 기본 키가 아닌 속성 사이의 이행 종속을 제거하는 단계다.</p>
<pre><code class="language-text">student_id -&gt; major_id -&gt; major_name</code></pre>
<p>학생 번호가 학과 번호를 결정하고, 학과 번호가 다시 학과명을 결정한다. <code>major_name</code>은 학생 번호에 직접 의존하기보다 <code>major_id</code>를 거쳐 간접적으로 결정된다.</p>
<pre><code class="language-text">students(student_id, name, major_id)
majors(major_id, major_name)</code></pre>
<p>학과 정보를 별도 테이블로 분리하면 학과명이 변경되어도 한 곳만 수정하면 된다.</p>
<h3 id="76-bcnf는-모든-결정자가-후보-키인지-확인한다">7.6 BCNF는 모든 결정자가 후보 키인지 확인한다</h3>
<p><strong>BCNF(Boyce-Codd Normal Form)</strong>는 3NF보다 조금 더 엄격하다. 테이블에 존재하는 모든 함수 종속에서 결정자가 후보 키가 되도록 요구한다.</p>
<p>초보 단계에서는 다음처럼 기억하면 충분하다.</p>
<blockquote>
<p>어떤 일반 속성이 다른 행의 값을 결정하는 구조가 숨어 있지 않은지 한 번 더 점검하는 단계</p>
</blockquote>
<p>대부분의 업무 시스템은 우선 3NF까지 안정적으로 설계한 뒤, 복잡한 후보 키 관계가 있을 때 BCNF를 검토한다.</p>

<h3 id="78-정규화한-학사-시스템-예시">7.8 정규화한 학사 시스템 예시</h3>
<pre><code class="language-sql">CREATE TABLE majors (
    major_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    major_code VARCHAR(20) NOT NULL UNIQUE,
    major_name VARCHAR(100) NOT NULL
);

CREATE TABLE students (
    student_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    student_no VARCHAR(20) NOT NULL UNIQUE,
    name VARCHAR(100) NOT NULL,
    major_id INTEGER REFERENCES majors(major_id)
);

CREATE TABLE courses (
    course_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    course_code VARCHAR(20) NOT NULL UNIQUE,
    title VARCHAR(100) NOT NULL
);

CREATE TABLE enrollments (
    student_id BIGINT REFERENCES students(student_id),
    course_id INTEGER REFERENCES courses(course_id),
    score NUMERIC(5, 2) CHECK (score BETWEEN 0 AND 100),
    PRIMARY KEY (student_id, course_id)
);</code></pre>
<p>이 구조에서는 학생, 학과, 과목의 설명을 각각 한 곳에서 관리한다. <code>enrollments</code>는 학생과 과목의 N:M 관계를 연결하면서 관계 자체의 속성인 <code>score</code>를 저장한다.</p>
<h3 id="79-정규화는-많을수록-좋은가">7.9 정규화는 많을수록 좋은가?</h3>
<p>정규화를 많이 하면 중복은 줄지만 조회할 때 필요한 <code>JOIN</code>이 늘어날 수 있다. 분석 리포트처럼 읽기 성능이 매우 중요하거나 계산 비용이 큰 경우에는 일부 값을 의도적으로 중복 저장하는 <strong>반정규화(Denormalization)</strong>를 검토할 수 있다.</p>
<p>반정규화는 설계를 대충 하는 것이 아니다. 다음 조건을 확인한 뒤 의도적으로 적용해야 한다.</p>
<ul>
<li>실제 성능 측정에서 병목이 확인되었는가?</li>
<li>중복값을 누가 언제 갱신할지 규칙이 있는가?</li>
<li>원본 데이터가 어디인지 명확한가?</li>
<li>Materialized View, 캐시, 인덱스로 먼저 해결할 수 없는가?</li>
</ul>

<h2 id="8-erd-데이터-구조를-코드보다-먼저-그리기">8. ERD: 데이터 구조를 코드보다 먼저 그리기</h2>

<h3 id="82-속성의-종류">8.2 속성의 종류</h3>

<th>설명</th>
<th>예시</th>
</tr>
</thead>
<tbody><tr>
<td>단순 속성</td>
<td>더 나누지 않고 하나의 값으로 관리</td>
<td>성별, 생년월일</td>
</tr>
<tr>
<td>복합 속성</td>
<td>여러 세부 속성으로 나눌 수 있음</td>
<td>주소 = 시·구·도로명·상세주소</td>
</tr>
<tr>
<td>단일값 속성</td>
<td>한 인스턴스에 하나의 값</td>
<td>학번</td>
</tr>
<tr>
<td>다중값 속성</td>
<td>한 인스턴스에 여러 값</td>
<td>취미, 여러 전화번호</td>
</tr>
<tr>
<td>유도 속성</td>
<td>다른 값으로 계산 가능</td>
<td>생년월일로 계산한 나이</td>
</tr>
<tr>
<td>키 속성</td>
<td>인스턴스를 고유하게 식별</td>
<td>학생 번호</td>
</tr>
</tbody></table>
<p>다중값 속성은 한 컬럼에 쉼표로 넣기보다 별도 테이블로 분리하는 것이 일반적이다. 유도 속성은 값이 계속 바뀌거나 쉽게 계산할 수 있다면 직접 저장하지 않고 조회 시 계산할 수 있다.</p>
<h3 id="83-카디널리티와-선택성">8.3 카디널리티와 선택성</h3>
<p>ERD의 관계선에는 한쪽 인스턴스가 다른 쪽 인스턴스 몇 개와 연결되는지 표시한다.</p>
<table>
<thead>
<tr>
<th>표기 의미</th>
<th>설명</th>
<th>예시</th>
</tr>
</thead>
<tbody><tr>
<td>1:1</td>
<td>양쪽이 하나씩 연결</td>
<td>사용자와 사용자 상세정보</td>
</tr>
<tr>
<td>1:N</td>
<td>한쪽 하나가 반대쪽 여러 개와 연결</td>
<td>학과와 학생</td>
</tr>
<tr>
<td>N:M</td>
<td>양쪽 모두 여러 개와 연결</td>
<td>학생과 강좌</td>
</tr>
<tr>
<td>0..1</td>
<td>없거나 하나</td>
<td>직원의 선택적 주차권</td>
</tr>
<tr>
<td>1..N</td>
<td>반드시 하나 이상</td>
<td>주문에 포함된 주문항목</td>
</tr>
</tbody></table>
<p><strong>카디널리티(Cardinality)</strong>가 최대 연결 개수를 표현한다면, <code>0</code> 또는 <code>1</code>로 시작하는 표기는 관계 참여가 선택인지 필수인지 나타낸다.</p>
<h3 id="84-식별-관계와-비식별-관계">8.4 식별 관계와 비식별 관계</h3>
<table>
<thead>
<tr>
<th>관계</th>
<th>특징</th>
<th>예시</th>
</tr>
</thead>
<tbody><tr>
<td>식별 관계</td>
<td>부모의 PK가 자식 PK의 일부가 됨</td>
<td>주문 <code>(order_id)</code>과 주문항목 <code>(order_id, item_no)</code></td>
</tr>
<tr>
<td>비식별 관계</td>
<td>부모의 PK가 자식의 일반 FK가 됨</td>
<td>학과와 학생의 <code>major_id</code></td>
</tr>
</tbody></table>
<p>식별 관계의 자식은 부모 없이는 식별하기 어렵다. 반면 비식별 관계의 자식은 자체 기본 키를 가지고 외래 키로 부모를 참조한다.</p>
<h3 id="85-erd를-만드는-순서">8.5 ERD를 만드는 순서</h3>
<ol>
<li>요구사항에서 관리할 명사를 찾는다.</li>
<li>명사가 단순한 속성인지 독립적인 엔티티인지 구분한다.</li>
<li>각 엔티티의 기본 키와 필수 속성을 정한다.</li>
<li>엔티티 사이의 업무 관계를 동사로 표현한다.</li>
<li>관계의 카디널리티와 선택성을 정한다.</li>
<li>N:M 관계를 교차 엔티티로 변환한다.</li>
<li>데이터 중복, 누락된 규칙, 삭제 영향을 검토한다.</li>
</ol>
<p>예를 들어 &quot;학생은 여러 강좌를 수강하고, 강좌에는 여러 학생이 참여한다&quot;는 요구사항에서는 학생과 강좌 사이에 N:M 관계가 발견된다. 이를 <code>수강신청</code> 엔티티로 해결한다.</p>
<h3 id="86-erd-검토-질문">8.6 ERD 검토 질문</h3>
<ul>
<li>엔티티 이름만 보고 어떤 데이터를 관리하는지 알 수 있는가?</li>
<li>모든 엔티티에 안정적인 식별자가 있는가?</li>
<li>외래 키가 올바른 부모 엔티티를 참조하는가?</li>
<li>필수 관계와 선택 관계가 실제 업무 규칙과 일치하는가?</li>
<li>N:M 관계가 교차 엔티티로 해소되었는가?</li>
<li>여러 값을 갖는 속성이 한 컬럼에 들어가 있지 않은가?</li>
<li>부모를 삭제할 때 자식 데이터를 어떻게 처리할지 정했는가?</li>
</ul>
<h3 id="87-dbml로-빠르게-erd-작성하기">8.7 DBML로 빠르게 ERD 작성하기</h3>
<p><a href="https://dbdiagram.io/">dbdiagram.io</a>에서는 DBML 문법으로 ERD를 작성하고 SQL로 내보낼 수 있다.</p>
<pre><code class="language-text">Table students {
  student_id bigint [pk, increment]
  student_no varchar(20) [unique, not null]
  name varchar(100) [not null]
  major_id int [ref: &gt; majors.major_id]
}

Table majors {
  major_id int [pk, increment]
  major_code varchar(20) [unique, not null]
  major_name varchar(100) [not null]
}

Table courses {
  course_id int [pk, increment]
  title varchar(100) [not null]
}

Table enrollments {
  student_id bigint [ref: &gt; students.student_id]
  course_id int [ref: &gt; courses.course_id]
  enrolled_at date [not null]

  indexes {
    (student_id, course_id) [pk]
  }
}</code></pre>
<p>ERD 도구는 그림을 대신 그려 주지만 업무 규칙을 결정해 주지는 않는다. 올바른 엔티티와 관계를 판단하는 일은 설계자의 몫이다.</p>

<h3 id="91-하나의-요구사항이-테이블이-되기까지">9.1 하나의 요구사항이 테이블이 되기까지</h3>
<p>요구사항이 다음과 같다고 가정해 보자.</p>
<blockquote>
<p>학생은 하나의 학과에 소속되고 여러 강좌를 수강할 수 있다. 강좌에도 여러 학생이 참여할 수 있으며 수강 신청일과 성적을 기록한다.</p>
</blockquote>
<h4 id="개념적-모델">개념적 모델</h4>
<pre><code class="language-text">학생 -&gt; 학과에 소속된다 -&gt; 학과
학생 -&gt; 강좌를 수강한다 -&gt; 강좌</code></pre>
<p>이 단계에서는 특정 DBMS의 데이터 타입이나 인덱스를 고민하지 않는다. 업무 담당자도 이해할 수 있는 수준으로 대상을 찾는다.</p>
<h4 id="논리적-모델">논리적 모델</h4>
<pre><code class="language-text">MAJORS(major_id PK, major_code UK, major_name)
STUDENTS(student_id PK, student_no UK, name, major_id FK)
COURSES(course_id PK, course_code UK, title)
ENROLLMENTS(student_id PK/FK, course_id PK/FK, enrolled_at, score)</code></pre>
<p>N:M 관계인 학생과 강좌 사이에 <code>ENROLLMENTS</code>를 추가하고 기본 키, 외래 키, 고유 키를 결정한다.</p>
<h4 id="물리적-모델">물리적 모델</h4>
<pre><code class="language-text">student_id: BIGINT GENERATED AS IDENTITY
score: NUMERIC(5, 2)
enrolled_at: DATE DEFAULT CURRENT_DATE
idx_enrollments_course: (course_id, student_id)</code></pre>
<p>PostgreSQL에서 사용할 구체적인 데이터 타입, 기본값, 인덱스 이름과 저장 전략을 결정한다.</p>

<h3 id="93-낙관적-잠금과-비관적-잠금">9.3 낙관적 잠금과 비관적 잠금</h3>
<table>
<thead>
<tr>
<th>비교</th>
<th>낙관적 잠금</th>
<th>비관적 잠금</th>
</tr>
</thead>
<tbody><tr>
<td>기본 가정</td>
<td>충돌이 드물다</td>
<td>충돌 가능성이 높다</td>
</tr>
<tr>
<td>처리 방식</td>
<td>저장할 때 버전이 같은지 확인</td>
<td>읽을 때부터 다른 변경을 잠금</td>
</tr>
<tr>
<td>적합한 예</td>
<td>게시글·프로필 수정</td>
<td>은행 이체·좌석 예매</td>
</tr>
<tr>
<td>대표 구현</td>
<td><code>version</code> 컬럼 비교</td>
<td><code>SELECT ... FOR UPDATE</code></td>
</tr>
</tbody></table>
<p>낙관적 잠금의 예시는 다음과 같다.</p>
<pre><code class="language-sql">UPDATE posts
SET title = '수정된 제목',
    version = version + 1
WHERE post_id = 10
  AND version = 3;</code></pre>
<p>영향받은 행이 0개라면 다른 사용자가 먼저 데이터를 수정해 버전이 달라졌다는 뜻이다. 애플리케이션은 사용자에게 다시 시도하도록 안내할 수 있다.</p>
<p>비관적 잠금은 데이터를 읽을 때부터 충돌을 막는다.</p>
<pre><code class="language-sql">BEGIN;

SELECT seat_id, status
FROM seats
WHERE seat_id = 101
FOR UPDATE;

UPDATE seats
SET status = 'RESERVED'
WHERE seat_id = 101;

COMMIT;</code></pre>
<p>잠금은 안전성을 높이지만 오래 유지하면 다른 트랜잭션이 기다리게 된다. 필요한 행만 짧은 시간 동안 잠그는 것이 중요하다.</p>
<h3 id="94-약한-엔티티-설계">9.4 약한 엔티티 설계</h3>
<p>주문항목은 주문 없이 존재할 수 없다. 주문번호만으로는 어떤 항목인지 구분할 수 없으므로 주문번호와 항목번호를 함께 기본 키로 사용할 수 있다.</p>
<pre><code class="language-sql">CREATE TABLE order_items (
    order_id BIGINT REFERENCES orders(order_id) ON DELETE CASCADE,
    item_no SMALLINT NOT NULL,
    product_id BIGINT REFERENCES products(product_id),
    quantity INTEGER NOT NULL CHECK (quantity &gt; 0),
    unit_price NUMERIC(12, 2) NOT NULL CHECK (unit_price &gt;= 0),
    PRIMARY KEY (order_id, item_no)
);</code></pre>
<p><code>ON DELETE CASCADE</code>는 주문이 삭제될 때 그 주문에 속한 주문항목도 함께 삭제한다. 편리하지만 삭제 영향이 크므로 실제 업무의 보존 정책과 일치하는지 확인해야 한다.</p>
<h3 id="95-nm-교차-테이블과-인덱스">9.5 N:M 교차 테이블과 인덱스</h3>
<pre><code class="language-sql">CREATE TABLE enrollments (
    student_id BIGINT REFERENCES students(student_id) ON DELETE CASCADE,
    course_id INTEGER REFERENCES courses(course_id) ON DELETE CASCADE,
    enrolled_at DATE NOT NULL DEFAULT CURRENT_DATE,
    score NUMERIC(5, 2),
    PRIMARY KEY (student_id, course_id),
    CONSTRAINT chk_enrollment_score
        CHECK (score IS NULL OR score BETWEEN 0 AND 100)
);

CREATE INDEX idx_enrollments_course_student
    ON enrollments (course_id, student_id);</code></pre>
<p>복합 기본 키 <code>(student_id, course_id)</code>는 학생을 기준으로 수강 내역을 찾을 때 유리하다. 반대로 강좌별 학생을 자주 찾는다면 <code>(course_id, student_id)</code> 순서의 인덱스를 추가할 수 있다.</p>
<blockquote>
<p>인덱스 컬럼 순서는 단순히 양쪽 경우를 모두 만드는 것이 아니라 실제 <code>WHERE</code>, <code>JOIN</code>, <code>ORDER BY</code> 패턴을 확인한 뒤 결정해야 한다. 인덱스가 많아지면 쓰기와 저장 공간 비용도 증가한다.</p>
</blockquote>

<h2 id="10-스키마-전략과-rdbms-선택">10. 스키마 전략과 RDBMS 선택</h2>
<h3 id="101-데이터베이스와-스키마는-어떻게-다를까">10.1 데이터베이스와 스키마는 어떻게 다를까?</h3>
<p><strong>스키마(Schema)</strong>는 테이블, 뷰, 함수 같은 데이터베이스 객체를 논리적으로 묶는 이름 공간이다.</p>
<pre><code class="language-text">하나의 PostgreSQL 서버
└── campus_db
    ├── public
    ├── academic
    │   ├── students
    │   ├── courses
    │   └── enrollments
    └── audit
        └── change_logs</code></pre>
<p>건물에 비유하면 데이터베이스는 하나의 건물이고, 스키마는 용도별로 구분한 사무실에 가깝다. 같은 데이터베이스 안에서도 스키마별로 이름과 권한을 분리할 수 있다.</p>
<p>DBMS에 따라 <code>database</code>, <code>schema</code>, <code>user</code>의 의미와 계층이 다르다.</p>
<table>
<thead>
<tr>
<th>DBMS</th>
<th>일반적인 구조</th>
</tr>
</thead>
<tbody><tr>

<h3 id="104-ansi-sql과-dbms별-문법-차이">10.4 ANSI SQL과 DBMS별 문법 차이</h3>
<p>SQL에는 국제 표준이 있지만 모든 DBMS가 완전히 같은 문법과 기능을 제공하지는 않는다. <code>SELECT</code>, <code>JOIN</code>, <code>GROUP BY</code>, <code>CASE</code>, <code>COALESCE</code> 같은 핵심 문법은 대체로 공통이지만 페이지 조회, 자동 증가, 날짜, JSON 기능은 차이가 크다.</p>

<ul>

<li>식별자는 소문자 <code>snake_case</code>처럼 일관된 규칙을 사용한다.</li>
<li>날짜, 자동 증가, JSON, 페이지네이션은 DBMS별 차이를 별도로 관리한다.</li>
<li>성능 최적화가 필요할 때는 DBMS 전용 인덱스와 기능을 의도적으로 사용한다.</li>

<h3 id="115-강좌와-수강-신청-테이블-추가">11.5 강좌와 수강 신청 테이블 추가</h3>
<pre><code class="language-sql">CREATE TABLE academic.courses (
    course_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    course_code VARCHAR(20) NOT NULL UNIQUE,
    title VARCHAR(100) NOT NULL,
    credits SMALLINT NOT NULL CHECK (credits BETWEEN 1 AND 6)
);

CREATE TABLE academic.enrollments (
    student_id BIGINT REFERENCES academic.students(student_id)
        ON DELETE CASCADE,
    course_id INTEGER REFERENCES academic.courses(course_id)
        ON DELETE CASCADE,
    enrolled_at DATE NOT NULL DEFAULT CURRENT_DATE,
    score NUMERIC(5,2),
    PRIMARY KEY (student_id, course_id),
    CONSTRAINT chk_score
        CHECK (score IS NULL OR score BETWEEN 0 AND 100)
);

CREATE INDEX idx_enrollments_course_student
    ON academic.enrollments (course_id, student_id);</code></pre>
<h3 id="116-alter-table로-구조-변경하기">11.6 ALTER TABLE로 구조 변경하기</h3>
<pre><code class="language-sql">-- 컬럼 추가
ALTER TABLE academic.students
ADD COLUMN phone VARCHAR(20);

-- 기존 데이터가 조건을 만족할 때 NOT NULL 추가
ALTER TABLE academic.students
ALTER COLUMN phone SET NOT NULL;

-- 제약 조건 추가
ALTER TABLE academic.students
ADD CONSTRAINT chk_email_format CHECK (email LIKE '%@%');

-- 컬럼 타입 변경
ALTER TABLE academic.students
ALTER COLUMN phone TYPE VARCHAR(30);</code></pre>
<p>작은 개발 DB에서는 간단해 보이는 변경도 대용량 운영 테이블에서는 전체 재작성, 긴 잠금, 복제 지연을 일으킬 수 있다. 운영 환경에서는 실행계획뿐 아니라 잠금 시간, 롤백 방법, 배포 순서를 함께 준비해야 한다.</p>
<p>PostgreSQL에서는 운영 중 일반 인덱스 생성을 다음처럼 수행할 수 있다.</p>
<pre><code class="language-sql">CREATE INDEX CONCURRENTLY idx_students_grade
    ON academic.students (grade);</code></pre>
<p><code>CONCURRENTLY</code>는 일반 생성보다 오래 걸릴 수 있지만 쓰기 작업을 장시간 막는 위험을 줄인다. 트랜잭션 블록 안에서는 실행할 수 없다는 점도 기억해야 한다.</p>

<p>트랜잭션 처리, 트리거, ID 초기화, 외래 키 제약의 세부 동작은 DBMS마다 다르다. 특히 운영 환경에서는 <code>TRUNCATE</code>가 항상 롤백 불가능하다고 가정하거나, 모든 트리거가 동일하게 동작한다고 가정하면 안 된다.</p>
<h3 id="118-ddl-설계-체크리스트">11.8 DDL 설계 체크리스트</h3>

<li>기본 키가 안정적이며 자주 변경되지 않는가?</li>
<li>자연키가 필요하다면 <code>UNIQUE</code> 제약으로 업무 중복을 막았는가?</li>
<li>외래 키가 실제 관계와 삭제 정책을 반영하는가?</li>
<li>금액과 비율에 적절한 정밀도를 사용했는가?</li>
<li>시간 컬럼의 타임존과 저장 기준이 일관적인가?</li>
<li><code>CHECK</code>와 <code>ENUM</code>이 자주 바뀌는 업무를 과도하게 고정하지 않는가?</li>
<li>JSON으로 넣은 데이터가 사실상 별도 컬럼이나 테이블이어야 하지는 않는가?</li>
<li>자주 사용하는 FK와 검색 조건에 인덱스가 필요한가?</li>

<h2 id="12-dml-데이터를-조회하고-변경하기">12. DML: 데이터를 조회하고 변경하기</h2>
<p><strong>DML(Data Manipulation Language)</strong>은 테이블에 저장된 데이터를 조회하거나 추가, 수정, 삭제하는 명령이다.</p>
<pre><code class="language-text">CREATE -&gt; INSERT -&gt; SELECT -&gt; UPDATE -&gt; DELETE
구조 생성   데이터 추가   조회      수정      삭제</code></pre>
<h3 id="121-insert로-데이터-추가하기">12.1 INSERT로 데이터 추가하기</h3>
<pre><code class="language-sql">INSERT INTO academic.majors (major_code, major_name)
VALUES
    ('CS', '컴퓨터공학과'),
    ('BUS', '경영학과');

INSERT INTO academic.students
    (student_no, name, email, major_id, grade)
VALUES
    ('2026001', '김학생', 'kim@example.com', 1, 1),
    ('2026002', '이학생', 'lee@example.com', 1, 2),
    ('2026003', '박학생', 'park@example.com', 2, 1);

INSERT INTO academic.courses (course_code, title, credits)
VALUES
    ('CS101', '데이터베이스', 3),
    ('CS102', '알고리즘', 3),
    ('BUS101', '경영학개론', 3);</code></pre>
<p>컬럼 목록을 생략하면 테이블 구조가 바뀌었을 때 오류나 잘못된 입력이 발생하기 쉽다. 실무에서는 <code>INSERT INTO table (column1, column2)</code>처럼 컬럼을 명시하는 습관이 좋다.</p>
<h3 id="122-update와-delete에서는-where를-먼저-확인한다">12.2 UPDATE와 DELETE에서는 WHERE를 먼저 확인한다</h3>
<pre><code class="language-sql">UPDATE academic.students
SET grade = grade + 1
WHERE enrolled = TRUE
  AND grade &lt; 4;</code></pre>
<p><code>WHERE</code>를 생략하면 모든 행이 수정된다. 먼저 같은 조건으로 <code>SELECT</code>를 실행해 대상 행을 확인하면 실수를 줄일 수 있다.</p>
<pre><code class="language-sql">SELECT student_id, name, grade
FROM academic.students
WHERE enrolled = TRUE
  AND grade &lt; 4;</code></pre>
<p>삭제도 같은 원칙을 적용한다.</p>
<pre><code class="language-sql">DELETE FROM academic.enrollments
WHERE student_id = 1001
  AND course_id = 10;</code></pre>
<p>중요한 변경은 트랜잭션 안에서 확인한 뒤 확정할 수 있다.</p>
<pre><code class="language-sql">BEGIN;

UPDATE academic.students
SET enrolled = FALSE
WHERE student_no = '2026003';

-- 결과 확인
SELECT student_no, name, enrolled
FROM academic.students
WHERE student_no = '2026003';

COMMIT;
-- 문제가 있다면 COMMIT 대신 ROLLBACK;</code></pre>
<h3 id="123-select의-작성-순서와-논리적-실행-순서">12.3 SELECT의 작성 순서와 논리적 실행 순서</h3>
<p>SQL은 다음 순서로 작성한다.</p>
<pre><code class="language-sql">SELECT
    s.student_no,
    s.name,
    m.major_name
FROM academic.students AS s
JOIN academic.majors AS m
    ON m.major_id = s.major_id
WHERE s.enrolled = TRUE
ORDER BY s.name ASC
LIMIT 20;</code></pre>
<p>하지만 데이터베이스가 논리적으로 처리하는 순서는 다르다.</p>
<pre><code class="language-text">FROM -&gt; JOIN -&gt; WHERE -&gt; GROUP BY -&gt; HAVING
     -&gt; SELECT -&gt; ORDER BY -&gt; LIMIT</code></pre>
<p>이 순서를 알면 <code>WHERE</code>에서 <code>SELECT</code>의 별칭을 사용할 수 없는 이유를 이해하기 쉽다. 별칭은 논리적으로 <code>WHERE</code>보다 나중인 <code>SELECT</code> 단계에서 만들어지기 때문이다.</p>
<h3 id="124-where-조건-패턴">12.4 WHERE 조건 패턴</h3>
<table>
<thead>
<tr>
<th>목적</th>
<th>예시</th>
</tr>
</thead>
<tbody><tr>
<td>값 비교</td>
<td><code>grade = 3</code>, <code>score &gt;= 80</code></td>
</tr>
<tr>
<td>범위</td>
<td><code>grade BETWEEN 2 AND 4</code></td>
</tr>
<tr>
<td>목록</td>
<td><code>major_id IN (1, 3, 5)</code></td>
</tr>
<tr>
<td>접두어 검색</td>
<td><code>name LIKE '김%'</code></td>
</tr>
<tr>
<td>NULL 검사</td>
<td><code>phone IS NULL</code></td>
</tr>
<tr>
<td>여러 조건</td>
<td><code>enrolled = TRUE AND grade &lt; 4</code></td>
</tr>
</tbody></table>
<p><code>AND</code>, <code>OR</code>, <code>NOT</code>을 함께 쓰면 우선순위를 눈으로 파악하기 어렵다. 괄호로 의도를 명확하게 표현하자.</p>
<pre><code class="language-sql">WHERE enrolled = TRUE
  AND (major_id = 1 OR grade = 4);</code></pre>
<p><code>LIKE '김%'</code>는 문자열 앞부분이 고정되어 일반 B-Tree 인덱스를 활용할 가능성이 있지만, <code>LIKE '%학생%'</code>처럼 앞에 와일드카드가 있으면 일반 인덱스를 사용하기 어렵다.</p>
<h3 id="125-null은-값이-아니라-값이-없거나-모름을-나타낸다">12.5 NULL은 값이 아니라 값이 없거나 모름을 나타낸다</h3>
<p>다음 조건은 올바르지 않다.</p>
<pre><code class="language-sql">WHERE phone = NULL;</code></pre>
<p>NULL은 일반 비교 연산자로 판단하지 않고 <code>IS NULL</code> 또는 <code>IS NOT NULL</code>을 사용한다.</p>
<pre><code class="language-sql">SELECT student_no, name
FROM academic.students
WHERE phone IS NULL;</code></pre>
<p>NULL이 포함된 계산 결과도 보통 NULL이 된다.</p>
<pre><code class="language-sql">SELECT NULL + 5;                  -- NULL
SELECT COALESCE(NULL, 0) + 5;    -- 5</code></pre>
<p><code>COALESCE</code>는 왼쪽부터 확인해 처음 만나는 NULL이 아닌 값을 반환한다.</p>
<pre><code class="language-sql">SELECT
    name,
    COALESCE(phone, '연락처 미등록') AS phone_display
FROM academic.students;</code></pre>
<h3 id="126-문자열과-날짜-함수">12.6 문자열과 날짜 함수</h3>
<pre><code class="language-sql">SELECT
    UPPER('hello') AS upper_text,
    LOWER('WORLD') AS lower_text,
    LENGTH('database') AS text_length,
    SUBSTRING('database' FROM 1 FOR 4) AS short_text,
    TRIM('  SQL  ') AS trimmed_text,
    REPLACE('hello world', 'world', 'database') AS replaced_text;</code></pre>
<p>PostgreSQL의 날짜 함수 예시는 다음과 같다.</p>
<pre><code class="language-sql">SELECT
    CURRENT_DATE,
    CURRENT_TIMESTAMP,
    EXTRACT(YEAR FROM CURRENT_DATE) AS current_year,
    DATE_TRUNC('month', CURRENT_TIMESTAMP) AS month_start,
    CURRENT_TIMESTAMP - INTERVAL '30 days' AS thirty_days_ago;</code></pre>
<p>날짜 함수 이름과 반환 타입은 DBMS별 차이가 크므로 다른 DB로 이동할 때 확인해야 한다.</p>
<h3 id="127-case로-값에-의미-있는-이름-붙이기">12.7 CASE로 값에 의미 있는 이름 붙이기</h3>
<pre><code class="language-sql">SELECT
    student_no,
    name,
    grade,
    CASE grade
        WHEN 1 THEN '신입생'
        WHEN 4 THEN '졸업반'
        ELSE grade || '학년'
    END AS grade_label
FROM academic.students
ORDER BY grade, name;</code></pre>
<p><code>CASE</code>는 조회 결과를 분류하거나 조건에 따라 다른 값을 표현할 때 유용하다. 하지만 중요한 업무 규칙을 쿼리마다 서로 다르게 작성하면 불일치가 생길 수 있으므로 공통 기준은 코드, 뷰 또는 기준 테이블로 관리하는 방법도 고려한다.</p>
<h3 id="128-dml-안전-체크리스트">12.8 DML 안전 체크리스트</h3>
<ul>
<li><code>UPDATE</code>와 <code>DELETE</code> 전에 같은 <code>WHERE</code> 조건으로 <code>SELECT</code>했는가?</li>
<li>중요한 변경을 트랜잭션으로 묶었는가?</li>
<li><code>SELECT *</code> 대신 필요한 컬럼만 선택했는가?</li>
<li>NULL을 <code>= NULL</code>로 비교하지 않았는가?</li>
<li>문자열 연결이 아닌 파라미터 바인딩으로 SQL Injection을 막았는가?</li>
<li>대량 삭제·수정을 작은 배치로 나눌 필요는 없는가?</li>
<li>정렬 결과가 필요하면 <code>ORDER BY</code>를 명시했는가?</li>
</ul>

<h2 id="데이터베이스를-왜-배워야-할까">데이터베이스를 왜 배워야 할까?</h2>
<h3 id="131-대부분의-서비스는-데이터를-중심으로-동작한다">13.1 대부분의 서비스는 데이터를 중심으로 동작한다</h3>
<p>화면과 API가 잘 만들어져도 고객, 주문, 결제 데이터가 잘못 저장되면 서비스는 정상적으로 운영될 수 없다. 데이터베이스는 많은 애플리케이션의 중심 상태를 보관한다.</p>
<h3 id="132-개발자가-직접-sql을-작성하지-않아도-원리는-필요하다">13.2 개발자가 직접 SQL을 작성하지 않아도 원리는 필요하다</h3>
<p>ORM은 SQL 작성을 줄여 주지만 데이터베이스의 동작까지 대신 이해해 주지는 않는다. 관계 설정이나 인덱스를 잘못 설계하면 ORM이 느린 쿼리를 대량으로 만들 수 있다.</p>
<p>다음 문제를 해결하려면 데이터베이스 지식이 필요하다.</p>
<ul>
<li>왜 같은 API가 데이터가 늘어난 뒤 갑자기 느려졌을까?</li>
<li>왜 고객 정보가 중복 저장되었을까?</li>
<li>왜 동시에 주문하면 재고가 음수가 될까?</li>
<li>왜 데이터를 삭제했는데 관련 주문 정보가 남았을까?</li>
<li>어떤 컬럼에 인덱스를 만들어야 할까?</li>
</ul>
<h3 id="133-좋은-데이터-모델이-서비스의-복잡도를-낮춘다">13.3 좋은 데이터 모델이 서비스의 복잡도를 낮춘다</h3>
<p>데이터 구조가 명확하면 프로그램 코드도 단순해진다. 반대로 데이터 모델이 모호하면 코드 곳곳에서 중복, 예외 처리, 데이터 보정 작업이 늘어난다.</p>
<h3 id="134-성능과-비용을-함께-개선할-수-있다">13.4 성능과 비용을 함께 개선할 수 있다</h3>
<p>불필요한 전체 조회, 잘못된 조인, 과도한 중복 저장은 서버 자원과 클라우드 비용을 증가시킨다. 적절한 인덱스와 쿼리, 데이터 모델은 응답 속도와 비용을 동시에 개선한다.</p>
<h3 id="135-데이터-분석과-ai의-출발점이-된다">13.5 데이터 분석과 AI의 출발점이 된다</h3>
<p>통계 분석, 추천 시스템, 머신러닝, RAG도 결국 신뢰할 수 있는 데이터를 수집하고 조회하는 과정에서 시작한다. 원본 데이터의 의미와 관계를 이해하지 못하면 좋은 분석 결과를 얻기 어렵다.</p>
<pre><code class="language-text">업무 데이터 -&gt; 데이터베이스 -&gt; 정제와 조회 -&gt; 분석/모델 학습 -&gt; 서비스 활용</code></pre>
<h3 id="136-직무-간-의사소통이-쉬워진다">13.6 직무 간 의사소통이 쉬워진다</h3>
<p>백엔드 개발자, 데이터 엔지니어, 데이터 분석가, AI 엔지니어, DBA는 모두 데이터베이스를 서로 다른 관점에서 사용한다. 테이블, 키, 트랜잭션, 인덱스, 스키마 같은 공통 개념을 이해하면 협업이 훨씬 쉬워진다.</p>

<h2 id="자주-하는-오해">자주 하는 오해</h2>
<h3 id="데이터베이스는-데이터를-저장하는-파일이다">&quot;데이터베이스는 데이터를 저장하는 파일이다&quot;</h3>
<p>데이터베이스는 값뿐 아니라 구조, 관계, 규칙을 포함한다. DBMS는 여기에 동시성, 권한, 복구 기능을 제공한다.</p>
<h3 id="nosql은-sql보다-무조건-빠르다">&quot;NoSQL은 SQL보다 무조건 빠르다&quot;</h3>
<p>속도는 데이터 구조, 쿼리, 인덱스, 데이터 양, 서버 구성에 따라 달라진다. 특정 키 조회에는 Redis가 매우 빠를 수 있지만 복잡한 관계 분석에는 관계형 DB가 더 적합할 수 있다.</p>
<h3 id="nosql에는-스키마가-없다">&quot;NoSQL에는 스키마가 없다&quot;</h3>
<p>저장 전에 고정된 스키마를 강제하지 않을 수는 있지만 데이터 구조 자체가 사라지는 것은 아니다. 구조와 검증 책임이 애플리케이션으로 이동할 수 있다.</p>
<h3 id="orm을-사용하면-sql과-데이터베이스를-몰라도-된다">&quot;ORM을 사용하면 SQL과 데이터베이스를 몰라도 된다&quot;</h3>
<p>ORM은 생산성을 높여 주지만 테이블 관계, 트랜잭션, 인덱스, 실행되는 쿼리의 비용은 개발자가 이해해야 한다.</p>
<h3 id="처음부터-여러-종류의-데이터베이스를-사용해야-한다">&quot;처음부터 여러 종류의 데이터베이스를 사용해야 한다&quot;</h3>
<p>기술이 늘어나면 운영과 장애 대응도 복잡해진다. 특별한 이유가 없다면 익숙한 관계형 DBMS 하나로 시작하고, 명확한 문제가 생겼을 때 다른 저장소를 추가하는 것이 안전하다.</p>

<h2 id="초보자를-위한-선택-연습">초보자를 위한 선택 연습</h2>
<p>다음 요구사항에는 어떤 데이터베이스가 어울릴지 생각해 보자.</p>
<h3 id="사례-1-은행-송금-내역">사례 1: 은행 송금 내역</h3>
<ul>
<li>잔액이 정확해야 한다.</li>
<li>출금과 입금이 함께 성공하거나 함께 취소되어야 한다.</li>
<li>거래 내역 사이의 관계가 중요하다.</li>
</ul>
<p><strong>관계형 DBMS</strong>가 적합하다. 강력한 트랜잭션과 데이터 무결성이 핵심이기 때문이다.</p>
<h3 id="사례-2-로그인-세션">사례 2: 로그인 세션</h3>
<ul>
<li>세션 ID로 값을 매우 빠르게 조회한다.</li>
<li>일정 시간이 지나면 자동으로 삭제되어야 한다.</li>
<li>복잡한 조인이 필요하지 않다.</li>
</ul>
<p><strong>Redis 같은 키-값 데이터베이스</strong>가 잘 맞는다.</p>
<h3 id="사례-3-옵션이-제각각인-상품-카탈로그">사례 3: 옵션이 제각각인 상품 카탈로그</h3>
<ul>
<li>노트북에는 CPU와 메모리가 있다.</li>
<li>의류에는 색상과 사이즈가 있다.</li>
<li>식품에는 유통기한과 원산지가 있다.</li>
</ul>
<p>유연한 구조가 필요하므로 <strong>문서형 데이터베이스</strong>를 고려할 수 있다. 다만 주문과 결제 데이터는 별도의 관계형 DB에 두는 방식도 가능하다.</p>
<h3 id="사례-4-친구-추천-서비스">사례 4: 친구 추천 서비스</h3>
<ul>
<li>사용자와 사용자 사이의 연결을 탐색한다.</li>
<li>친구의 친구, 최단 연결 경로를 자주 찾는다.</li>
</ul>
<p>관계를 직접 탐색하는 <strong>그래프 데이터베이스</strong>가 유리할 수 있다.</p>
<hr />
<h2 id="핵심-정리">핵심 정리</h2>
<ul>
<li>파일은 단순하지만 데이터가 커지고 사용자가 늘면 중복, 불일치, 동시 수정 문제가 발생한다.</li>
<li>데이터베이스는 데이터뿐 아니라 구조, 관계, 규칙을 함께 관리한다.</li>
<li>DBMS는 저장, 조회, 동시성 제어, 트랜잭션, 보안, 백업과 복구를 담당한다.</li>
<li>ACID는 트랜잭션의 원자성, 일관성, 격리성, 지속성을 설명하는 핵심 원칙이다.</li>
<li>관계형 DB는 테이블, 행, 열과 PK·FK를 이용해 데이터의 관계를 표현한다.</li>
<li>NoSQL은 문서, 키-값, 그래프 등 다양한 모델을 사용하며 특정 접근 패턴과 분산 처리에 활용된다.</li>
<li>정규화는 중복과 삽입·갱신·삭제 이상을 줄이며, 보통 1NF에서 3NF 순으로 검토한다.</li>
<li>ERD는 엔티티, 속성, 관계와 카디널리티를 코드 작성 전에 검증하는 설계도다.</li>
<li>개념적 모델은 업무의 대상을, 논리적 모델은 구조와 키를, 물리적 모델은 타입·인덱스·DBMS 구현을 결정한다.</li>
<li>N:M 관계는 교차 테이블로 해결하고, 약한 엔티티는 부모 키를 포함해 식별할 수 있다.</li>
<li>스키마는 데이터베이스 객체를 논리적으로 묶으며 프로젝트와 권한을 구분하는 데 사용할 수 있다.</li>
<li>RDBMS는 제품마다 타입과 함수가 다르므로 표준 SQL과 DB 전용 기능의 균형이 필요하다.</li>
<li>DDL은 구조를 만들고, DML은 데이터를 조회·추가·수정·삭제한다.</li>
<li>제약 조건은 모든 애플리케이션에 공통으로 적용되는 데이터 품질의 마지막 방어선이다.</li>
<li><code>UPDATE</code>와 <code>DELETE</code>는 대상 행을 먼저 조회하고 중요한 작업은 트랜잭션으로 보호한다.</li>
<li>데이터베이스 선택은 유행보다 데이터의 관계, 정확성, 조회 방식, 규모와 운영 역량에서 시작한다.</li>
</ul>
<hr />
<h2 id="마무리">마무리</h2>
<p>데이터베이스를 처음 공부할 때는 SQL 문법부터 외우기 쉽다. 하지만 문법보다 먼저 이해해야 할 질문은 다음과 같다.</p>
<blockquote>
<p>이 데이터는 왜 저장하며, 어떤 데이터와 연결되고, 어떤 규칙을 지켜야 하는가?</p>
</blockquote>
<p>이 질문에 답할 수 있어야 엔티티와 관계를 올바르게 설계하고 적절한 DBMS와 데이터 타입을 선택할 수 있다. Day 1에서는 데이터 구조를 만들고 기본적인 조회와 변경까지 경험했다. 다음 단계에서는 집계, 다양한 JOIN, 서브쿼리, CTE와 윈도우 함수를 이용해 여러 테이블에서 더 복잡한 의미를 찾아가게 된다.</p>

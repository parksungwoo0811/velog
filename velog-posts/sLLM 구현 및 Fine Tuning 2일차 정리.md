<p>구글의 통번역 서비스?
버티컬 도메인?</p>
<p>2일차는 1일차에 배운 sLLM과 LoRA를 실제 서비스로 연결하는 날이다. 핵심 질문은 “모델을 학습시킬까, 문서를 검색시킬까, 그리고 어떻게 빠르고 안전하게 서비스할까?”이다.</p>

<h2 id="1-1-모델-성능-향상-adapter에서-dora까지">1-1. 모델 성능 향상: Adapter에서 DoRA까지</h2>
<p>PEFT는 전체 모델을 다시 학습하지 않고, 작은 추가 파라미터만 학습하는 방법들의 묶음이다.</p>
<ul>
<li>Adapter: 모델 층 사이에 작은 모듈을 넣어 학습한다.</li>
<li>LoRA: 원래 가중치의 변화량만 낮은 차원의 행렬로 학습한다.</li>
<li>QLoRA: 모델을 4비트처럼 작게 불러오고 LoRA를 학습해 메모리를 더 아낀다.</li>
<li>DoRA: 가중치의 크기와 방향을 나누어 다루어 LoRA의 표현력을 보완한다.</li>
</ul>
<p>초보자 비유로 보면, Full Fine-Tuning은 책 전체를 다시 쓰는 일이고 LoRA는 필요한 쪽에 보충 메모를 붙이는 일이다. 보충 메모가 작아도 업무 용어, 답변 형식, 자주 쓰는 규칙을 바꾸는 데는 충분히 효과적일 수 있다.</p>
<h2 id="1-2-context--reasoning-모델이-읽을-재료를-잘-고르는-일">1-2. Context &amp; Reasoning: 모델이 읽을 재료를 잘 고르는 일</h2>
<p>모델이 답하려면 질문과 관련된 근거가 필요하다. RAG는 관련 문서를 찾아 주고, 맥락 압축은 너무 긴 문서에서 중요한 내용만 남긴다. Long Context는 문서를 가능한 한 길게 그대로 넣는 방식이다.</p>
<p>예를 들어 규정 문서가 100쪽이라면 다음 선택지가 있다.</p>
<ul>
<li>RAG: 질문과 관련된 2~3개 조항만 찾아 넣는다.</li>
<li>맥락 압축: 찾은 조항이 길면 답에 필요한 조건과 예외만 요약한다.</li>
<li>Long Context: 모델의 입력 한도가 충분하다면 긴 원문을 그대로 넣는다.</li>
</ul>
<p>문서가 길다고 무조건 많이 넣으면 좋은 것은 아니다. 입력이 길수록 비용과 지연시간이 늘고, 핵심이 묻힐 수 있다.</p>
<h2 id="1-3-추론-효율화-학습이-아니라-실행을-개선하는-일">1-3. 추론 효율화: 학습이 아니라 실행을 개선하는 일</h2>
<p>학습이 답변의 성향을 바꾸는 작업이라면, 추론 효율화는 답변을 만드는 비용과 시간을 줄이는 작업이다. 실제 서비스에서는 LoRA만 적용하는 것이 아니라, 맥락 처리와 추론 효율화를 함께 조합한다.</p>
<pre><code class="language-text">LoRA로 업무 답변 방식 조정
        +
RAG와 맥락 압축으로 근거 제공
        +
양자화 등으로 비용과 지연시간 절감
        =
실무형 sLLM 서비스</code></pre>
<hr />

<h2 id="2-1-언제-rag를-먼저-쓸까">2-1. 언제 RAG를 먼저 쓸까?</h2>
<p>규정·가격·재고·공지처럼 자주 바뀌는 정보는 RAG가 적합하다. 문서만 갱신하면 다음 답변부터 반영할 수 있기 때문이다.</p>
<p>예를 들어 “이번 달 출장 정산 기준은 무엇인가요?”라는 질문에는 최신 문서를 찾아 근거와 함께 답하는 방식이 안전하다.</p>
<h2 id="2-2-언제-fine-tuning이-필요할까">2-2. 언제 Fine-Tuning이 필요할까?</h2>
<p>도메인 특유의 표현, 일관된 답변 형식, 복잡한 질문에 대한 기본 대응 방식은 Fine-Tuning이 강점이다.</p>
<p>예를 들어 법무 보조 챗봇이 매번 “결론 → 근거 조항 → 주의사항” 순서로 답하도록 만들고 싶다면, 그런 모범 답변을 SFT 데이터로 학습시킬 수 있다.</p>

<h2 id="2-4-자주-하는-실패와-교훈">2-4. 자주 하는 실패와 교훈</h2>

<li>RAG만으로 모든 문제를 풀려 하면, 문서에 없는 판단형 질문에서 약해진다.</li>
<li>Fine-Tuning만으로 모든 문제를 풀려 하면, 자주 바뀌는 정보를 따라가기 어렵다.</li>
<li>처음부터 거대한 구조를 만들기보다, 질문 유형 하나와 문서 묶음 하나로 작은 PoC를 먼저 검증하는 편이 좋다.</li>
</ul>

<h1 id="3-peft-시나리오-도출-문제에서-기술을-고르는-순서">3. PEFT 시나리오 도출: 문제에서 기술을 고르는 순서</h1>
<p>좋은 서비스는 “LoRA를 쓰자”로 시작하지 않는다. 어떤 문제를 해결할지, 어떤 데이터를 쓸지, 무엇을 성공으로 볼지부터 정한다.</p>
<h2 id="3-1-rag만-적용한-경우와-결합한-경우">3-1. RAG만 적용한 경우와 결합한 경우</h2>
<pre><code class="language-text">기본 RAG
질문 → 문서 검색 → 원문을 모델에 전달 → 답변

결합 방식
질문 → 문서 검색 → 핵심 문맥 압축 → LoRA 적용 모델 → 답변</code></pre>
<p>기본 RAG는 근거를 전달하지만 모델 자체의 도메인 이해나 답변 형식은 바꾸지 않는다. 반면 맥락 압축과 Fine-Tuning을 결합하면, 필요한 정보는 짧고 선명하게 주고 모델은 도메인에 맞는 방식으로 답하도록 만들 수 있다.</p>
<h2 id="3-2-시나리오를-만드는-네-단계">3-2. 시나리오를 만드는 네 단계</h2>
<ol>
<li>목적 정의: 내부 보안, 도메인 전문성, 또는 둘 다 중 무엇이 우선인지 정한다.</li>
<li>데이터 구분: 검색용 원문 문서와 학습용 질문·답변 데이터를 따로 준비한다.</li>
<li>기법 배분: 맥락 압축 중심인지, 파라미터 학습 중심인지 결정한다.</li>
<li>검증 기준: 정확도, 근거 제시, 지연시간, 비용 중 무엇을 측정할지 미리 정한다.</li>
</ol>
<h2 id="3-3-예시-계약서-검토-보조-서비스">3-3. 예시: 계약서 검토 보조 서비스</h2>
<p>가상의 계약서 검토 보조 서비스를 생각해 보자.</p>
<ul>
<li>목적: 위험 조항을 놓치지 않고 검토를 돕는다.</li>
<li>데이터: 계약서 조항, 조항 요약, 위험 유형별 안내문을 준비한다.</li>
<li>맥락 압축: 긴 계약서에서 관련 조항만 뽑아 짧게 정리한다.</li>
<li>LoRA SFT: 법무 용어, 답변 형식, 검토 기준을 학습한다.</li>
<li>검증: 위험 조항 탐지 정확도, 근거 제시 여부, 평균 응답시간을 본다.</li>
</ul>
<p>여기서 AI의 답변은 최종 법률 판단이 아니라 검토를 돕는 초안이어야 한다. 고위험 의사결정은 담당 전문가의 검토 절차를 유지해야 한다.</p>

<h1 id="4-sllm-서비스-설계-검색-압축-생성의-역할을-나눈다">4. sLLM 서비스 설계: 검색, 압축, 생성의 역할을 나눈다</h1>
<p>교재의 기본 서비스 구조는 Qwen2.5-1.5B-Instruct를 생성 모델로, BGE-M3를 임베딩 모델로 사용한다.</p>
<pre><code class="language-text">사용자 질문
    ↓
BGE-M3가 질문을 의미 벡터로 변환
    ↓
벡터 DB에서 관련 문서 검색
    ↓
맥락 압축으로 핵심 조건·예외만 정리
    ↓
LoRA가 적용된 Qwen이 답변 생성
    ↓
사용자에게 응답</code></pre>
<h2 id="4-1-각-구성-요소가-하는-일">4-1. 각 구성 요소가 하는 일</h2>
<ul>
<li>임베딩: 문장 의미를 숫자 벡터로 바꿔 유사한 질문과 문서를 찾는다.</li>
<li>벡터 DB: 문서 벡터를 저장하고 가장 가까운 문서 조각을 검색한다.</li>
<li>맥락 압축: 검색된 문서 중 답에 필요한 핵심만 남긴다.</li>
<li>Qwen: 문맥과 질문을 바탕으로 자연어 답변을 만든다.</li>
<li>LoRA Adapter: Qwen이 특정 도메인의 용어와 응답 방식에 더 잘 맞도록 조정한다.</li>
</ul>
<h2 id="4-2-모델-선택은-업무-환경을-기준으로-한다">4-2. 모델 선택은 업무 환경을 기준으로 한다</h2>
<p>Qwen2.5-1.5B-Instruct는 비교적 작은 크기, 다국어 지원, 활발한 생태계가 장점이다. 한국어 비중이 매우 큰 환경에서는 한국어·영어 균형에 강점을 둔 다른 공개 모델도 비교 후보가 될 수 있다.</p>
<p>중요한 것은 “가장 큰 모델”이 아니라 다음 조건을 만족하는 모델이다.</p>
<ul>
<li>목표 언어에서 답변 품질이 충분한가?</li>
<li>사용할 장비의 메모리와 지연시간에 맞는가?</li>
<li>내부 운용과 라이선스 조건에 맞는가?</li>
<li>RAG, LoRA, 양자화 같은 필요한 도구와 잘 연결되는가?</li>
</ul>
<h2 id="4-3-벡터-db를-고르는-기준">4-3. 벡터 DB를 고르는 기준</h2>
<p>벡터 DB는 이름보다 운영 조건을 먼저 본다.</p>
<ul>
<li>완전 내부 설치가 가능한가?</li>
<li>Dense 검색과 Sparse 검색을 함께 쓸 수 있는가?</li>
<li>문서 유형·부서·작성일 같은 메타데이터로 필터링할 수 있는가?</li>
<li>작은 실험에는 가볍고, 서비스 확대 시에는 확장 가능한가?</li>
</ul>
<p>작은 실습에서는 단순 인덱스로 시작할 수 있지만, 실제 서비스에서는 권한 관리와 문서 갱신 정책도 설계해야 한다.</p>

<h2 id="5-1-context-compression">5-1. Context Compression</h2>
<p>검색 결과를 모두 붙이는 대신, 답변에 필요한 내용만 압축하는 방법이다. 예를 들어 여러 문서에서 “신청 기한”, “승인자”, “예외 조건”만 뽑아 모델에 전달할 수 있다.</p>
<p>압축은 토큰 수와 비용을 줄이는 장점이 있지만, 너무 과하면 중요한 예외가 빠질 수 있다. 그래서 실제 서비스에서는 원문과 압축 결과를 표본으로 비교 검증해야 한다.</p>
<h2 id="5-2-long-context">5-2. Long Context</h2>
<p>Long Context는 모델이 긴 문서를 한 번에 읽도록 입력 길이를 늘리는 방식이다. 교재는 YaRN 같은 위치 정보 확장 설정을 예시로 든다.</p>
<p>장점은 검색·요약 과정 없이 넓은 문맥을 볼 수 있다는 점이다. 단점은 긴 입력만큼 메모리와 시간이 더 들고, 모든 모델과 환경에서 같은 품질을 보장하지 않는다는 점이다.</p>
<h2 id="5-3-qlora">5-3. QLoRA</h2>
<p>QLoRA는 모델을 낮은 정밀도로 불러 메모리를 줄이고 LoRA Adapter를 학습하는 방식이다. GPU 메모리가 제한된 환경에서 더 큰 모델을 다루는 데 유용하다.</p>
<p>다만 양자화 설정과 지원 하드웨어에 따라 동작 방식이 달라진다. 따라서 코드에서 사용 장치가 CUDA인지, Apple Silicon MPS인지, CPU인지 확인하고 그에 맞는 경로를 선택해야 한다.</p>

<h1 id="6-추론-효율화-같은-답을-더-빠르고-가볍게-만든다">6. 추론 효율화: 같은 답을 더 빠르고 가볍게 만든다</h1>
<p>추론 효율화는 모델이 답을 생성할 때의 메모리와 시간을 줄이는 기술이다. 모델 품질, 맥락 처리와는 다른 세 번째 축이지만 실서비스에서는 함께 적용한다.</p>
<h2 id="6-1-quantization">6-1. Quantization</h2>
<p>양자화는 가중치와 활성값의 숫자 정밀도를 낮추는 방법이다. FP16이나 FP32 대신 INT8, INT4 등을 사용해 메모리와 연산량을 줄인다.</p>

<th>주의점</th>
</tr>
</thead>
<tbody><tr>
<td>FP16</td>
<td align="right">100% 기준</td>
<td align="right">1배 기준</td>

<tr>

<p>PTQ는 학습 후에 양자화하는 방식이라 적용이 간단하다. QAT는 학습 중 양자화를 고려해 품질 손실을 줄이려는 방식이다.</p>
<h2 id="6-2-moe-필요한-전문가만-켠다">6-2. MoE: 필요한 전문가만 켠다</h2>
<p>MoE는 입력마다 모든 파라미터를 계산하지 않고, Router가 일부 Expert만 골라 쓰는 구조다.</p>
<pre><code class="language-text">입력 토큰 → Router → 선택된 Expert 몇 개만 계산 → 결과 결합</code></pre>
<p>전체 모델은 클 수 있지만 한 번의 답변에서 실제로 계산하는 부분은 작게 유지할 수 있다. 다만 Router와 Expert 분배를 안정적으로 운영하는 난이도가 있다.</p>
<h2 id="6-3-speculative-decoding-작은-모델이-초안을-쓰고-큰-모델이-검토한다">6-3. Speculative Decoding: 작은 모델이 초안을 쓰고 큰 모델이 검토한다</h2>
<p>작고 빠른 Draft 모델이 다음 토큰들을 미리 제안하고, 더 정확한 Target 모델이 여러 후보를 한 번에 검증한다. 맞는 후보는 바로 채택하고 틀린 지점부터 Target 모델이 다시 생성한다.</p>
<p>핵심 장점은 최종 품질 기준을 Target 모델에 두면서 생성 속도를 높일 수 있다는 점이다.</p>
<h2 id="6-4-kv-cache-최적화">6-4. KV Cache 최적화</h2>
<p>Transformer는 다음 토큰을 만들 때 이미 읽은 토큰의 Key와 Value를 다시 계산하지 않도록 캐시에 저장한다. 긴 대화에서는 이 캐시가 커져 메모리 병목이 될 수 있다.</p>
<ul>
<li>PagedAttention: 캐시를 페이지 단위로 관리해 메모리 단편화를 줄인다.</li>
<li>MQA: 여러 Query가 Key와 Value를 공유해 캐시 크기를 줄인다.</li>
<li>GQA: 완전 공유와 기존 방식의 중간 형태로, 최근 모델에서 자주 사용된다.</li>
</ul>

<h1 id="7-peft-응용-실습-전체-파이프라인을-api-서비스로-조립한다">7. PEFT 응용 실습: 전체 파이프라인을 API 서비스로 조립한다</h1>
<p>마지막 파트의 목표는 Qwen, BGE-M3, LoRA Adapter를 하나의 HR 문서 Q&amp;A 서비스로 묶고 FastAPI로 제공하는 것이다.</p>
<h2 id="7-1-최종-파이프라인">7-1. 최종 파이프라인</h2>
<pre><code class="language-text">사용자 질문
    ↓
RAG 검색 선택
    ↓
Context Compression 또는 Long Context 선택
    ↓
LoRA 또는 QLoRA가 적용된 Qwen 생성
    ↓
필요하면 4비트 양자화로 추론 최적화
    ↓
FastAPI Endpoint를 통해 응답 반환</code></pre>
<p>여기서 RAG는 문서를 찾고, 맥락 압축은 찾은 문서를 줄이며, LoRA는 도메인에 맞는 답변 성향을 만든다. 이 세 역할을 섞어 생각하지 않는 것이 중요하다.</p>

<h2 id="7-3-lora-adapter-자동-연결-정책">7-3. LoRA Adapter 자동 연결 정책</h2>
<p>서비스는 Adapter 파일이 정상인지 먼저 검사해야 한다. 설정에 따라 다음처럼 동작하게 만들 수 있다.</p>
<ul>
<li>auto: 정상 Adapter가 있으면 LoRA 모델을 쓰고, 없으면 Base Model로 동작한다.</li>
<li>base: Adapter가 있어도 Base Model만 쓴다.</li>
<li>lora: Adapter가 없으면 오류로 처리한다.</li>
</ul>
<p>초기 실습에서는 auto가 편하지만, 운영 환경에서는 의도치 않게 Base Model로 바뀌지 않도록 모니터링과 상태 확인이 필요하다.</p>
<h2 id="7-4-api-실행과-통합-테스트">7-4. API 실행과 통합 테스트</h2>
<p>FastAPI는 웹 API를 제공하는 프레임워크다. 서비스가 실행되면 문서 업로드, 검색, 통합 질의 같은 기능을 API로 테스트할 수 있다.</p>
<p>테스트할 때는 다음을 확인한다.</p>
<ul>
<li>LoRA 적용 전후에 같은 질문의 답이 실제로 개선됐는가?</li>
<li>맥락 압축 뒤에 중요한 조건과 예외가 사라지지 않았는가?</li>
<li>평균 응답시간이 서비스 목표를 만족하는가?</li>
<li>검색 결과 없음, 입력 토큰 초과 같은 예외를 안전하게 처리하는가?</li>
</ul>

<h1 id="마무리-2일차의-핵심-한-문장">마무리: 2일차의 핵심 한 문장</h1>
<p>sLLM 서비스의 품질은 모델 하나로 결정되지 않는다. 파라미터를 어떻게 학습시킬지, 문맥을 어떻게 찾아서 전달할지, 추론을 어떻게 효율화할지의 세 축을 업무 목적에 맞게 함께 설계해야 한다.</p>
<p>마지막으로 실제 운영에서는 성능 저하, 문서 변경, 오류 응답을 계속 관찰해야 한다. 사람이 모든 답변을 수동으로 감시하기보다, 평가·로그·재학습 판단을 운영 체계로 연결하는 방향이 이후 AIOps와 Agentic AI 주제로 이어진다.</p>

<blockquote>
<p>이 글은 모델 개발을 처음 접하는 학습자가 <strong>문제 정의부터 데이터 준비, Feature Engineering, 학습·최적화, 평가, 해석, 운영 모니터링까지</strong> 한 번에 큰 그림을 잡을 수 있도록 정리한 입문 자료입니다.  </p>
</blockquote>
<hr />
<h2 id="먼저-보는-전체-지도">먼저 보는 전체 지도</h2>
<p>머신러닝 프로젝트는 단순히 알고리즘을 골라 <code>fit()</code>을 실행하는 일이 아니다. 실제 흐름은 다음과 같다.</p>
<pre><code class="language-text">비즈니스 문제 이해
  → 데이터 준비
  → 데이터 전처리와 탐색
  → Feature Engineering
  → 모델 학습과 최적화
  → 모델 평가
  → 모델 해석
  → 배포와 모니터링
  → 필요 시 재학습 또는 재구축</code></pre>
<p>이 과정은 일직선이 아니다. 평가 결과가 나쁘면 Feature Engineering으로 돌아가고, 운영 중 데이터가 달라지면 다시 학습하거나 모델 전체를 다시 설계한다. 즉, <strong>모델 개발은 반복되는 순환 과정</strong>이다.</p>

<h1 id="1-분석-프로세스-이해">1. 분석 프로세스 이해</h1>
<h2 id="11-데이터-분석-과제는-여러-축으로-나뉜다">1.1 데이터 분석 과제는 여러 축으로 나뉜다</h2>
<p>분석 과제를 이해하려면 다음 네 가지 질문을 해보자.</p>
<ol>
<li><strong>데이터는 어떤 형태인가?</strong><ul>
<li>정형 데이터: 행과 열이 뚜렷한 표 형태. 예: 고객 테이블, 거래 내역</li>
<li>비정형 데이터: 고정된 표 구조가 없는 텍스트, 이미지, 음성 등</li>
</ul>
</li>
<li><strong>정답이 있는가?</strong><ul>
<li>지도학습: 정답 <code>Y</code>가 있다. 예: 과거 이탈 여부로 미래 이탈 예측</li>
<li>비지도학습: 정답 없이 구조를 찾는다. 예: 비슷한 고객끼리 군집화</li>
</ul>
</li>
<li><strong>어떤 기법을 쓰는가?</strong><ul>
<li>통계 분석, 머신러닝, 딥러닝, 규칙 기반 시스템 등을 선택할 수 있다.</li>
</ul>
</li>
<li><strong>무엇을 위해 분석하는가?</strong><ul>
<li>단순 예측만이 아니라 성능 평가와 결과 해석까지 포함해야 한다.</li>
</ul>
</li>
</ol>
<p>예를 들어 “고객 문의 내용을 자동 분류하자”라는 과제는 비정형 텍스트를 다루는 지도학습 분류 문제다. 반면 “고객을 비슷한 소비 패턴끼리 묶자”는 정형 데이터를 활용한 비지도학습 문제다.</p>
<h2 id="12-데이터-분석의-표준적인-단계">1.2 데이터 분석의 표준적인 단계</h2>
<h3 id="1단계-비즈니스-이해">1단계: 비즈니스 이해</h3>
<p>문제를 기술 용어가 아니라 업무 언어로 분명하게 정의한다.</p>
<ul>
<li>해결하려는 문제는 무엇인가?</li>
<li>결과를 어디에 사용할 것인가?</li>
<li>성공을 무엇으로 판단할 것인가?</li>
<li>잘못된 예측은 어떤 비용을 만드는가?</li>
</ul>
<p>예를 들어 “고객 이탈을 예측한다”만으로는 부족하다. 이탈이 계약 해지인지, 일정 기간 미납인지, 서비스 미접속인지부터 합의해야 한다. 이 정의가 달라지면 <code>Y</code> 자체가 달라진다.</p>
<h3 id="2단계-데이터-준비">2단계: 데이터 준비</h3>
<p>필요한 데이터를 수집·통합하고 탐색적 데이터 분석(EDA)과 품질 점검을 수행한다.</p>
<ul>
<li>필요한 원천 데이터 확인</li>
<li>여러 시스템의 데이터 결합</li>
<li>결측치, 이상치, 중복, 단위 오류 확인</li>
<li>변수 분포와 관계 탐색</li>
</ul>
<h3 id="3단계-데이터-전처리">3단계: 데이터 전처리</h3>
<p>모델이 읽을 수 있는 형태로 데이터를 정제하고 변환한다.</p>
<ul>
<li>결측치 대체</li>
<li>이상치 처리</li>
<li>숫자 크기 조정(Scaling)</li>
<li>범주형 변수 인코딩</li>
<li>파생변수 생성</li>
<li>필요 변수 선택</li>
</ul>
<h3 id="4단계-모델링">4단계: 모델링</h3>
<p>문제에 알맞은 통계·머신러닝·딥러닝 알고리즘을 고르고 학습한다. 한 번 학습하고 끝나는 것이 아니라 여러 설정을 비교하며 최적화한다.</p>
<h3 id="5단계-모델-평가">5단계: 모델 평가</h3>
<p>성능 지표로 예측력을 확인하고, 결과가 업무 목적에 맞는지 해석한다. 이 단계의 산출물은 단순한 점수표가 아니라 <strong>어떤 모델을 왜 선택해야 하는가에 대한 근거</strong>다.</p>
<h3 id="6단계-모델-적용과-운영">6단계: 모델 적용과 운영</h3>
<p>운영 시스템에 모델을 배포하고 예측 결과를 실제 업무에 연결한다. 이후에는 데이터와 성능 변화를 계속 모니터링한다.</p>
<h2 id="13-시나리오로-이해하는-분석-흐름-고객-이탈-예측">1.3 시나리오로 이해하는 분석 흐름: 고객 이탈 예측</h2>
<h3 id="문제-정의">문제 정의</h3>
<p>“어떤 고객이 미래에 이탈할 것인가?”를 예측한다고 하자. 먼저 이탈 기준을 구체화한다.</p>
<ul>
<li>계약 해지</li>
<li>일정 기간 요금 미납</li>
<li>장기간 서비스 미사용</li>
</ul>
<h3 id="target과-feature-정의">Target과 Feature 정의</h3>
<ul>
<li>Target <code>Y</code>: 미래 기간에 이탈했는지 여부</li>
<li>Feature <code>X</code>: 성별, 연령, 직업, 가입 기간, 납입 금액, 미납 경험, 접속 횟수 등</li>
</ul>
<p>모델은 결국 <code>X → Y</code>의 관계, 즉 입력을 정답으로 연결하는 함수나 규칙을 찾는다.</p>
<h3 id="분석-요건-정의">분석 요건 정의</h3>
<ul>
<li>어떤 고객을 분석 대상에 넣을 것인가?</li>
<li>어느 기간의 데이터를 사용할 것인가?</li>
<li>이탈을 얼마나 먼 미래까지 예측할 것인가?</li>
<li>분류 모델 중 어떤 후보를 비교할 것인가?</li>
</ul>
<h2 id="14-관찰-기간-예측-기간-기준일">1.4 관찰 기간, 예측 기간, 기준일</h2>
<p>시간이 있는 문제에서 가장 중요한 설계 중 하나다.</p>
<pre><code class="language-text">과거 -------------------------------- 기준일 ---------------- 미래
          관찰 기간                              예측 기간
       Feature X 생성                           Target Y 판정</code></pre>
<ul>
<li><strong>관찰 기간(Observation Window)</strong>: Feature를 모으는 과거 구간</li>
<li><strong>예측 기간(Target Window)</strong>: Target 발생 여부를 판단하는 미래 구간</li>
<li><strong>기준일(Reference Date)</strong>: 과거와 미래를 가르는 예측 시점</li>
</ul>
<p>예를 들어 기준일 이전 3년의 거래 데이터를 보고, 기준일 이후 6개월 안에 이탈할지를 예측할 수 있다.</p>
<blockquote>
<p>중요한 원칙: 예측 시점 이후에만 알 수 있는 정보는 Feature에 넣으면 안 된다. 미래 정보가 섞이면 Data Leakage가 발생한다.</p>
</blockquote>

<p>같은 예측·분류 문제라도 데이터의 형태, 규모, 처리 방식에 따라 최적 전략이 달라진다.</p>

<li>카드 결제 순간에 승인 여부를 정해야 한다면 수십 밀리초 안에 계산 가능한 Feature와 모델이 필요하다.</li>
</ul>
<p>정확도가 조금 높은 모델보다 <strong>제시간에 안정적으로 응답하는 모델</strong>이 실무에서는 더 나을 수 있다.</p>
<h2 id="22-데이터-준비는-가장-많은-시간이-드는-단계다">2.2 데이터 준비는 가장 많은 시간이 드는 단계다</h2>
<p>모델링 프로젝트에서는 알고리즘 개발보다 데이터 탐색·정제·변환에 더 많은 시간이 드는 경우가 흔하다. 이유는 다음과 같다.</p>
<ul>
<li>시스템마다 고객 ID 형식이 다르다.</li>
<li>같은 금액도 원, 천 원, 달러 등 단위가 다를 수 있다.</li>
<li>누락값의 의미가 단순 실수인지 “해당 없음”인지 구분해야 한다.</li>
<li>데이터가 업무 정의와 맞는지 담당자 확인이 필요하다.</li>
</ul>
<p>즉, <strong>비즈니스 문제를 정확히 정의하는 일은 가장 중요하고, 데이터를 준비하는 일은 가장 오래 걸린다.</strong></p>
<h2 id="23-데이터-구축-프로세스">2.3 데이터 구축 프로세스</h2>
<pre><code class="language-text">원천 데이터
  → 수집
  → 정제(Cleaning)
  → 변환(Transformation)
  → 통합(Integration)
  → Target·Feature 생성
  → 분석용 Master 데이터셋
  → EDA와 Feature Engineering
  → 모델 학습·평가</code></pre>
<p>원천에는 고객, 상품, 계약, 거래, 상담, 온라인 행동 등 여러 테이블이 있을 수 있다. 이를 분석 기준에 맞게 합치고 <code>X</code>와 <code>Y</code>가 한 행에 정리된 분석용 데이터셋을 만든다.</p>
<h2 id="24-데이터-품질-garbage-in-garbage-out">2.4 데이터 품질: Garbage In, Garbage Out</h2>
<p>“쓰레기가 들어가면 쓰레기가 나온다”는 원칙이다. 모델이 아무리 좋아도 입력 데이터가 틀리면 결과도 믿을 수 없다.</p>
<h3 id="품질-문제의-연쇄-효과">품질 문제의 연쇄 효과</h3>
<pre><code class="language-text">부정확한 데이터 추출
  → 탐색 단계에서 오류 수정 비용 증가
  → 오류를 놓친 채 학습
  → 모델 성능 저하
  → 잘못된 의사결정</code></pre>
<h3 id="실무-체크리스트">실무 체크리스트</h3>
<ul>
<li>값의 허용 범위를 벗어나지 않았는가? 예: 나이 <code>-3</code></li>
<li>단위가 통일됐는가? 예: 원과 천 원 혼용</li>
<li>날짜 순서가 논리적인가? 예: 해지일이 가입일보다 빠름</li>
<li>ID가 중복되거나 누락되지 않았는가?</li>
<li>Target이 업무 정의와 일치하는가?</li>
<li>수집 시점이 예측 시점보다 뒤인 정보가 섞이지 않았는가?</li>
</ul>
<h2 id="25-preparation-preprocessing-wrangling의-차이">2.5 Preparation, Preprocessing, Wrangling의 차이</h2>
<p>현장에서는 경계가 조금씩 다르게 쓰이지만 다음처럼 이해하면 편하다.</p>
<h3 id="data-preparation">Data Preparation</h3>
<p>데이터 접근부터 분석용 데이터셋을 만드는 전 과정을 포괄하는 가장 넓은 개념이다.</p>
<h3 id="data-preprocessing">Data Preprocessing</h3>
<p>모델이 사용할 수 있도록 정제·축소·변환하는 준비 과정이다. 결측치 처리, 이상치 처리, 인코딩, Scaling 등이 포함된다.</p>
<h3 id="data-wrangling">Data Wrangling</h3>
<p>분석 과정 중 필요할 때 반복적으로 데이터를 가공하는 작업이다. Sampling, 분할, Binning, 집계, 형식 변경 등이 포함될 수 있다.</p>
<blockquote>
<p>정리하면 Preparation이 큰 우산이고, Preprocessing은 모델 입력을 만드는 핵심 준비 작업이며, Wrangling은 분석 중 반복되는 실무적 가공에 가깝다.</p>
</blockquote>
<hr />
<h1 id="3-feature-engineering">3. Feature Engineering</h1>
<h2 id="31-feature-engineering이란">3.1 Feature Engineering이란?</h2>
<p>원본 데이터를 모델 성능에 도움이 되는 형태의 Feature로 가공하는 모든 과정이다.</p>
<pre><code class="language-text">Raw Data → Feature → Model → Insight
              ↑
      Feature Engineering</code></pre>
<p>좋은 Feature는 복잡한 모델 하나보다 더 큰 성능 개선을 만들기도 한다. 모델은 주어진 입력 안에서만 규칙을 배우므로, 문제를 잘 표현하는 입력을 만드는 일이 중요하다.</p>
<p>예를 들어 생년월일 자체보다 <strong>현재 나이</strong>, 거래 날짜 목록보다 <strong>최근 30일 거래 횟수</strong>, 대출금과 소득 각각보다 <strong>소득 대비 부채 비율</strong>이 더 직접적인 신호가 될 수 있다.</p>
<h2 id="32-모델-개발-pipeline에서의-위치">3.2 모델 개발 Pipeline에서의 위치</h2>
<pre><code class="language-text">문제 정의 → 데이터 수집 → EDA → Feature Engineering → 모델링 → 평가
                                  ↑                 ↓
                                  └──── 반복 ──────┘</code></pre>
<p>데이터 전처리는 데이터를 분석 가능한 상태로 만드는 과정이고, Feature Engineering은 그중에서도 <strong>모델 성능 향상에 초점을 둔 작업</strong>이다.</p>
<h2 id="33-feature-extraction과-feature-creation">3.3 Feature Extraction과 Feature Creation</h2>
<h3 id="feature-transformation-기계적·알고리즘-기반-변환">Feature Transformation: 기계적·알고리즘 기반 변환</h3>
<p>데이터의 통계적·수학적 구조를 이용해 자동으로 변환한다.</p>
<ul>
<li>결측치 대체</li>
<li>이상치 처리</li>
<li>표준화·정규화</li>
<li>Min/Max Scaling</li>
<li>범주형 변수 One-Hot Encoding</li>
<li>날짜 분해: 연, 월, 요일, 시간대</li>
<li>경과 시간 계산</li>
<li>텍스트 Tokenization·Vectorization</li>
</ul>
<h3 id="feature-creation-도메인-지식-기반-파생변수-생성">Feature Creation: 도메인 지식 기반 파생변수 생성</h3>
<p>업무를 이해해야 만들 수 있는 의미 있는 변수를 설계한다.</p>
<ul>
<li>가입 기간 = 기준일 - 가입일</li>
<li>소득 대비 부채 비율 = 부채 / 소득</li>
<li>최근 구매 후 경과일</li>
<li>최근 30일 평균 사용량</li>
<li>이전 7일 대비 사용량 증감률</li>
</ul>
<p>이 영역은 알고리즘만으로 해결하기 어렵고 도메인 지식과 창의성이 중요하다.</p>

<h3 id="aggregation-예시">Aggregation 예시</h3>

<ul>

<li>범주형: 최빈값, 고유 범주 수</li>
</ul>
<h2 id="35-차원의-저주">3.5 차원의 저주</h2>
<p>Feature 수, 즉 차원이 늘면 공간이 매우 빠르게 커진다. 같은 밀도로 공간을 채우려면 필요한 데이터 수가 기하급수적으로 증가한다.</p>
<p>쉽게 말해 1차원 선에서는 몇 개 점만 있어도 가까운 이웃이 있지만, 100차원 공간에서는 데이터가 대부분 서로 멀리 떨어진다. 데이터가 부족한데 Feature만 많으면 모델은 빈 공간의 우연한 패턴까지 외워 버린다.</p>
<p>그 결과:</p>
<ul>
<li>Train 성능은 높지만 Test 성능은 낮아진다.</li>
<li>학습 시간과 메모리 사용량이 늘어난다.</li>
<li>결과 해석이 어려워진다.</li>
</ul>
<p>대응 방법은 <strong>Feature Selection</strong>과 <strong>차원 축소</strong>다.</p>
<h2 id="36-feature-selection의-목적과-단계">3.6 Feature Selection의 목적과 단계</h2>
<p>목적은 단순히 변수 수를 줄이는 데 있지 않다.</p>
<ul>
<li>학습 시간 단축</li>
<li>과적합 완화</li>
<li>모델 안정성 향상</li>
<li>해석 가능성 향상</li>
</ul>
<p>대표적인 절차는 다음과 같다.</p>
<ol>
<li><strong>최초 정의</strong>: 도메인 지식, 경험, 사례로 후보 Feature를 넓게 만든다.</li>
<li><strong>신뢰성 검증</strong>: 결측률, 오류, 수집 지속성 등 데이터 품질을 확인한다.</li>
<li><strong>중요도 검증</strong>: 통계·ML 분석으로 예측력이 낮은 변수를 거른다.</li>
<li><strong>논리성 검증</strong>: 업무 관점에서 영향 방향과 크기가 납득 가능한지 본다.</li>
<li><strong>최종 선정</strong>: 성능·안정성·운영 가능성을 함께 고려해 확정한다.</li>
</ol>
<h2 id="37-logical-trend-분석">3.7 Logical Trend 분석</h2>
<p>Feature 값이 변할 때 Target이 변하는 방향과 크기가 업무적으로 자연스러운지 확인하는 과정이다.</p>
<p>예를 들어 연체 횟수가 늘수록 부도 위험이 대체로 증가한다면 논리적이다. 그런데 어떤 달에는 증가하고, 다음 달에는 감소하며, 전체로 합치면 다시 증가하는 등 관계가 심하게 흔들린다면 안정성이 낮은 Feature일 수 있다.</p>
<p>확인할 세 가지는 다음과 같다.</p>
<ul>
<li><strong>변별력</strong>: Target을 잘 구분하는가?</li>
<li><strong>논리성</strong>: 영향 방향이 업무 상식과 맞는가?</li>
<li><strong>안정성</strong>: 기간이나 집단이 달라져도 관계가 유지되는가?</li>
</ul>
<p>Robust한 모델은 Robust한 Feature에서 출발한다.</p>
<hr />
<h1 id="4-모델-학습-및-최적화">4. 모델 학습 및 최적화</h1>
<h2 id="41-모델-lifecycle">4.1 모델 Lifecycle</h2>
<h3 id="개발-단계">개발 단계</h3>
<pre><code class="language-text">원천 데이터 → 가공 데이터(X, Y) → 데이터 분할
  → Train 학습 → 학습 모델
  → Test 평가 → 후보 비교 → 최종 모델 선택</code></pre>
<h3 id="운영-단계">운영 단계</h3>
<pre><code class="language-text">신규 데이터 → 개발 때와 같은 가공 로직 → 최종 모델 적용
  → 예측값 생성 → 모니터링 → 필요 시 재학습·재개발</code></pre>
<p>개발과 운영에서 Feature 계산 방식이 다르면 같은 모델도 엉뚱한 결과를 낸다. 전처리 로직까지 함께 저장·배포해야 하는 이유다.</p>
<h2 id="42-data-partition-train-validation-test">4.2 Data Partition: Train, Validation, Test</h2>
<p>데이터를 나누는 이유는 아직 보지 못한 데이터에서 잘 작동하는지 확인하기 위해서다.</p>
<table>
<thead>
<tr>
<th>데이터셋</th>
<th>역할</th>
<th>시험 비유</th>
</tr>
</thead>
<tbody><tr>
<td>Train</td>
<td>모델 파라미터 학습</td>
<td>교과서와 연습문제</td>
</tr>
<tr>
<td>Validation</td>
<td>하이퍼파라미터와 모델 후보 선택</td>
<td>모의고사</td>
</tr>
<tr>
<td>Test</td>
<td>최종 일반화 성능을 한 번 평가</td>
<td>실제 시험</td>
</tr>
</tbody></table>
<p>일반적인 예시는 Train/Test를 8:2 또는 7:3으로, Train/Validation/Test를 6:2:2로 나누는 것이다. 비율은 데이터 규모와 목적에 따라 달라질 수 있다.</p>
<blockquote>
<p>Test는 모델 선택에 반복 사용하면 안 된다. 답을 보면서 공부하는 것처럼 Test에 맞춰진 모델이 되기 때문이다.</p>
</blockquote>
<h2 id="43-hold-out과-cross-validation">4.3 Hold-Out과 Cross Validation</h2>
<h3 id="hold-out">Hold-Out</h3>
<p>데이터를 한 번 나누는 방식이다.</p>
<ul>
<li><strong>Random Split</strong>: 무작위 분할. 일반적인 독립 데이터에 사용</li>
<li><strong>Time-series Split</strong>: 과거로 학습하고 미래로 검증. 시간 순서가 있는 문제에 사용</li>
</ul>
<p>시계열을 무작위로 섞으면 미래 정보가 과거 학습에 들어갈 수 있으므로 시간 순서를 지켜야 한다.</p>
<h3 id="cross-validation">Cross Validation</h3>
<p>데이터를 <code>K</code>개 묶음으로 나누고, 한 묶음씩 Validation으로 바꾸며 <code>K</code>번 학습한다. 성능 평균으로 모델을 비교하므로 한 번의 우연한 분할에 덜 흔들린다.</p>
<p>단점은 <code>K</code>번 학습하므로 계산량이 커진다는 점이다. 최종 Test는 별도로 남겨 두어야 한다.</p>
<h3 id="k-fold">K-Fold</h3>
<p>전체 데이터를 비슷한 크기의 <code>K</code>개 Fold로 단순 분할한다. 연속값을 예측하는 회귀 문제에 흔히 쓴다.</p>
<h3 id="stratified-k-fold">Stratified K-Fold</h3>
<p>각 Fold에서 클래스 비율이 원본과 비슷하게 유지되도록 나눈다. 불량 2%, 정상 98%처럼 클래스 불균형이 있는 분류 문제에 적합하다.</p>
<h2 id="44-sampling-방법">4.4 Sampling 방법</h2>
<h3 id="random-sampling">Random Sampling</h3>
<p>모집단의 각 샘플이 뽑힐 확률을 같게 하는 단순 무작위 추출이다.</p>
<h3 id="partitioned-sampling">Partitioned Sampling</h3>
<p>최종 평가는 전체 Test로 하고, 학습 비용을 줄이기 위해 Train에서만 일부를 Sampling한다. 대규모 데이터에서 실험 속도를 높일 때 유용하다.</p>
<h3 id="over-sampling">Over Sampling</h3>
<p>작은 클래스를 늘려 큰 클래스와 균형을 맞춘다.</p>
<ul>
<li>Random Over Sampling: 소수 클래스를 그대로 복제</li>
<li>SMOTE: 소수 클래스의 가까운 이웃 사이에서 합성 샘플 생성</li>
</ul>
<p>장점은 소수 클래스 정보를 보존한다는 것이고, 단순 복제는 과적합 위험이 있다.</p>
<h3 id="under-sampling">Under Sampling</h3>
<p>큰 클래스를 줄여 작은 클래스와 균형을 맞춘다. 빠르지만 다수 클래스의 중요한 정보를 버릴 수 있다.</p>
<p>예시는 사기/정상 거래, 이탈/유지, 불량/정상처럼 관심 클래스가 매우 적은 경우다.</p>
<blockquote>
<p>Sampling은 원칙적으로 Train에만 적용한다. Validation과 Test의 실제 분포를 바꾸면 운영 성능을 왜곡할 수 있다.</p>
</blockquote>
<h2 id="45-최적화란">4.5 최적화란?</h2>
<p>주어진 조건에서 가장 좋은 결과를 얻도록 방법을 조정하는 과정이다. 머신러닝에서는 하이퍼파라미터, 데이터, Feature, 알고리즘 등을 조정해 다음을 추구한다.</p>
<ul>
<li>성능 향상</li>
<li>새 데이터에 대한 일반화 향상</li>
<li>학습 속도와 자원 효율 향상</li>
</ul>
<p>최적화는 점수 하나를 무조건 가장 크게 만드는 일이 아니다. 운영 속도, 설명 가능성, 안정성, 비용도 함께 고려해야 한다.</p>

<h3 id="ensemble-간단-비교">Ensemble 간단 비교</h3>
<ul>
<li><strong>Bagging</strong>: 여러 모델을 독립적으로 학습해 평균·투표. 예: Random Forest</li>
<li><strong>Boosting</strong>: 이전 모델의 실수를 다음 모델이 보완. 예: XGBoost, LightGBM</li>
<li><strong>Stacking</strong>: 서로 다른 모델의 예측값을 또 다른 메타 모델의 입력으로 사용</li>
</ul>
<h2 id="47-parameter와-hyperparameter">4.7 Parameter와 Hyperparameter</h2>

<tr>

<p>Parameter는 모델 <strong>안에서 학습되는 값</strong>이고, Hyperparameter는 모델 <strong>바깥에서 학습 방식을 조정하는 값</strong>이다. 하이퍼파라미터에는 언제나 절대적인 최댓값이 있는 것이 아니라 데이터와 목적에 맞는 적절한 값이 있다.</p>
<h2 id="48-hyperparameter-탐색-방법">4.8 Hyperparameter 탐색 방법</h2>
<h3 id="grid-search">Grid Search</h3>
<p>미리 정한 모든 조합을 전수 조사한다.</p>
<ul>
<li>장점: 격자 안에서는 빠짐없이 비교</li>
<li>단점: 변수가 많아지면 조합 수가 폭발</li>
<li>적합한 경우: 하이퍼파라미터 수와 후보가 적을 때</li>
</ul>
<h3 id="random-search">Random Search</h3>
<p>정한 범위에서 무작위 조합을 뽑는다.</p>
<ul>
<li>장점: 고차원 공간에서 Grid보다 효율적</li>
<li>단점: 최적 조합을 반드시 고른다는 보장은 없음</li>
<li>적합한 경우: 탐색 공간이 넓을 때</li>
</ul>
<h3 id="bayesian-search">Bayesian Search</h3>
<p>이전 실험 결과를 이용해 다음에 시도할 유망한 지점을 선택한다.</p>
<ul>
<li>장점: 적은 실험으로 좋은 값에 접근 가능</li>
<li>단점: 탐색 자체의 구현과 계산이 복잡</li>
<li>적합한 경우: 한 번의 학습 비용이 큰 모델</li>
</ul>
<h2 id="49-overfitting과-underfitting">4.9 Overfitting과 Underfitting</h2>
<h3 id="overfitting-과대적합">Overfitting, 과대적합</h3>
<p>학습 데이터를 지나치게 외워 Train에서는 매우 잘 맞지만 Validation/Test에서는 성능이 떨어지는 상태다.</p>
<p>원인:</p>
<ul>
<li>Train과 Test의 분포 차이</li>
<li>데이터 수 부족</li>
<li>Feature 과다</li>
<li>지나치게 복잡한 알고리즘</li>
</ul>
<h3 id="underfitting-과소적합">Underfitting, 과소적합</h3>
<p>모델이 너무 단순하거나 학습이 부족해 Train에서도 패턴을 제대로 배우지 못한 상태다.</p>
<h3 id="대응-방법">대응 방법</h3>
<table>
<thead>
<tr>
<th>구분</th>
<th>Overfitting 대응</th>
<th>Underfitting 대응</th>
</tr>
</thead>
<tbody><tr>
<td>데이터</td>
<td>데이터 추가, Test와 유사한 Train 구성</td>
<td>데이터 추가가 도움이 될 수 있음</td>
</tr>
<tr>
<td>Feature</td>
<td>불필요한 Feature 제거</td>
<td>유용한 Feature 추가</td>
</tr>
<tr>
<td>모델</td>
<td>단순화, 정규화</td>
<td>더 복잡한 알고리즘, 충분한 탐색 범위</td>
</tr>
</tbody></table>
<p>좋은 모델은 Train 점수가 가장 높은 모델이 아니라 <strong>Train과 Test 모두에서 안정적으로 좋은 모델</strong>이다.</p>
<h2 id="410-data-leakage">4.10 Data Leakage</h2>
<p>모델이 실제 예측 시점에는 알 수 없는 정보를 학습에 사용하는 치명적인 오류다. 개발 점수는 99%처럼 매우 높지만 운영 성능이 급락할 수 있다.</p>
<h3 id="target-leakage">Target Leakage</h3>
<p>Feature에 Target 결과가 직접 또는 간접 포함되는 경우다.</p>
<ul>
<li>폐렴 예측에 진단 후 처방된 약 정보를 사용</li>
<li>이탈 예측에 해지 후 납부한 위약금 정보를 사용</li>
</ul>
<h3 id="train-test-contamination">Train-Test Contamination</h3>
<p>Test 정보가 전처리나 학습 과정에 노출되는 경우다.</p>
<ul>
<li>전체 데이터 평균으로 결측치를 대체</li>
<li>전체 데이터로 Scaling 기준을 계산</li>
<li>Feature Selection을 전체 데이터에서 수행한 뒤 분할</li>
</ul>
<p>올바른 순서는 다음과 같다.</p>
<pre><code class="language-text">먼저 Train/Validation/Test 분할
  → Train에서만 평균·표준편차·변환 규칙 학습
  → 같은 규칙을 Validation/Test에 적용</code></pre>
<h3 id="교재-퀴즈-해설">교재 퀴즈 해설</h3>
<ol>
<li>결측치 대체 평균은 <strong>Train에서 계산</strong>하고 Train·Validation·Test 모두에 적용한다.</li>
<li>하이퍼파라미터는 <strong>Validation 성능</strong>을 기준으로 고른다.</li>
<li>최종 정확도는 학습과 선택에 관여하지 않은 <strong>Test 성능</strong>으로 보고한다.</li>
</ol>

<p>지표는 “가장 유명한 것”이 아니라 잘못된 예측이 만드는 업무 비용에 따라 고른다.</p>
<h2 id="52-classification-평가-confusion-matrix">5.2 Classification 평가: Confusion Matrix</h2>
<p>실제값과 예측값의 조합을 네 칸으로 정리한 표다.</p>
<table>
<thead>
<tr>
<th></th>
<th align="right">실제 Positive</th>
<th align="right">실제 Negative</th>
</tr>
</thead>
<tbody><tr>
<td>예측 Positive</td>
<td align="right">TP</td>
<td align="right">FP</td>
</tr>
<tr>
<td>예측 Negative</td>
<td align="right">FN</td>
<td align="right">TN</td>
</tr>
</tbody></table>
<ul>
<li><strong>TP</strong>: 관심 대상을 맞게 잡음</li>
<li><strong>TN</strong>: 비관심 대상을 맞게 제외</li>
<li><strong>FP</strong>: 아닌데 맞다고 오탐</li>
<li><strong>FN</strong>: 맞는데 아니라고 미탐</li>
</ul>
<h3 id="accuracy">Accuracy</h3>
<p>전체 중 맞힌 비율이다.</p>
<p>$$
Accuracy = \frac{TP + TN}{TP + FP + FN + TN}
$$</p>
<h3 id="recall">Recall</h3>
<p>실제 Positive 중 잡아낸 비율이다.</p>
<p>$$
Recall = \frac{TP}{TP + FN}
$$</p>
<p>암 환자를 놓치지 않는 것이 중요하다면 Recall을 우선한다.</p>
<h3 id="precision">Precision</h3>
<p>Positive라고 예측한 것 중 진짜 Positive의 비율이다.</p>
<p>$$
Precision = \frac{TP}{TP + FP}
$$</p>
<p>정상 이메일을 스팸으로 잘못 막는 피해가 크다면 Precision을 중요하게 본다.</p>
<h3 id="f1-score">F1 Score</h3>
<p>Precision과 Recall의 조화평균이다.</p>
<p>$$
F1 = 2 \times \frac{Precision \times Recall}{Precision + Recall}
$$</p>
<p>두 값 중 하나만 지나치게 높고 다른 하나가 낮으면 F1도 낮아진다.</p>
<h2 id="53-숫자-예제로-계산하기">5.3 숫자 예제로 계산하기</h2>
<p>100명 중 실제 이탈자가 25명이고 다음과 같이 예측했다고 하자.</p>
<ul>
<li>TP = 20</li>
<li>FN = 5</li>
<li>FP = 15</li>
<li>TN = 60</li>
</ul>
<p>그러면:</p>
<ul>
<li>Accuracy = <code>(20 + 60) / 100 = 0.80</code></li>
<li>Recall = <code>20 / (20 + 5) = 0.80</code></li>
<li>Precision = <code>20 / (20 + 15) ≈ 0.57</code></li>
<li>F1 ≈ <code>0.67</code></li>
</ul>
<p>정확도만 보면 80%로 괜찮아 보이지만, 이탈한다고 예측한 사람 중 실제 이탈자는 약 57%뿐이다. 여러 지표를 함께 봐야 하는 이유다.</p>
<h2 id="54-클래스-불균형에서-accuracy의-함정">5.4 클래스 불균형에서 Accuracy의 함정</h2>
<p>CCTV 범인 탐지에서 실제 범인이 10%, 일반인이 90%라고 하자. 모든 사람을 일반인이라고 예측하면 Accuracy는 90%지만 범인은 한 명도 잡지 못해 Recall은 0이다.</p>
<p>따라서:</p>
<ul>
<li>전체 정답률만 원하면 Accuracy</li>
<li>범인을 놓치지 않으려면 Recall</li>
<li>일반인을 범인으로 오탐하지 않으려면 Precision</li>
<li>오탐과 미탐을 함께 균형 있게 보려면 F1</li>
</ul>
<p>교재의 비교 예시에서도 Accuracy가 가장 높은 모델이 반드시 가장 좋은 모델은 아니다. “일반인을 범인으로 잘못 판단하는 오류를 최소화”하는 목적이라면 False Positive가 적고 Precision이 높은 쪽을 봐야 한다.</p>

<h2 id="55-baseline-모델과-naive-모델">5.5 Baseline 모델과 Naive 모델</h2>
<p>모델 점수는 절대값보다 <strong>비교 기준</strong>이 중요하다.</p>
<h3 id="baseline-모델">Baseline 모델</h3>
<p>비교를 위해 정한 기준 모델이다.</p>
<ul>
<li>기존 운영 모델</li>
<li>단순한 선형 모델</li>
<li>규칙 기반 모델</li>
<li>Naive 모델</li>
</ul>
<h3 id="naive-모델">Naive 모델</h3>
<p>학습 없이 매우 단순한 규칙으로 예측한다.</p>
<ul>
<li>분류: 모두 다수 클래스로 예측</li>
<li>회귀: 모두 평균값으로 예측</li>
<li>시계열: 다음 값을 직전 값으로 예측</li>
</ul>
<p>복잡한 모델이 Naive 모델보다도 못하다면 운영할 이유가 거의 없다.</p>
<h2 id="56-auc-임계값-전체에서-보는-분류-능력">5.6 AUC: 임계값 전체에서 보는 분류 능력</h2>
<p>분류 모델은 보통 먼저 0~1 확률을 출력한다. 임계값을 0.5로 정하면 그 이상을 Positive로 분류하지만, 임계값을 바꾸면 Recall과 FP 비율이 달라진다.</p>
<p>ROC Curve는 임계값을 0부터 1까지 바꾸며 성능 변화를 그린 곡선이고, AUC는 그 아래 면적이다.</p>
<ul>
<li>0.5 근처: 무작위 수준</li>
<li>1에 가까움: Positive를 Negative보다 위에 정렬하는 능력이 좋음</li>
<li>0.5보다 작음: 예측 방향이 뒤집혔을 가능성</li>
</ul>
<p>AUC는 특정 임계값 하나가 아니라 <strong>전체 확률 순위 품질</strong>을 평가할 때 유용하다. 다만 심한 클래스 불균형에서는 AUCPR도 함께 보는 것이 좋다.</p>
<h2 id="57-lift-상위-고객을-골라-쓸-때의-성능">5.7 Lift: 상위 고객을 골라 쓸 때의 성능</h2>
<p>Lift는 상위 예측 집단의 Positive 비율이 전체 무작위 집단보다 몇 배 높은지를 보여준다.</p>
<p>$$
Lift@K% = \frac{상위\ K%의\ Positive\ 비율}{전체\ Positive\ 비율}
$$</p>
<p>전체 이탈률이 15%인데 예측 점수 상위 10%의 이탈률이 50%라면:</p>
<p>$$
Lift@10% = 0.50 / 0.15 \approx 3.33
$$</p>
<p>즉, 무작위로 연락할 때보다 상위 10%에 연락하면 약 3.33배 높은 밀도로 이탈 고객을 만날 수 있다.</p>
<h3 id="auc와-lift를-함께-보는-법">AUC와 Lift를 함께 보는 법</h3>
<ul>
<li>AUC: 전체 고객 순위가 전반적으로 좋은가?</li>
<li>Lift: 실제로 캠페인할 상위 1%, 10%, 20%에서 좋은가?</li>
</ul>
<p>전체 AUC가 조금 낮아도 상위 1% Lift가 매우 높다면 소수 고객만 선별하는 업무에서 더 유용할 수 있다. 반대로 AUC는 높지만 필요한 상위 구간 Lift가 낮으면 실제 캠페인 효과는 기대보다 작을 수 있다.</p>

<h2 id="59-regression의-기본-개념">5.9 Regression의 기본 개념</h2>
<p>회귀는 독립변수와 연속형 종속변수의 관계를 가장 잘 설명하는 식을 찾는다.</p>
<p>$$
\hat{y} = a_1x_1 + a_2x_2 + \cdots + a_kx_k + b
$$</p>
<ul>
<li>관측값 <code>y</code>: 실제값</li>
<li>예측값 <code>ŷ</code>: 회귀식이 계산한 값</li>
<li>잔차 <code>y - ŷ</code>: 관측값과 예측값의 차이</li>
</ul>
<p>최소제곱법은 잔차 제곱합을 가장 작게 만드는 계수를 찾는다.</p>
<h2 id="510-회귀-평가-지표">5.10 회귀 평가 지표</h2>
<h3 id="mae-mean-absolute-error">MAE: Mean Absolute Error</h3>
<p>오차 절댓값의 평균이다.</p>
<p>$$
MAE = \frac{1}{n}\sum_{i=1}^{n}|y_i-\hat{y}_i|
$$</p>
<ul>
<li>장점: 실제값과 단위가 같아 직관적</li>
<li>단점: 데이터 단위에 의존</li>
</ul>
<p>예를 들어 MAE가 3만 원이면 평균적으로 약 3만 원 정도 틀린다는 뜻이다.</p>
<h3 id="mse-mean-squared-error">MSE: Mean Squared Error</h3>
<p>오차를 제곱한 뒤 평균낸다.</p>
<p>$$
MSE = \frac{1}{n}\sum_{i=1}^{n}(y_i-\hat{y}_i)^2
$$</p>
<ul>
<li>장점: 큰 오차에 강한 벌점</li>
<li>단점: 이상치에 민감하고 단위가 제곱이라 해석이 어렵다.</li>
</ul>
<h3 id="rmse-root-mean-squared-error">RMSE: Root Mean Squared Error</h3>
<p>MSE에 제곱근을 취한다.</p>
<p>$$
RMSE = \sqrt{\frac{1}{n}\sum_{i=1}^{n}(y_i-\hat{y}_i)^2}
$$</p>
<ul>
<li>큰 오차를 강조하면서 원래 단위로 돌아온다.</li>
<li>여전히 이상치에 민감하다.</li>
</ul>
<h3 id="mape-mean-absolute-percentage-error">MAPE: Mean Absolute Percentage Error</h3>
<p>실제값 대비 절대 오차 비율의 평균이다.</p>
<p>$$
MAPE = \frac{100}{n}\sum_{i=1}^{n}\left|\frac{y_i-\hat{y}_i}{y_i}\right|
$$</p>
<ul>
<li>장점: 백분율이라 직관적이며 서로 다른 규모를 비교하기 좋다.</li>
<li>단점: 실제값이 0이면 계산할 수 없고, 실제값이 매우 작으면 과도하게 커진다.</li>
</ul>
<p>실제값 1, 2, 3에 대한 예측이 1, 1.5, 2.5라면 각 비율 오차는 0%, 25%, 약 16.7%이고 MAPE는 약 13.9%다.</p>
<p>MAPE가 불안정할 때는 실제값과 예측값의 평균 크기로 나누는 sMAPE 등을 고려할 수 있다.</p>
<h3 id="r²-결정계수">R²: 결정계수</h3>
<p>모델이 종속변수의 변동을 얼마나 설명하는지 나타낸다.</p>
<p>$$
R^2 = 1 - \frac{SSE}{SST}
$$</p>
<ul>
<li><code>SST</code>: 실제값이 평균에서 떨어진 총 변동</li>
<li><code>SSR</code>: 모델이 설명한 변동</li>
<li><code>SSE</code>: 모델이 설명하지 못한 잔차 변동</li>
<li>관계: <code>SST = SSR + SSE</code></li>
</ul>
<p>일반적으로 1에 가까울수록 설명력이 좋다. 0이면 단순 평균 예측과 비슷하고, 음수면 평균만 예측하는 Naive 모델보다도 못할 수 있다.</p>
<h3 id="adjusted-r²">Adjusted R²</h3>
<p>R²는 쓸모없는 독립변수를 추가해도 낮아지지 않는 문제가 있다. 조정된 R²는 변수 수와 데이터 수를 반영해 불필요한 변수 추가에 벌점을 준다.</p>

<h1 id="6-모델-해석">6. 모델 해석</h1>
<h2 id="61-왜-모델-해석이-필요한가">6.1 왜 모델 해석이 필요한가?</h2>
<p>복잡한 ML/DL 모델은 성능이 높아도 내부 의사결정 과정을 이해하기 어려운 블랙박스가 될 수 있다.</p>
<p>해석이 필요한 이유:</p>
<ul>
<li>사용자가 결과를 신뢰할 수 있어야 한다.</li>
<li>잘못된 상관관계와 Leakage를 발견해야 한다.</li>
<li>규제·감사·고객 설명 요구에 대응해야 한다.</li>
<li>모델 개선에 필요한 Feature 힌트를 얻어야 한다.</li>
</ul>
<p>선형회귀는 계수로 영향 방향과 크기를 어느 정도 볼 수 있지만, 복잡한 비선형 모델은 별도 설명 기법이 필요하다. 이를 다루는 영역이 XAI(Explainable AI)다.</p>
<h2 id="62-shap의-직관">6.2 SHAP의 직관</h2>
<p>SHAP은 게임이론의 Shapley Value를 이용해 각 Feature가 예측값을 기준값에서 얼마나 올리거나 내렸는지 기여도를 배분한다.</p>
<p>예를 들어 한 고객의 신용 예측에서:</p>
<ul>
<li>소득과 긴 거래 기간은 점수를 올림</li>
<li>높은 부채와 연체 경험은 점수를 내림</li>
</ul>
<p>처럼 한 건의 예측을 Feature별 기여로 나눠 설명할 수 있다.</p>
<blockquote>
<p>주의: SHAP은 모델이 학습한 관계를 설명한다. 그 자체가 현실의 인과관계를 증명하지는 않는다.</p>
</blockquote>
<h2 id="63-shap으로-보는-세-가지-관점">6.3 SHAP으로 보는 세 가지 관점</h2>
<h3 id="1-feature-importance">1) Feature Importance</h3>
<p><code>mean(|SHAP value|)</code>처럼 각 Feature의 절대 기여도를 평균내 전체적으로 중요한 변수 순위를 본다.</p>
<p>질문: “모델이 전반적으로 가장 많이 참고한 정보는 무엇인가?”</p>
<h3 id="2-feature-impact">2) Feature Impact</h3>
<p>각 샘플의 SHAP 값 분포와 Feature 값의 높고 낮음을 함께 본다.</p>
<p>질문:</p>
<ul>
<li>중요한 Feature가 예측을 어느 방향으로 움직이는가?</li>
<li>높은 값과 낮은 값의 효과가 다른가?</li>
<li>일부 샘플에서만 영향이 큰가?</li>
</ul>
<h3 id="3-feature-dependence">3) Feature Dependence</h3>
<p>Feature 값이 변할 때 SHAP 값이 어떻게 달라지는지 본다. 다른 Feature와의 상호작용도 색이나 그룹으로 확인할 수 있다.</p>
<p>예를 들어 연령이 증가할수록 이탈 기여도가 커지지만, 활동 고객 여부에 따라 같은 연령에서도 영향이 달라질 수 있다. 상품 수가 많을 때 이탈 기여도가 특정 구간부터 급증하는 비선형 패턴도 찾을 수 있다.</p>
<h3 id="해석-시-꼭-확인할-것">해석 시 꼭 확인할 것</h3>
<ul>
<li>중요도가 높다고 인과관계가 있는 것은 아니다.</li>
<li>상관된 Feature끼리는 기여도가 나뉘거나 불안정할 수 있다.</li>
<li>전체 설명과 한 고객의 개별 설명은 다르다.</li>
<li>설명 결과도 시간에 따라 변할 수 있으므로 운영 중 점검해야 한다.</li>
</ul>

<h1 id="7-모델-모니터링">7. 모델 모니터링</h1>
<h2 id="71-model-drift란">7.1 Model Drift란?</h2>
<p>개발 시점과 운영 시점의 환경 차이 때문에 시간이 지나며 모델 성능이나 동작 특성이 달라지는 현상이다.</p>
<p>모니터링하지 않으면:</p>
<ul>
<li>예측 정확도와 신뢰도가 감소한다.</li>
<li>잘못된 예측이 업무 의사결정으로 이어진다.</li>
<li>매출 손실과 리스크 증가가 발생할 수 있다.</li>
</ul>
<p>Drift는 크게 입력, 출력, 관계의 변화로 나눌 수 있다.</p>
<h2 id="72-data-drift-입력-분포-변화">7.2 Data Drift: 입력 분포 변화</h2>
<p>운영 시점 Feature 분포가 학습 시점과 달라진 현상이다.</p>
<p>$$
P_t(X) \neq P_{ref}(X)
$$</p>
<h3 id="발생-예시">발생 예시</h3>
<ul>
<li>신규 연령대 고객이 대량 유입</li>
<li>계절·이벤트로 특정 상품 수요 급증</li>
<li>사회적 사건으로 소비 패턴 변화</li>
<li>센서 교체로 단위가 바뀜</li>
<li>결측치 처리나 데이터 Pipeline 로직 변경</li>
</ul>
<p>입력이 달라졌다고 성능이 반드시 나빠지는 것은 아니지만, 위험 신호이므로 점검해야 한다.</p>
<h2 id="73-prediction-drift-예측-분포-변화">7.3 Prediction Drift: 예측 분포 변화</h2>
<p>모델이 출력하는 예측값이나 확률의 분포가 기준 시점과 달라진 현상이다.</p>
<p>$$
P_t(\hat{Y}) \neq P_{ref}(\hat{Y})
$$</p>
<p>예:</p>
<ul>
<li>신용점수 예측이 전반적으로 낮아짐</li>
<li>긍정 분류 비율이 갑자기 감소</li>
<li>확률이 0과 1 근처가 아니라 0.4~0.6에 몰려 모델 불확실성이 증가</li>
</ul>
<p>Prediction Drift는 Data Drift나 Concept Drift의 결과로 나타나는 경우가 많다. 다만 입력을 전부 모니터링하기 어렵거나 정답이 늦게 도착할 때 빠른 경보 지표로 유용하다.</p>
<h2 id="74-concept-drift-x와-y의-관계-변화">7.4 Concept Drift: X와 Y의 관계 변화</h2>
<p>입력과 정답 사이의 패턴 자체가 변해 기존 규칙이 더 이상 유효하지 않은 상태다.</p>
<p>$$
P_t(Y|X) \neq P_{ref}(Y|X)
$$</p>
<h3 id="발생-예시-1">발생 예시</h3>
<ul>
<li>금리 변화로 부도 위험 기준이 달라짐</li>
<li>법·규제 개정</li>
<li>UI 개편으로 클릭 패턴 변화</li>
<li>상품 분류 기준 변경</li>
<li>경쟁사 등장으로 고객 이탈 이유 변화</li>
<li>경기 침체로 소비 패턴 변화</li>
</ul>
<p>Concept Drift는 실제 정답을 받아 성능을 측정해야 가장 확실히 알 수 있다. 그러나 정답이 몇 달 뒤에 생기는 업무라면 탐지가 늦어질 수 있다.</p>

<li>모델 성능은 유지되고 예측 분포만 달라졌다면 Threshold 조정을 검토한다.</li>
<li>성능이 실제로 떨어졌다면 최신 데이터로 Re-training한다.</li>
<li>재학습으로도 개선되지 않으면 Feature와 모델 구조를 다시 설계한다.</li>
</ol>
<h2 id="76-model-renewal의-세-수준">7.6 Model Renewal의 세 수준</h2>
<h3 id="threshold-adjustment">Threshold Adjustment</h3>
<p>모델은 그대로 두고 판정 기준만 바꾼다.</p>
<p>예: 위험 확률 0.20 이하를 우량으로 보던 기준을 0.15 이하로 강화</p>
<p>장점은 빠르고 저렴하다는 것이지만, 모델의 순위 능력이 이미 무너졌다면 해결책이 아니다.</p>
<h3 id="re-training">Re-training</h3>
<p>Feature 정의와 모델 구조는 유지하고 최신 데이터로 파라미터를 다시 학습한다.</p>
<p>예: 같은 Feature를 사용하지만 최근 데이터 패턴에 맞게 계수·트리 구조가 바뀜</p>
<h3 id="re-modeling">Re-modeling</h3>
<p>EDA, Feature 생성·선택, 알고리즘 선정까지 다시 수행한다. Concept Drift처럼 문제 구조가 바뀌었을 때 필요하다.</p>
<pre><code class="language-text">작은 변화                       큰 변화
Threshold 조정 → Re-training → Re-modeling</code></pre>
<hr />
<h1 id="appendix-a-end-to-end-모델링-프로세스">Appendix A. End-to-End 모델링 프로세스</h1>
<p>전체 과정을 변수 유형 관점에서 연결하면 다음과 같다.</p>
<h2 id="a1-범주형-변수">A.1 범주형 변수</h2>
<pre><code class="language-text">분포·결측·이상치 분석
  → 값의 Level 확인
  → 필요 시 분석 제외
  → 결측치 대체
  → 희소 범주 Re-grouping
  → One-Hot Encoding
  → 변수 유의성·논리성 분석
  → Feature Selection</code></pre>
<p>범주가 너무 많으면 희소성과 차원 증가 문제가 생긴다. 드문 범주를 <code>기타</code>로 합치거나 업무적으로 의미 있는 그룹으로 묶을 수 있다.</p>
<h2 id="a2-연속형-변수">A.2 연속형 변수</h2>
<pre><code class="language-text">분포·결측·이상치 분석
  → 결측치 대체
  → 이상치 대체·제한
  → 필요 시 Scaling 또는 Binning
  → 변수 유의성·상관 분석
  → Feature Selection</code></pre>
<p>상관이 매우 높은 변수들을 동시에 쓰면 해석과 안정성에 문제가 생길 수 있으므로 목적에 따라 선택하거나 결합한다.</p>
<h2 id="a3-공통-학습·평가-흐름">A.3 공통 학습·평가 흐름</h2>
<pre><code class="language-text">전처리와 Feature Engineering
  → Data Partition
  → 모델 학습·최적화
  → 모델 평가(AUC, R² 등)
  → 모델 해석</code></pre>
<p>모든 단계가 모든 프로젝트에 똑같이 필요한 것은 아니지만, 생략할 때는 반드시 이유가 있어야 한다.</p>
<hr />
<h1 id="appendix-b-automl">Appendix B. AutoML</h1>
<h2 id="b1-automl이란">B.1 AutoML이란?</h2>
<p>분석 Workflow의 전체 또는 일부를 자동화하는 기술이다.</p>
<p>전통적인 Workflow에서는 사람이 데이터 탐색, 준비, Feature Engineering, 모델 선택, 학습, 하이퍼파라미터 조정을 각각 수행한다. AutoML은 이 중 여러 단계를 자동으로 탐색·비교한다.</p>
<pre><code class="language-text">데이터 획득 → 탐색 → 준비 → Feature Engineering
→ 모델 선택 → 학습 → Hyperparameter Tuning → 예측</code></pre>
<h2 id="b2-automl이-등장한-배경">B.2 AutoML이 등장한 배경</h2>
<p>머신러닝에는 다음 역량이 동시에 필요하다.</p>
<ul>
<li>도메인 지식</li>
<li>수학·통계</li>
<li>프로그래밍</li>
<li>데이터 처리</li>
<li>적절한 알고리즘과 평가 지표 선택</li>
</ul>
<p>전문가에게도 반복 실험은 시간과 노력이 많이 든다. AutoML은 반복적이고 기계적인 후보 탐색을 자동화해 진입 장벽과 실험 비용을 낮춘다.</p>
<h2 id="b3-자동화-수준">B.3 자동화 수준</h2>
<p>일반적으로 사람의 판단이 많이 필요한 앞단보다 반복 계산이 많은 뒷단이 자동화하기 쉽다.</p>
<pre><code class="language-text">자동화 낮음                                              자동화 높음
비즈니스 문제 정의 → 전처리 → Feature Engineering → 학습·평가</code></pre>
<ul>
<li>비즈니스 문제 정의: 주제, 분석 요건, 필요한 데이터 결정</li>
<li>Preprocessing: 데이터 입수·변환·통합</li>
<li>Feature Engineering: 추출·선택</li>
<li>Training: 모델 선택, 하이퍼파라미터 탐색, 평가</li>
</ul>
<p>AutoML이 모델을 잘 골라도 Target 정의가 틀리거나 데이터가 누출되면 좋은 프로젝트가 될 수 없다.</p>
<h2 id="b4-궁극적-목표-model-lifecycle-자동화">B.4 궁극적 목표: Model Lifecycle 자동화</h2>
<p>현재 AutoML은 모델링 단계 중심이지만, 장기적으로는 다음 순환을 자동화하는 방향으로 발전한다.</p>
<pre><code class="language-text">모델링 → 배포 → 모니터링 → Drift 감지
  → 재학습 또는 재구축 → 다시 배포</code></pre>
<p>이를 위해서는 성능 기준, 경보 조건, 승인 절차, 롤백 방식, 데이터 품질 검사까지 함께 설계해야 한다.</p>
<h2 id="b5-data-analyst의-역할-변화">B.5 Data Analyst의 역할 변화</h2>
<p>자동화가 분석가를 없앤다기보다 역할의 중심을 바꾼다.</p>
<p>과거에는 데이터 가공과 모델 실험에 많은 시간을 썼다면, 앞으로는 다음 역량이 더 중요해진다.</p>
<ul>
<li>올바른 비즈니스 문제와 Target 정의</li>
<li>데이터 의미와 품질 판단</li>
<li>자동화 결과의 검증</li>
<li>위험·공정성·설명 가능성 검토</li>
<li>IT·업무 담당자와의 협업</li>
<li>분석 결과를 실제 의사결정으로 연결</li>
</ul>
<p>즉, 반복 작업은 줄고 <strong>설계와 활용을 연결하는 역할</strong>은 강화된다.</p>
<hr />
<h1 id="마지막-정리-모델-개발에서-기억할-15가지">마지막 정리: 모델 개발에서 기억할 15가지</h1>
<ol>
<li>좋은 모델은 좋은 문제 정의에서 시작한다.</li>
<li>Target의 업무 정의가 바뀌면 모델의 의미도 바뀐다.</li>
<li>관찰 기간과 예측 기간을 분리해 미래 정보 누출을 막는다.</li>
<li>데이터 품질은 알고리즘보다 먼저 확인한다.</li>
<li>데이터 특성에 따라 모델과 인프라 전략이 달라진다.</li>
<li>Feature Engineering은 원본 데이터를 문제에 맞는 표현으로 바꾸는 일이다.</li>
<li>Feature가 많다고 항상 좋은 것은 아니다.</li>
<li>Train은 학습, Validation은 선택, Test는 최종 평가에 사용한다.</li>
<li>Sampling과 전처리 기준 계산은 Train에서만 한다.</li>
<li>Train 점수보다 보지 못한 데이터에서의 일반화 성능이 중요하다.</li>
<li>Accuracy 하나만 보면 클래스 불균형 문제를 놓칠 수 있다.</li>
<li>평가지표는 오탐과 미탐의 비즈니스 비용에 맞춰 선택한다.</li>
<li>SHAP 같은 설명은 모델의 판단 근거를 보여주지만 인과관계를 증명하지 않는다.</li>
<li>배포는 끝이 아니라 모니터링의 시작이다.</li>
<li>AutoML이 자동화해도 문제 정의와 결과 검증은 사람의 책임이다.</li>
</ol>

<h1 id="빠른-복습-문제">빠른 복습 문제</h1>
<details>
1. Train 평균으로 Test 결측치를 채워야 하는 이유는?

<p>Test의 정보를 학습 과정에 노출하지 않기 위해서다. 전체 데이터 평균을 사용하면 Test 분포가 전처리 규칙에 반영되어 Train-Test Contamination이 생긴다.</p>
</details>

<details>
2. Accuracy 99%인 모델이 나쁠 수도 있는 이유는?

<p>Positive가 1%뿐인 데이터에서 모두 Negative로 예측해도 Accuracy는 99%다. 그러나 Positive Recall은 0이므로 관심 대상을 한 건도 찾지 못한다.</p>
</details>

<details>
3. AUC와 Lift의 차이는?

<p>AUC는 전체 데이터에서 확률 순위의 전반적인 분류 능력을 보고, Lift는 실제로 사용할 상위 구간에서 Positive를 얼마나 농축했는지 본다.</p>
</details>

<details>
4. Data Drift와 Concept Drift의 차이는?

<p>Data Drift는 입력 <code>X</code>의 분포가 변한 것이고, Concept Drift는 같은 <code>X</code>가 <code>Y</code>로 이어지는 관계 자체가 변한 것이다.</p>
</details>

<details>
5. Re-training과 Re-modeling은 어떻게 다른가?

<p>Re-training은 같은 Feature와 모델 구조를 유지한 채 최신 데이터로 다시 학습한다. Re-modeling은 EDA, Feature, 알고리즘 선택부터 다시 설계한다.</p>
</details>

<p>전체 흐름은 다음과 같다.</p>
<pre><code class="language-text">사용자
  ↓
DNS → Load Balancer → Ingress
                          ↓
                       Service
                          ↓
                  Deployment가 관리하는 Pod들
                          ↓
                    Container → App

설정: ConfigMap / Secret
데이터: PVC → PV → 실제 스토리지</code></pre>

<h1 id="1일차-wrap-up">1일차 Wrap-up</h1>
<h2 id="1-쿠버네티스가-필요한-이유">1. 쿠버네티스가 필요한 이유</h2>
<p>Docker는 컨테이너 하나를 실행하는 데 적합하다.</p>
<pre><code class="language-bash">docker run my-api:1.0.0</code></pre>
<p>하지만 실제 서비스에는 더 많은 운영 판단이 필요하다.</p>
<ul>
<li>컨테이너가 죽으면 다시 실행해야 한다.</li>
<li>사용자가 늘면 실행 개수를 늘려야 한다.</li>
<li>여러 컨테이너로 요청을 분산해야 한다.</li>
<li>새 버전을 서비스 중단 없이 배포해야 한다.</li>
<li>여러 서버 중 실행할 위치를 정해야 한다.</li>
<li>설정과 비밀값을 안전하게 전달해야 한다.</li>
</ul>
<p>쿠버네티스는 사용자가 선언한 <strong>원하는 상태</strong>와 현재 상태를 계속 비교하고, 둘이 다르면 자동으로 맞춘다. 이를 <strong>조정 루프(Reconciliation Loop)</strong>라고 한다.</p>
<pre><code class="language-text">원하는 상태: Pod 3개
현재 상태:   Pod 2개
판단:        1개 부족
동작:        Pod 1개 생성</code></pre>
<h2 id="2-컨테이너와-이미지">2. 컨테이너와 이미지</h2>
<ul>
<li><strong>이미지(Image)</strong>: 애플리케이션과 실행에 필요한 파일을 묶은 읽기 전용 설계도</li>
<li><strong>컨테이너(Container)</strong>: 이미지를 실제로 실행한 프로세스</li>
<li><strong>레지스트리(Registry)</strong>: 이미지를 저장하고 배포하는 서버. Harbor, ECR 등이 있다.</li>
</ul>
<pre><code class="language-text">소스 코드 → 이미지 빌드 → 레지스트리에 Push → 클러스터가 Pull → 컨테이너 실행</code></pre>
<p>운영에서는 <code>latest</code>보다 버전을 식별할 수 있는 태그를 사용하는 것이 좋다.</p>
<pre><code class="language-text">좋지 않은 예: shop-api:latest
좋은 예:     shop-api:1.4.2
더 좋은 예: shop-api:1.4.2-a1b2c3d  # Git 커밋 식별자 포함</code></pre>

<p><strong>클러스터</strong>는 쿠버네티스가 관리하는 여러 서버의 집합이다.</p>
<pre><code class="language-text">Control Plane: 판단하고 지시한다.
Worker Node:   실제 Pod를 실행한다.</code></pre>

<h2 id="4-선언형-관리와-매니페스트">4. 선언형 관리와 매니페스트</h2>
<p>쿠버네티스에서는 YAML로 원하는 상태를 표현한다. 이 파일을 <strong>매니페스트</strong>라고 한다.</p>
<pre><code class="language-yaml">apiVersion: apps/v1
kind: Deployment
metadata:
  name: example-api
spec:
  replicas: 3</code></pre>
<p>모든 리소스는 보통 다음 네 부분으로 읽는다.</p>

<h2 id="5-kubectl-kubelet-context와-namespace">5. kubectl, kubelet, Context와 Namespace</h2>
<ul>
<li><strong>kubectl</strong>: 사용자가 API Server에 명령을 보내는 CLI 도구</li>
<li><strong>kubelet</strong>: 각 Node에서 Pod와 컨테이너가 정상 실행되는지 관리하는 에이전트</li>
</ul>
<pre><code class="language-text">사용자 → kubectl → API Server → Scheduler/Controller → kubelet → Container</code></pre>
<p>Context는 접속할 클러스터, 사용자, 기본 Namespace의 묶음이다.</p>
<pre><code class="language-bash">kubectl config current-context
kubectl config get-contexts
kubectl config view --minify</code></pre>
<p>Namespace는 하나의 클러스터를 팀이나 환경별로 논리적으로 나눈 공간이다. RBAC은 사용자가 어떤 리소스에 어떤 동작을 할 수 있는지 제한한다.</p>
<pre><code class="language-bash">kubectl auth can-i list pods -n &lt;namespace&gt;
kubectl auth can-i create deployments.apps -n &lt;namespace&gt;</code></pre>

<pre><code class="language-text">상태 확인 → 이벤트 확인 → 로그 확인 → 컨테이너 내부 확인</code></pre>
<pre><code class="language-bash">kubectl get pods -o wide
kubectl describe pod &lt;pod-name&gt;
kubectl logs &lt;pod-name&gt; --tail=100
kubectl logs &lt;pod-name&gt; --previous

<p><code>describe</code>의 마지막 <strong>Events</strong>에는 스케줄링 실패, 이미지 다운로드 실패, 프로브 실패 등 주요 원인이 기록된다.</p>
<h2 id="7-pod-핵심-복습">7. Pod 핵심 복습</h2>
<p>Pod는 쿠버네티스의 최소 실행 단위다. 하나 이상의 컨테이너가 네트워크와 볼륨을 공유한다.</p>
<pre><code class="language-text">Pod
 ├─ Container: application
 └─ Container: sidecar

공유 항목: Pod IP, localhost, Volume</code></pre>
<h3 id="running과-ready는-다르다">Running과 Ready는 다르다</h3>

<li><code>Running 0/1</code>: 프로세스는 실행됐지만 아직 트래픽을 받을 준비가 안 됐다.</li>

<h1 id="8장-deployment와-롤아웃">8장. Deployment와 롤아웃</h1>
<h2 id="81-deployment-replicaset-pod의-관계">8.1 Deployment, ReplicaSet, Pod의 관계</h2>
<p>세 리소스는 역할이 다르다.</p>
<pre><code class="language-text">Deployment: 버전과 배포 전략 관리
     ↓
ReplicaSet: 같은 버전의 Pod 개수 관리
     ↓
Pod: 실제 컨테이너 실행</code></pre>
<p>새 버전으로 배포하면 새로운 ReplicaSet이 생긴다. 이전 ReplicaSet은 보통 <code>replicas: 0</code> 상태로 남는다. 롤백은 이전 ReplicaSet을 다시 늘리는 방식으로 동작한다.</p>
<p>Pod 이름에서도 관계를 확인할 수 있다.</p>
<pre><code class="language-text">example-api-7d9f8c4b-x2k9p
            └──────┘
          ReplicaSet 해시</code></pre>
<pre><code class="language-bash">kubectl get deployment,replicaset,pod -l app=example-api
kubectl rollout history deployment/example-api</code></pre>
<p><code>revisionHistoryLimit</code>은 롤백을 위해 보존할 이전 ReplicaSet 개수를 정한다.</p>
<h2 id="82-deployment-매니페스트">8.2 Deployment 매니페스트</h2>
<pre><code class="language-yaml">apiVersion: apps/v1
kind: Deployment
metadata:
  name: example-api # selector 와 template.labels 는 반드시 일치
spec:
  replicas: 3
  revisionHistoryLimit: 5 # 롤백용 이력 보관 개수 (기본 10)
  selector:
    matchLabels:
      app: example-api # 불변— 만든 뒤 못 바꾼다
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1 # 목표보다 최대 1개 더 만들어도 된다
      maxUnavailable: 0 # 사용 가능한 개수는 줄이지 않는다
  template: # 여기부터가 Pod 스펙 
    metadata:
      labels:
        app: example-api
    spec:
      containers:
        - name: app
          image: registry.example.com/example-api:1.0.0</code></pre>
<p><code>spec.selector.matchLabels</code>와 <code>spec.template.metadata.labels</code>는 서로 일치해야 한다. Deployment의 selector는 생성 후 변경할 수 없다.</p>
<h2 id="83-rollingupdate-전략">8.3 RollingUpdate 전략</h2>
<ul>
<li><code>maxSurge</code>: 목표 개수보다 추가로 생성할 수 있는 Pod 수</li>
<li><code>maxUnavailable</code>: 업데이트 중 사용할 수 없어도 되는 Pod 수</li>
</ul>
<p>복제본이 3개이고 <code>maxSurge: 1</code>, <code>maxUnavailable: 0</code>이라면 다음처럼 진행된다.</p>
<pre><code class="language-text">기존 3개 실행
→ 새 Pod 1개 추가
→ 새 Pod가 Ready
→ 기존 Pod 1개 종료
→ 위 과정을 반복
→ 새 버전 3개, 이전 버전 0개</code></pre>
<p>readinessProbe가 없다면 쿠버네티스는 컨테이너가 시작된 직후 준비됐다고 판단할 수 있다. 초기화 중인 Pod로 요청이 전달될 수 있으므로 안전한 롤링 업데이트에는 readinessProbe가 필요하다.</p>
<h2 id="84-롤아웃-실행과-관찰">8.4 롤아웃 실행과 관찰</h2>
<p>배포 명령이 끝나도 실제 롤아웃은 계속 진행될 수 있다. <code>rollout status</code>로 완료 여부를 확인한다.</p>
<pre><code class="language-bash">kubectl set image deployment/example-api app=registry.example.com/example-api:1.0.1
kubectl rollout status deployment/example-api --timeout=180s
kubectl get pods -w
kubectl get replicasets -w</code></pre>
<p>CI/CD에서는 <code>apply</code> 성공만으로 배포 성공을 판단하면 안 된다. 새 Pod가 Ready 상태가 되는지까지 확인해야 한다.</p>
<h2 id="85-롤아웃이-멈추는-대표-원인">8.5 롤아웃이 멈추는 대표 원인</h2>
<table>
<thead>
<tr>
<th>상태</th>
<th>대표 원인</th>
<th>우선 확인</th>
</tr>
</thead>
<tbody><tr>
<td>Pending</td>
<td>Node 자원 부족, taint, affinity 조건</td>
<td><code>kubectl describe pod</code>의 Events</td>
</tr>
<tr>
<td>ImagePullBackOff</td>
<td>이미지 이름·태그 오류, Registry 권한</td>
<td><code>describe pod</code>의 pull 오류</td>
</tr>
<tr>
<td>CrashLoopBackOff</td>
<td>애플리케이션 시작 실패</td>
<td><code>kubectl logs --previous</code></td>
</tr>
<tr>
<td>Running 0/1</td>
<td>readinessProbe 실패</td>
<td><code>describe pod</code>의 probe 메시지</td>
</tr>
<tr>
<td>매우 느린 진행</td>
<td>startupProbe 유예가 김</td>
<td><code>kubectl get pods -w</code></td>
</tr>
<tr>
<td>ProgressDeadlineExceeded</td>
<td>제한 시간 동안 진전 없음</td>
<td>롤아웃 상태와 새 Pod 원인</td>
</tr>
</tbody></table>
<p><code>maxUnavailable: 0</code>이면 새 Pod가 준비되지 않을 때 기존 Pod를 유지하므로 서비스 용량을 보호할 수 있다.</p>
<h2 id="86-롤백과-이력">8.6 롤백과 이력</h2>
<pre><code class="language-bash">kubectl rollout history deployment/example-api
kubectl rollout history deployment/example-api --revision=3
kubectl rollout undo deployment/example-api
kubectl rollout undo deployment/example-api --to-revision=3</code></pre>
<p>변경 이유를 기록하면 어떤 버전으로 돌아갈지 판단하기 쉽다.</p>
<pre><code class="language-bash">kubectl annotate deployment/example-api \
  kubernetes.io/change-cause=&quot;1.0.1 timeout fix&quot; --overwrite</code></pre>
<p>필요하면 진행 중인 롤아웃을 잠시 멈추고 재개할 수 있다.</p>
<pre><code class="language-bash">kubectl rollout pause deployment/example-api
kubectl rollout resume deployment/example-api</code></pre>
<p>롤백은 Kubernetes 리소스와 애플리케이션 버전을 되돌린다. Git의 코드와 DB 스키마까지 자동으로 되돌리지는 않는다. DB 변경은 이전 앱과 호환되도록 단계적으로 설계해야 한다.</p>
<h2 id="87-스케일-조정">8.7 스케일 조정</h2>
<pre><code class="language-bash"># 긴급하거나 일시적인 변경
kubectl scale deployment/example-api --replicas=6

# 자동 확장 예시
kubectl autoscale deployment/example-api --min=3 --max=10 --cpu-percent=70</code></pre>
<p>운영 설정은 YAML과 Git에도 반영해야 다음 <code>apply</code>에서 되돌아가지 않는다. HPA가 복제본 수를 관리한다면 선언 파일의 고정 <code>replicas</code> 값과 충돌하지 않도록 관리 방식도 함께 정한다.</p>
<h2 id="88-무중단-배포의-조건">8.8 무중단 배포의 조건</h2>
<p>무중단 배포는 설정 하나로 완성되지 않는다.</p>
<ul>
<li>readinessProbe로 준비된 Pod만 트래픽을 받게 한다.</li>
<li><code>maxUnavailable: 0</code>으로 배포 중 용량 감소를 막는다.</li>
<li>복제본을 2개 이상 둬 교체 중에도 서비스가 남게 한다.</li>
<li><code>preStop</code>으로 Service 대상에서 빠지는 시간을 기다린다.</li>
<li>애플리케이션이 graceful shutdown을 지원해야 한다.</li>
<li>Node 작업까지 고려한다면 PodDisruptionBudget도 사용한다.</li>
</ul>

<h1 id="9장-service와-클러스터-네트워킹">9장. Service와 클러스터 네트워킹</h1>
<h2 id="91-pod-ip를-직접-사용하면-안-되는-이유">9.1 Pod IP를 직접 사용하면 안 되는 이유</h2>
<p>Pod는 재생성될 때 IP가 바뀐다. 애플리케이션 설정에 Pod IP를 직접 적으면 장애 복구나 배포 후 연결이 끊긴다.</p>
<p>Service는 바뀌는 Pod 앞에 고정된 접근점을 제공한다.</p>
<pre><code class="language-text">클라이언트 → Service 이름/ClusterIP → Ready Pod 중 하나</code></pre>
<h2 id="92-service는-가상-접근점이다">9.2 Service는 가상 접근점이다</h2>
<p>ClusterIP를 가진 실제 프로세스나 서버가 존재하는 것은 아니다. 일반적으로 kube-proxy가 각 Node에 트래픽 변환 규칙을 만들고, 커널이 목적지를 Pod IP로 바꾼다.</p>
<p>따라서 ClusterIP에 <code>ping</code>이 안 되는 것은 이상 현상이 아니다. TCP/HTTP 연결은 <code>curl</code>이나 <code>nc</code>로 확인한다.</p>
<h2 id="93-service-selector-endpoint">9.3 Service, Selector, Endpoint</h2>
<pre><code class="language-yaml">apiVersion: v1
kind: Service
metadata:
  name: example-api
spec:
  type: ClusterIP
  selector:
    app: example-api
  ports:
    - name: http
      port: 80
      targetPort: 8080</code></pre>

<p>Service가 찾은 실제 대상은 Endpoint 또는 EndpointSlice에서 확인한다.</p>
<pre><code class="language-bash">kubectl get endpoints example-api

<p>NodePort의 흐름은 다음과 같다.</p>
<pre><code class="language-text">NodeIP:NodePort → ClusterIP:port → PodIP:targetPort</code></pre>
<p>NodePort는 제한된 포트 범위를 사용하고 Node 주소를 알아야 하므로 일반적인 HTTP 운영 진입점으로는 잘 사용하지 않는다.</p>
<p>클라우드의 <code>LoadBalancer</code> Service는 외부 Load Balancer를 만들기 때문에 서비스 수에 따라 비용과 관리 대상이 늘어날 수 있다. 실제 동작과 지원 annotation은 클라우드 및 설치된 컨트롤러에 따라 다르다.</p>
<h2 id="95-클러스터-dns와-coredns">9.5 클러스터 DNS와 CoreDNS</h2>
<p>Service를 만들면 DNS 이름이 자동으로 등록된다.</p>
<pre><code class="language-text">&lt;service&gt;.&lt;namespace&gt;.svc.cluster.local</code></pre>
<p>호출 위치에 따라 이름을 줄여 쓸 수 있다.</p>
<pre><code class="language-text">같은 Namespace: example-api
다른 Namespace: example-api.team-a
전체 이름:       example-api.team-a.svc.cluster.local</code></pre>
<p>애플리케이션 설정에는 바뀔 수 있는 IP보다 Service 이름을 사용한다.</p>
<pre><code class="language-yaml">spring:
  datasource:
    url: jdbc:mysql://mysql:3306/example</code></pre>
<pre><code class="language-bash">kubectl run dns-test --rm -it --image=busybox:1.36 -- \
  nslookup example-api</code></pre>
<p>CoreDNS가 이름을 ClusterIP로 바꾸고, 노드의 네트워크 규칙이 ClusterIP를 다시 Pod IP로 바꾼다.</p>
<h2 id="96-세션과-부하-분산">9.6 세션과 부하 분산</h2>
<p>Service는 연결을 여러 Pod에 분산한다. 사용자 세션을 특정 Pod 메모리에만 저장하면 다음 요청이 다른 Pod로 전달될 때 세션을 찾지 못할 수 있다.</p>
<p>권장 방식은 상태를 Pod 밖에 두는 것이다.</p>
<ul>
<li>Redis나 DB에 세션 저장</li>
<li>무상태 토큰 사용</li>
<li>필요한 경우에만 <code>sessionAffinity</code> 같은 고정 방식 사용</li>
</ul>
<p>Pod 고정은 해당 Pod가 종료되면 상태를 잃기 때문에 근본적인 해결책이 아니다. HTTP keep-alive나 connection pool 때문에 여러 요청이 계속 같은 Pod로 보일 수도 있다.</p>
<h2 id="97-service-연결-장애-진단">9.7 Service 연결 장애 진단</h2>
<p>클러스터 내부의 진단용 컨테이너에서 아래 순서로 확인한다.</p>
<pre><code class="language-text">Pod IP → Service IP → Service DNS 이름 → 외부 경로</code></pre>
<pre><code class="language-bash"># 1. Pod가 직접 응답하는가?
curl http://&lt;pod-ip&gt;:8080/health

# 2. Service IP로 응답하는가?
curl http://&lt;cluster-ip&gt;:80/health

# 3. DNS 이름으로 응답하는가?
nslookup example-api
curl http://example-api/health

# 4. 실제 대상이 등록됐는가?
kubectl get endpoints example-api</code></pre>

<h1 id="10장-호출-흐름-추적">10장. 호출 흐름 추적</h1>
<h2 id="101-요청이-지나가는-여섯-구간">10.1 요청이 지나가는 여섯 구간</h2>
<p>외부 사용자의 요청이 애플리케이션까지 도착하는 길을 구간별로 나누면 장애 지점을 빠르게 찾을 수 있다.</p>
<pre><code class="language-text">1. 사용자 → DNS/Load Balancer
2. Load Balancer → Ingress Controller 또는 대상 Pod
3. 내부 호출 이름 → Service ClusterIP
4. Service ClusterIP → Pod IP:targetPort
5. Pod IP → 컨테이너 포트
6. 컨테이너 포트 → 실제 애플리케이션 프로세스</code></pre>
<p>컨트롤러와 <code>target-type</code> 구성에 따라 외부 요청은 Service를 거치지 않고 Load Balancer에서 Pod IP로 직접 전달될 수도 있다.</p>
<h2 id="102-사용자에서-load-balancer까지">10.2 사용자에서 Load Balancer까지</h2>
<p>이 구간은 클러스터 외부이므로 <code>kubectl</code>만으로 모두 확인할 수 없다.</p>
<p>확인할 대상은 다음과 같다.</p>
<ul>
<li>DNS 레코드가 올바른 Load Balancer를 가리키는가?</li>
<li>Ingress의 <code>ADDRESS</code>가 할당됐는가?</li>
<li>인증서가 유효하고 갱신되고 있는가?</li>
<li>외부에서 실제 호출했을 때 응답하는가?</li>
</ul>
<pre><code class="language-bash">dig +short api.example.com
kubectl get ingress example-api
curl -I https://api.example.com/health</code></pre>
<h2 id="103-load-balancer에서-pod까지">10.3 Load Balancer에서 Pod까지</h2>
<p>클라우드 Load Balancer의 <code>target-type: ip</code> 구성에서는 Pod IP가 대상 그룹에 직접 등록된다. <code>instance</code> 방식에서는 Node IP와 NodePort를 거친다.</p>
<table>
<thead>
<tr>
<th>방식</th>
<th>대상</th>
<th>특징</th>
</tr>
</thead>
<tbody><tr>
<td><code>ip</code></td>
<td>Pod IP와 targetPort</td>
<td>Node를 한 번 덜 거침</td>
</tr>
<tr>
<td><code>instance</code></td>
<td>Node IP와 NodePort</td>

<p>Load Balancer의 자체 health check와 Kubernetes readinessProbe는 서로 다른 검사일 수 있다. 두 상태가 모두 정상인지 확인해야 한다.</p>
<h2 id="104-이름에서-service-service에서-pod까지">10.4 이름에서 Service, Service에서 Pod까지</h2>
<p>클러스터 내부 호출은 보통 두 번 변환된다.</p>
<pre><code class="language-text">example-api
  ↓ CoreDNS
ClusterIP:80
  ↓ 네트워크 변환 규칙
PodIP:8080</code></pre>
<p>이 구간은 별도의 애플리케이션 로그가 남지 않을 수 있으므로 Service와 Endpoint를 직접 확인한다.</p>
<pre><code class="language-bash">kubectl get service example-api -o wide
kubectl get endpoints example-api</code></pre>
<h2 id="105-pod에서-컨테이너-프로세스까지">10.5 Pod에서 컨테이너 프로세스까지</h2>
<p>Pod에 패킷이 도착해도 앱이 다른 포트에서 실행 중이거나 <code>127.0.0.1</code>에만 바인딩돼 있으면 외부에서 연결할 수 없다.</p>
<pre><code class="language-text">정상: 0.0.0.0:8080 또는 :::8080
문제: 127.0.0.1:8080</code></pre>
<p>운영 이미지에 진단 도구가 없다면 임시 디버그 컨테이너를 붙일 수 있다.</p>
<pre><code class="language-bash">kubectl debug -it &lt;pod-name&gt; \
  --image=nicolaka/netshoot \
  --target=app</code></pre>
<p>그리고 다음을 대조한다.</p>
<ul>
<li>Service의 <code>targetPort</code></li>
<li>Pod의 <code>containerPort</code></li>
<li>애플리케이션이 실제로 Listen하는 포트와 주소</li>
</ul>
<p><code>containerPort</code>는 주로 문서화와 이름 참조에 쓰이며, 그 값을 적었다고 앱이 자동으로 해당 포트에서 실행되는 것은 아니다.</p>
<h2 id="106-장애-시-복구와-조사-순서">10.6 장애 시 복구와 조사 순서</h2>
<p>최근 배포 직후 전체 오류가 발생했다면 서비스를 먼저 복구하고 원인을 조사한다.</p>
<pre><code class="language-text">0. 최근 배포와 설정 변경 확인
1. 명확히 관련 있다면 롤백
2. Pod IP 직접 호출
3. Endpoint 확인
4. Service 이름으로 호출
5. Ingress ADDRESS와 규칙 확인
6. DNS 확인
7. 클러스터 외부에서 호출</code></pre>
<p>이 순서를 따르면 정상인 구간을 하나씩 제외할 수 있다. 인증서와 외부 DNS는 배포와 무관하게 실패할 수 있으므로 별도의 상시 감시가 필요하다.</p>

<h1 id="11장-ingress와-외부-노출">11장. Ingress와 외부 노출</h1>
<h2 id="111-ingress가-해결하는-문제">11.1 Ingress가 해결하는 문제</h2>
<p>서비스마다 Load Balancer를 하나씩 만들면 비용과 관리 대상이 늘어난다. Ingress는 하나의 외부 진입점에서 HTTP의 Host와 Path를 기준으로 여러 Service에 요청을 전달한다.</p>
<pre><code class="language-text">                        /orders → order-service
사용자 → Load Balancer → /users  → user-service
                        /        → web-service</code></pre>
<ul>
<li>LoadBalancer Service는 주로 L4 TCP 단위로 처리한다.</li>
<li>Ingress는 L7 HTTP 정보를 이용해 Host와 Path로 분기할 수 있다.</li>
</ul>
<h2 id="112-ingress와-ingress-controller">11.2 Ingress와 Ingress Controller</h2>
<ul>
<li><strong>Ingress</strong>: 라우팅 규칙을 담은 Kubernetes 리소스</li>
<li><strong>Ingress Controller</strong>: 규칙을 읽고 실제 프록시나 클라우드 Load Balancer를 구성하는 프로그램</li>
</ul>
<p>Ingress 리소스만 만들고 이를 처리할 Controller가 없다면 트래픽 경로는 생성되지 않는다.</p>
<table>
<thead>
<tr>
<th>Controller</th>
<th>실제 구성 요소</th>
<th>특징</th>
</tr>
</thead>
<tbody><tr>
<td>AWS Load Balancer Controller</td>
<td>ALB/NLB</td>
<td>AWS 서비스, 인증서, WAF 연동</td>
</tr>
<tr>
<td>ingress-nginx</td>

<p>여러 Ingress가 하나의 Controller 설정으로 합쳐질 수 있으므로 Host와 리소스 이름을 고유하게 관리해야 한다.</p>
<h2 id="113-ingress-매니페스트">11.3 Ingress 매니페스트</h2>
<p>아래는 일반적인 구조 예시다. Annotation은 설치된 Controller에 따라 달라진다.</p>
<pre><code class="language-yaml">apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: example-api
spec:
  ingressClassName: &lt;controller-class&gt;
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: example-api
                port:
                  number: 80</code></pre>
<p><code>ingressClassName</code>은 어느 Controller가 이 Ingress를 처리할지 지정한다.</p>
<p>클라우드 Controller에서 여러 Ingress가 Load Balancer를 공유할 수 있는 기능을 제공하기도 한다. 이 설정을 빠뜨리면 Ingress마다 별도 Load Balancer가 생길 수 있으므로 사용 중인 Controller 문서를 확인해야 한다.</p>
<h2 id="114-host와-path-라우팅">11.4 Host와 Path 라우팅</h2>
<pre><code class="language-yaml">rules:
  - host: api.example.com
    http:
      paths:
        - path: /orders
          pathType: Prefix
          backend:
            service:
              name: order-api
              port:
                number: 80
        - path: /users
          pathType: Prefix
          backend:
            service:
              name: user-api
              port:
                number: 80</code></pre>
<p>경로가 겹칠 때는 일반적으로 더 구체적인 규칙이 우선한다.</p>
<pre><code class="language-text">Exact /api/orders
→ Prefix /api/v1
→ Prefix /api
→ Prefix /</code></pre>
<p><code>/</code>는 가장 넓은 catch-all 경로이므로 다른 경로를 가리지 않도록 주의한다. Host를 생략하면 예상하지 않은 도메인의 요청까지 받을 수 있어 운영에서는 명확한 Host를 지정하는 것이 안전하다.</p>
<h2 id="115-https">11.5 HTTPS</h2>
<p>클라우드 Load Balancer에서 TLS를 종료하는 구성에서는 사용자는 HTTPS로 접속하지만 애플리케이션에는 HTTP로 전달될 수 있다.</p>
<pre><code class="language-text">사용자 --HTTPS--&gt; Load Balancer --HTTP--&gt; Service/Pod</code></pre>
<p>애플리케이션은 <code>X-Forwarded-Proto</code> 같은 전달 헤더를 올바르게 해석해야 한다. 그렇지 않으면 HTTPS 접속 후 HTTP 주소로 리다이렉트되거나 무한 리다이렉트가 발생할 수 있다.</p>
<p>인증서 식별자와 실제 도메인은 코드 예제나 공개 저장소에 직접 노출하지 않는다. 인증서 갱신과 만료는 배포와 별도로 감시한다.</p>

<h2 id="122-configmap">12.2 ConfigMap</h2>
<p>ConfigMap에는 문자열 키-값이나 파일 내용을 저장할 수 있다.</p>
<pre><code class="language-yaml">apiVersion: v1
kind: ConfigMap
metadata:
  name: example-config
data:
  SPRING_PROFILES_ACTIVE: &quot;prod&quot;
  LOG_LEVEL: &quot;INFO&quot;
  REQUEST_TIMEOUT_MS: &quot;3000&quot;
  application-prod.yml: |
    server:
      shutdown: graceful</code></pre>
<p>YAML에서 숫자나 불린으로 해석되지 않도록 설정값을 문자열로 명확히 표현하는 것이 안전하다.</p>
<h2 id="123-환경변수로-주입">12.3 환경변수로 주입</h2>
<pre><code class="language-yaml">env:
  - name: SPRING_PROFILES_ACTIVE
    valueFrom:
      configMapKeyRef:
        name: example-config
        key: SPRING_PROFILES_ACTIVE
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: example-secret
        key: db-password
envFrom:
  - configMapRef:
      name: example-config</code></pre>
<p>환경변수는 컨테이너가 시작할 때 정해진다. ConfigMap이나 Secret을 변경해도 실행 중인 컨테이너의 환경변수는 자동으로 바뀌지 않으므로 Pod를 다시 만들어야 한다.</p>
<pre><code class="language-bash">kubectl rollout restart deployment/example-api</code></pre>
<h2 id="124-볼륨으로-주입">12.4 볼륨으로 주입</h2>
<p>ConfigMap을 볼륨으로 마운트하면 각 키가 파일이 된다.</p>
<pre><code class="language-yaml">volumes:
  - name: config
    configMap:
      name: example-config
containers:
  - name: app
    volumeMounts:
      - name: config
        mountPath: /config
        readOnly: true</code></pre>
<p>마운트된 파일은 일정 시간이 지나 갱신될 수 있지만, 애플리케이션이 파일을 다시 읽어야 실제 동작에 반영된다. 기존 파일이 있는 디렉터리에 마운트하면 원래 내용이 가려질 수 있으므로 경로를 신중하게 선택한다.</p>
<h2 id="125-설정-우선순위와-실제-값-확인">12.5 설정 우선순위와 실제 값 확인</h2>
<p>일반적으로 컨테이너에 직접 지정한 환경변수가 이미지의 기본 환경변수를 덮는다. 프레임워크에도 자체 설정 우선순위가 있으므로 최종값은 실행 중인 컨테이너에서 확인하는 것이 가장 정확하다.</p>
<pre><code class="language-bash">kubectl exec &lt;pod-name&gt; -- env | sort</code></pre>
<p>ConfigMap 변경 시 Pod 템플릿도 바뀌게 만드는 대표 방식은 다음과 같다.</p>
<ul>
<li>수동 <code>rollout restart</code></li>
<li>ConfigMap 내용의 해시를 Pod template annotation에 기록</li>
<li>버전이 포함된 ConfigMap 이름 사용</li>
<li>변경 감지 Controller 사용</li>
<li>파일 마운트 후 애플리케이션의 동적 재로딩 사용</li>
</ul>
<h2 id="126-secret은-암호화와-다르다">12.6 Secret은 암호화와 다르다</h2>
<p>Kubernetes Secret의 <code>data</code>는 base64로 표현된다. base64는 암호화가 아니므로 읽기 권한이 있으면 원래 값을 쉽게 확인할 수 있다.</p>
<p>보호 원칙은 다음과 같다.</p>
<ul>
<li>Secret 조회 권한을 RBAC으로 최소화한다.</li>
<li>Secret YAML과 출력 결과를 Git, 메신저, 문서에 남기지 않는다.</li>
<li>클러스터의 etcd 암호화 설정을 확인한다.</li>
<li>운영에서는 Secrets Manager, Vault, External Secrets 등의 사용을 검토한다.</li>
<li>실제 값은 코드에 적지 않고 안전한 입력 경로를 사용한다.</li>
</ul>
<p>Secret은 <code>stringData</code>를 통해 생성할 수 있지만, YAML에 쓴 값 자체는 평문이므로 해당 파일을 저장소에 커밋하면 안 된다.</p>
<pre><code class="language-yaml">apiVersion: v1
kind: Secret
metadata:
  name: example-secret
type: Opaque
stringData:
  db-password: &quot;&lt;provide-securely-at-deploy-time&gt;&quot;</code></pre>
<p>민감도가 높은 값은 환경변수보다 읽기 전용 파일 마운트를 고려할 수 있다. 환경변수는 로그, 진단 출력, 프로세스 정보 등에 노출될 가능성이 있다.</p>

<h2 id="128-pv-pvc-storageclass">12.8 PV, PVC, StorageClass</h2>
<ul>
<li><strong>PVC(PersistentVolumeClaim)</strong>: 애플리케이션이 제출하는 저장 공간 요청서</li>
<li><strong>PV(PersistentVolume)</strong>: 실제로 연결된 저장 볼륨</li>
<li><strong>StorageClass</strong>: 어떤 종류의 저장소를 어떻게 만들지 정의한 방식</li>
</ul>
<pre><code class="language-text">Pod → PVC 10Gi 요청 → StorageClass → PV 생성 → 실제 디스크 연결</code></pre>
<pre><code class="language-yaml">apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: example-data
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: &lt;storage-class&gt;
  resources:
    requests:
      storage: 10Gi</code></pre>
<p>Pod에서는 PVC를 볼륨으로 참조한다.</p>
<pre><code class="language-yaml">volumes:
  - name: data
    persistentVolumeClaim:
      claimName: example-data
containers:
  - name: app
    volumeMounts:
      - name: data
        mountPath: /data</code></pre>
<p><code>WaitForFirstConsumer</code> 방식에서는 PVC가 먼저 <code>Pending</code>이어도 정상일 수 있다. Pod가 배치될 Node와 가용 영역이 정해진 후 볼륨을 만든다.</p>

<td>성능과 백업을 고려한 블록 스토리지</td>
</tr>
<tr>
<td>여러 Pod의 공유 파일</td>
<td>공유 파일 스토리지</td>
</tr>

<p>PVC 삭제 시 실제 스토리지와 데이터가 함께 삭제되는지는 PV의 reclaim policy에 따라 달라진다. 삭제 전에 반드시 확인한다.</p>

<h1 id="13장-리소스와-배포-실전">13장. 리소스와 배포 실전</h1>
<h2 id="131-requests와-limits">13.1 requests와 limits</h2>
<ul>
<li><strong>requests</strong>: Scheduler가 Pod를 배치할 때 확보해야 한다고 판단하는 자원</li>
<li><strong>limits</strong>: 컨테이너가 사용할 수 있는 최대 자원</li>
</ul>
<pre><code class="language-yaml">resources:
  requests:
    cpu: 200m
    memory: 512Mi
  limits:
    cpu: &quot;1&quot;
    memory: 1Gi</code></pre>
<table>
<thead>
<tr>
<th>자원</th>
<th>limit 초과 시</th>
</tr>
</thead>
<tbody><tr>
<td>CPU</td>
<td>사용 속도가 제한되어 느려짐(Throttling)</td>
</tr>
<tr>
<td>Memory</td>
<td>OOMKilled로 컨테이너 종료 가능</td>
</tr>
</tbody></table>
<p>Scheduler는 주로 requests를 기준으로 배치한다. requests가 없으면 노드에 너무 많은 Pod가 몰릴 수 있고, 지나치게 크게 설정하면 Pod가 배치되지 않거나 노드를 낭비한다.</p>
<h2 id="132-단위">13.2 단위</h2>
<pre><code class="language-text">CPU 1000m = 1 vCPU
CPU 500m  = 0.5 vCPU

Memory 1Gi = 1024Mi</code></pre>
<p>메모리는 <code>Mi</code>, <code>Gi</code>처럼 1024 기반 단위를 일관되게 사용하는 것이 좋다. Node의 전체 용량이 아니라 시스템 예약분을 제외한 <code>Allocatable</code>을 기준으로 Pod가 배치된다.</p>
<h2 id="133-qos-class">13.3 QoS Class</h2>
<p>QoS는 requests와 limits 설정 결과로 자동 결정된다.</p>
<table>
<thead>
<tr>
<th>QoS</th>
<th>조건</th>
<th>자원 부족 시 보호 수준</th>
</tr>
</thead>
<tbody><tr>
<td>Guaranteed</td>
<td>모든 컨테이너의 CPU·Memory requests와 limits가 각각 같음</td>
<td>가장 높음</td>
</tr>
<tr>
<td>Burstable</td>
<td>requests 또는 limits가 일부 설정됨</td>
<td>중간</td>
</tr>
<tr>
<td>BestEffort</td>
<td>requests와 limits가 모두 없음</td>
<td>가장 먼저 축출될 수 있음</td>
</tr>
</tbody></table>
<p>중요한 서비스일수록 실제 사용량을 측정해 적절한 requests와 limits를 설정해야 한다.</p>
<h2 id="134-쿠버네티스에서-운영하기-좋은-앱의-조건">13.4 쿠버네티스에서 운영하기 좋은 앱의 조건</h2>
<ul>
<li>설정을 환경에서 읽는다.</li>
<li>로그를 stdout/stderr로 출력한다.</li>
<li>세션과 파일 같은 상태를 프로세스 밖에 둔다.</li>
<li>빠르게 시작하고 정상 종료 절차를 지원한다.</li>
<li>liveness와 readiness용 health endpoint를 제공한다.</li>
<li>컨테이너 하나에는 주 역할의 프로세스 하나를 둔다.</li>
</ul>
<p>Pod는 언제든 교체될 수 있다는 전제로 설계해야 한다.</p>
<h2 id="135-spring-boot-actuator-예시">13.5 Spring Boot Actuator 예시</h2>
<p>관리 엔드포인트를 일반 서비스 포트와 분리하면 외부 노출을 제어하기 쉽다.</p>
<pre><code class="language-yaml">management:
  server:
    port: 8081
  endpoint:
    health:
      probes:
        enabled: true
      show-details: never

server:
  shutdown: graceful

spring:
  lifecycle:
    timeout-per-shutdown-phase: 25s</code></pre>
<ul>
<li>liveness는 애플리케이션 프로세스 자체의 생존 여부를 확인한다.</li>
<li>readiness는 현재 요청을 처리할 준비가 됐는지 확인한다.</li>
<li>관리 endpoint의 상세 내부 정보를 외부에 공개하지 않는다.</li>
</ul>
<h2 id="136-graceful-shutdown">13.6 Graceful Shutdown</h2>
<p>Pod 종료는 즉시 프로세스를 강제 종료하는 과정이 아니다.</p>
<pre><code class="language-text">종료 요청
→ preStop 실행
→ SIGTERM 전달
→ 애플리케이션이 진행 중 요청 마무리
→ 유예 시간 내 종료되지 않으면 SIGKILL</code></pre>
<pre><code class="language-yaml">spec:
  terminationGracePeriodSeconds: 40
  containers:
    - name: app
      lifecycle:
        preStop:
          exec:
            command: [&quot;sh&quot;, &quot;-c&quot;, &quot;sleep 5&quot;]</code></pre>
<p>시간은 다음 관계를 만족하도록 여유 있게 정한다.</p>
<pre><code class="language-text">preStop 시간 + 애플리케이션 종료 유예 &lt; terminationGracePeriodSeconds</code></pre>
<p>컨테이너 이미지의 ENTRYPOINT도 애플리케이션이 SIGTERM을 받을 수 있는 exec 형식으로 구성해야 한다.</p>
<h2 id="137-운영형-deployment-예시">13.7 운영형 Deployment 예시</h2>
<pre><code class="language-yaml">apiVersion: apps/v1
kind: Deployment
metadata:
  name: example-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: example-api
  template:
    metadata:
      labels:
        app: example-api
    spec:
      terminationGracePeriodSeconds: 40
      containers:
        - name: app
          image: registry.example.com/example-api:1.0.0-a1b2c3d
          ports:
            - name: http
              containerPort: 8080
            - name: management
              containerPort: 8081
          envFrom:
            - configMapRef:
                name: example-config
            - secretRef:
                name: example-secret
          resources:
            requests:
              cpu: 300m
              memory: 768Mi
            limits:
              cpu: &quot;1&quot;
              memory: 1Gi
          lifecycle:
            preStop:
              exec:
                command: [&quot;sh&quot;, &quot;-c&quot;, &quot;sleep 5&quot;]</code></pre>
<p>숫자는 그대로 복사하기보다 실제 사용량과 시작 시간, 요청 처리 시간을 측정해 정한다.</p>
<h2 id="138-세-가지-probe와-security-context">13.8 세 가지 Probe와 Security Context</h2>
<pre><code class="language-yaml">startupProbe:
  httpGet:
    path: /actuator/health/liveness
    port: management
  periodSeconds: 5
  failureThreshold: 30

livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: management
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 3

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: management
  periodSeconds: 5
  timeoutSeconds: 3
  failureThreshold: 3

securityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true</code></pre>
<p><code>readOnlyRootFilesystem: true</code>를 사용하면 <code>/tmp</code> 같은 쓰기 경로도 막힌다. 애플리케이션이 임시 파일을 써야 한다면 필요한 경로에 <code>emptyDir</code> 등을 별도로 마운트한다.</p>
<h2 id="139-service와-ingress-연결">13.9 Service와 Ingress 연결</h2>
<p>일반 사용자 트래픽에는 서비스 포트만 공개하고 관리 포트는 내부 health check 용도로 제한한다.</p>
<pre><code class="language-yaml">apiVersion: v1
kind: Service
metadata:
  name: example-api
spec:
  selector:
    app: example-api
  ports:
    - name: http
      port: 80
      targetPort: http</code></pre>
<p>Ingress는 이 Service의 80번 포트로 연결한다. 외부 Load Balancer가 별도의 health check를 사용한다면 readiness 경로와 관리 포트를 안전하게 참조하도록 구성하되, 관리 포트 자체를 일반 사용자에게 노출하지 않는다.</p>

<h1 id="전체-연결-정리">전체 연결 정리</h1>
<p>하나의 배포를 기준으로 2일차 내용을 연결하면 다음과 같다.</p>
<pre><code class="language-text">1. Deployment가 원하는 버전과 Pod 수를 선언한다.
2. ReplicaSet이 필요한 수만큼 Pod를 유지한다.
3. readinessProbe를 통과한 Pod가 Service Endpoint에 등록된다.
4. Service가 바뀌는 Pod들에 고정된 이름과 접근점을 제공한다.
5. Ingress가 외부 Host/Path 요청을 Service로 전달한다.
6. ConfigMap과 Secret이 환경별 설정을 주입한다.
7. PVC가 Pod보다 오래 보존해야 할 데이터를 저장한다.
8. requests와 limits가 배치와 실행 중 자원 사용을 제어한다.
9. 롤링 업데이트와 graceful shutdown이 배포 중 요청 손실을 줄인다.
10. 장애가 나면 Pod → Endpoint → Service → Ingress → DNS 순서로 구간을 확인한다.</code></pre>
<p>쿠버네티스 운영에서 가장 중요한 관점은 <strong>Pod는 언제든 교체될 수 있다</strong>는 사실이다. 주소는 Service로 고정하고, 설정은 이미지 밖에서 주입하며, 데이터는 Pod 밖에 보관하고, 준비 상태와 종료 절차를 명확하게 만들어야 한다.</p>

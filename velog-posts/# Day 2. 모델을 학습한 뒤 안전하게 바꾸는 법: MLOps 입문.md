<h2 id="오늘의-질문-모델이-하나-더-생겼다면-바로-교체해도-될까">오늘의 질문: 모델이 하나 더 생겼다면 바로 교체해도 될까?</h2>
<p>Day 1에는 학습된 모델을 API로 호출하는 방법을 배웠다. 그런데 새 모델을 만들었다고 운영 중인 모델을 곧바로 덮어쓰면 문제가 생길 수 있다. 새 모델이 더 나쁠 수도 있고, 어떤 데이터·설정으로 학습했는지 모를 수도 있기 때문이다.</p>
<p>Day 2의 목표는 <strong>실험 기록 → 성능 검증 → 모델 버전 등록 → 승인된 모델만 서빙 → 같은 환경에서 배포</strong>라는 안전한 교체 절차를 이해하는 것이다.</p>
<pre><code class="language-text">새 데이터와 코드
    ↓
모델 학습 + 실험 기록
    ↓
성능·입력 형식 검사
    ├─ 실패: 기존 운영 모델 유지
    └─ 통과: 새 버전 등록·승격
                     ↓
               API가 승인된 모델 로드
                     ↓
               컨테이너로 실행·검증</code></pre>
<p>예시는 ‘다음 날 가격을 예측하는 서비스’로 들되, 같은 흐름을 자전거 수요나 전력 사용량 예측에도 적용할 수 있다.</p>
<h2 id="part-1-mlops-개요---왜-모델도-운영-절차가-필요할까">Part 1. MLOps 개요 - 왜 모델도 운영 절차가 필요할까?</h2>
<h3 id="1-1-devops와-mlops">1-1. DevOps와 MLOps</h3>

<h3 id="1-2-ml-라이프사이클과-성숙도">1-2. ML 라이프사이클과 성숙도</h3>
<p>모델은 <code>데이터 준비 → 학습 → 검증 → 배포 → 운영 관찰 → 개선</code>을 반복한다. 강의는 수동 노트북 작업, 실험·버전 관리가 있는 파이프라인, 배포 후 감시·자동 대응으로 발전하는 단계를 소개한다. 이 단계 이름은 학습을 위한 구분이며, 특정 도구 하나를 설치했다고 자동으로 성숙도가 올라가는 것은 아니다.</p>
<p>Day 2는 주로 <strong>학습부터 안전한 배포까지</strong>를 다루고, Day 3는 배포 후 성능이 떨어지는지 관찰하고 대응하는 과정을 더한다.</p>
<h2 id="part-2-모델-버전-관리와-레지스트리---새-모델과-운영-모델을-분리하기">Part 2. 모델 버전 관리와 레지스트리 - ‘새 모델’과 ‘운영 모델’을 분리하기</h2>
<h3 id="2-1-mlflow의-tracking은-실험-일지">2-1. MLflow의 Tracking은 실험 일지</h3>
<p>새 모델을 학습할 때마다 다음을 한 묶음의 실행 기록(run)으로 남긴다고 생각하면 쉽다.</p>

<p>예를 들어 ‘최근 5일 평균’을 입력에 추가해 모델을 다시 학습했다면, <strong>무엇을 바꿨고 점수가 어떻게 달라졌는지</strong>를 기록해야 개선인지 판단할 수 있다. 점수 하나만 따로 메모하면 어떤 모델의 점수인지 잊기 쉽다.</p>
<h3 id="2-2-registry는-모델-버전-창고">2-2. Registry는 모델 버전 창고</h3>
<p>Tracking이 실험 일지라면 Model Registry는 <strong>등록된 모델 버전을 관리하는 창고</strong>다. <code>v1</code>, <code>v2</code>처럼 버전을 구분하고, 어떤 버전을 운영에 사용할지 정한다. 강의의 <code>None → Staging → Production</code>은 ‘등록됨 → 검토 중 → 운영 승인’이라는 흐름으로 이해하면 된다.</p>
<p>중요한 점은 <strong>등록과 운영 투입이 다르다</strong>는 것이다. 성능 기준에 못 미치는 모델도 실험 기록은 남길 수 있지만, 운영 모델로 승격해서는 안 된다.</p>
<h3 id="2-3-api는-왜-모델-버전을-직접-적지-않을까">2-3. API는 왜 모델 버전을 직접 적지 않을까?</h3>
<p>예측 API가 항상 코드에 고정된 <code>v1</code> 파일만 읽으면 모델을 바꿀 때마다 서빙 코드를 고쳐야 한다. 반면 ‘운영 승인된 모델’을 읽도록 하면 새 버전을 승인하고 서버가 다시 로드할 때 모델을 교체할 수 있다.</p>
<p>다만 <strong>레지스트리에서 승격했다고 이미 실행 중인 서버의 메모리 속 모델이 저절로 바뀌는 것은 아니다.</strong> 재시작하거나 캐시를 비우고 새 모델을 로드하는 절차가 필요하다. 또 학습 때 사용한 정규화 기준과 서빙 때의 정규화 기준이 다르면 같은 입력도 엉뚱한 값으로 변환될 수 있으므로 모델과 전처리 정보를 함께 관리해야 한다.</p>
<h2 id="part-3-cicd-for-ml---반복-작업을-안전한-순서로-묶기">Part 3. CI/CD for ML - 반복 작업을 안전한 순서로 묶기</h2>
<p>CI/CD를 ‘새 코드나 모델을 검사하고 내보내는 자동 통로’라고 생각해 보자. 모델 서비스에서는 다음 순서를 설계할 수 있다.</p>
<ol>
<li>새 데이터와 코드가 들어온다.</li>
<li>정해진 절차로 모델을 학습하고 기록한다.</li>
<li>입력 형식과 예측 성능을 검사한다.</li>
<li>기준을 만족할 때만 새 모델을 승인한다.</li>
<li>배포 후 API가 실제로 새 버전을 사용하는지 확인한다.</li>
</ol>
<p>가령 새 모델의 RMSE가 기준보다 크다면 4번으로 넘어가지 않고 <strong>기존 운영 모델을 유지</strong>한다. 이것이 배포 게이트(gate)다. 문 앞에서 출입 조건을 확인하는 경비원에 비유할 수 있다.</p>
<p>강의에 나온 CI 스크립트는 전체 흐름을 이해시키는 예시다. <strong>자동 학습, 컨테이너 재배포, 롤백이 실제로 모두 연결됐는지는 실행 코드와 로그로 별도 확인</strong>해야 한다. 또한 모델이 더 정확하더라도 테스트 데이터가 잘못 분리됐거나 입력 스키마가 달라졌다면 배포를 멈춰야 한다.</p>
<h2 id="part-4-dockerize---실행-환경을-함께-포장하기">Part 4. Dockerize - 실행 환경을 함께 포장하기</h2>

<h3 id="4-2-같은-환경이-곧-항상-같은-예측값은-아니다">4-2. ‘같은 환경’이 곧 ‘항상 같은 예측값’은 아니다</h3>
<p>패키지 버전을 고정하면 환경 차이를 줄일 수 있지만, 같은 결과를 보장하려면 <strong>데이터, 전처리, 모델 파일, 난수 시드, 실행 조건</strong>도 확인해야 한다. 교재의 ‘로컬과 서버에서 점수가 달라지는’ 숫자는 환경 불일치를 설명하기 위한 사례이지, 모든 서비스에서 반드시 재현되는 값이 아니다.</p>
<p>강의에는 API와 MLflow 서버를 별도 컨테이너로 두는 그림이 나온다. 반면 제공된 축약 실습은 <strong>한 컨테이너 안에서 모델 등록 정보와 API를 함께 사용하는 형태</strong>다. 두 방식은 아키텍처 선택지가 다른 것이므로 강의 그림을 실행 결과로 착각하지 말자. 실제 운영에서는 저장소 영속성과 서버 분리 여부까지 설계해야 한다.</p>
<h2 id="part-5-데이터·모델-검증---배포-전-두-개의-문턱">Part 5. 데이터·모델 검증 - 배포 전 두 개의 문턱</h2>
<h3 id="5-1-입력-데이터-검증">5-1. 입력 데이터 검증</h3>
<p>모델이 숫자 두 개를 기대하는데 문자열이 들어오거나, 최근 20개 시점이 필요한데 19개만 들어오면 예측을 진행할 수 없다. API 스키마는 입력의 <strong>형식·길이·값 범위</strong>를 검사해 잘못된 요청을 먼저 거절한다.</p>
<p>예: 수량은 음수가 아니어야 하고, 날짜는 오래된 순서부터 최근 순서로 정렬되어야 한다. 형식 검증이 통과해도 날짜 순서 같은 <strong>의미상의 오류</strong>는 별도 검사가 필요할 수 있다.</p>
<h3 id="5-2-rmse로-성능-검증">5-2. RMSE로 성능 검증</h3>
<p>RMSE는 예측값과 실제값의 차이를 제곱해 평균 낸 뒤 제곱근을 취한 값이다.</p>
<pre><code class="language-text">RMSE = √(오차²의 평균)</code></pre>
<p>실제값이 <code>[100, 104]</code>, 예측값이 <code>[102, 102]</code>라면 오차는 <code>[-2, 2]</code>이고 RMSE는 <code>2</code>다. 제곱이 들어가므로 큰 실수에 더 민감하다. 단위는 예측 대상과 같다. 가격 예측이면 가격 단위, 대여량 예측이면 대수 단위다.</p>
<p>교재는 <code>RMSE ≤ 4</code> 같은 <strong>절대 기준</strong>과 ‘기존 운영 모델보다 크게 나빠지지 않을 것’이라는 <strong>상대 기준</strong>을 함께 소개한다. 기준 4는 어디서나 쓰는 정답이 아니라, 서비스가 감당할 수 있는 오차와 과거 모델 성능을 보고 정하는 예시다.</p>

<p>시계열은 과거로 학습하고 미래로 평가해야 한다. 미래의 데이터를 학습에 섞거나 <strong>전체 기간으로 학습한 스케일러를 과거 학습 구간에도 사용하면</strong> 미래 정보가 스며들어 평가 결과가 낙관적으로 보일 수 있다. 전처리 도구도 학습 구간에서만 맞춘 뒤 평가 구간에 적용해야 한다.</p>

<h3 id="mlops와-aiops는-어떻게-다를까">MLOps와 AIOps는 어떻게 다를까?</h3>
<p><strong>MLOps</strong>는 예측 모델 자체의 학습·검증·배포·운영을 관리한다. <strong>AIOps</strong>는 운영 중 쌓이는 로그·지표·이벤트를 활용해 서비스나 인프라의 이상을 찾고 대응하는 데 초점을 둔다. 예를 들어 ‘내일 전력 사용량을 예측하는 모델을 교체하는 과정’은 MLOps이고, ‘서버 응답 시간이 갑자기 늘어난 원인을 로그에서 탐지해 운영자에게 알리는 일’은 AIOps에 가깝다. 실제 서비스에서는 두 영역이 연결될 수 있다.</p>
<p>운영 중 입력값의 분포가 달라졌다고 해서 <strong>반드시</strong> 예측 오차가 커진 것은 아니다. 데이터 변화는 드리프트 점검의 신호이고, 모델 성능 저하는 나중에 확보한 실제값과 예측값을 비교해야 확인할 수 있다. 예를 들어 출근 시간대 이용자가 늘어도 모델이 이를 잘 예측하면 입력 분포는 변했지만 성능은 유지될 수 있다.</p>
<h2 id="part-7-통합-실습---기록부터-서빙-검증까지">Part 7. 통합 실습 - 기록부터 서빙 검증까지</h2>
<p>교재의 마지막 파트는 앞의 여섯 파트를 한 흐름으로 잇는다. 초보자라면 다음 순서로 점검하자.</p>
<ol>
<li><strong>기준 모델 준비</strong>: 입력 형식과 전처리 기준을 확인한다.</li>
<li><strong>새 모델 학습</strong>: 실행마다 파라미터·지표·모델 파일을 함께 기록한다.</li>
<li><strong>게이트 판단</strong>: 실제 평가 점수가 기준을 통과했는지 확인한다. 숫자가 예시 슬라이드와 같을 필요는 없다.</li>
<li><strong>버전 등록·승격</strong>: 통과한 모델만 운영용으로 지정한다.</li>
<li><strong>API 연결</strong>: API가 운영용 모델과 일치하는 전처리 기준을 읽는지 확인한다.</li>
<li><strong>컨테이너 실행</strong>: 빌드가 성공했는지뿐 아니라 API 호출까지 성공하는지 확인한다.</li>
<li><strong>재시작 후 재확인</strong>: 다시 켜도 같은 운영 버전을 읽는지 확인한다.</li>
</ol>
<h3 id="왜-교재의-예시-숫자와-내-결과가-다를-수-있을까">왜 교재의 예시 숫자와 내 결과가 다를 수 있을까?</h3>
<p>교재에는 <strong>두 모델을 비교하고 입력 피처를 개선하는 설명용 시나리오</strong>가 있다. 배포된 실습 스켈레톤은 이 흐름을 단순화해 <strong>하나의 시계열 모델을 학습하고 기준을 통과하면 등록하는 구조</strong>다. 데이터 기간, 입력 피처, 학습 반복 횟수, 컨테이너 구성도 자료 버전에 따라 다를 수 있다. 따라서 예시의 RMSE나 버전 번호를 자신의 실측값처럼 적지 말고, <strong>현재 실행한 코드·데이터·로그</strong>를 기준으로 기록해야 한다.</p>
<h3 id="완료-여부를-판단하는-질문">완료 여부를 판단하는 질문</h3>
<ul>
<li>새 학습 실행의 설정과 평가 지표를 확인할 수 있는가?</li>
<li>기준에 못 미치면 기존 운영 모델이 유지되는가?</li>
<li>API 응답에서 어떤 모델 버전을 썼는지 알 수 있는가?</li>
<li>컨테이너에서 같은 입력에 정상 응답하는가?</li>
<li>재시작 후에도 의도한 모델을 읽는가?</li>
</ul>
<p>하나라도 확인하지 못했다면 ‘완료’ 대신 <strong>미검증</strong>으로 기록한다. 특히 실습 코드에 미완성 함수가 있으면 등록까지 성공해도 모델 로딩이나 컨테이너 기동은 실패할 수 있다.</p>
<h2 id="day-2를-한-문장으로">Day 2를 한 문장으로</h2>
<p><strong>MLOps는 새 모델을 무조건 배포하는 기술이 아니라, 어떤 실험에서 나온 모델인지 기록하고, 충분히 검증한 버전만 안전하게 교체하는 운영 절차다.</strong> 다음 단계에서는 이렇게 배포한 모델이 시간이 지나도 계속 잘 작동하는지 감시한다.</p>
